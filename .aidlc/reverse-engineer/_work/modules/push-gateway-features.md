## Module: buzz-push-gateway (`crates/buzz-push-gateway`)
### Aspect: Features

#### What this service is

`buzz-push-gateway` is a standalone binary (`Cargo.toml:1-16`) implementing the "Public APNs Gateway Profile" of NIP-PL (`docs/nips/NIP-PL.md`, section "Public APNs Gateway Profile (Buzz, normative)"). Its own doc comment describes it as a "Stateful, capability-gated APNs last hop for NIP-PL" (lib.rs:1) and its `Cargo.toml` description is "Blind, capability-gated NIP-PL gateway for the Buzz mobile app" (Cargo.toml:3). It is deployed as `https://push.buzz.xyz`, a single deployment-global, multi-relay-tenant service — not a per-community or per-relay-deployment component. It is built by a dedicated `Dockerfile.push-gateway` and published as a separate container image (`ghcr.io/block/buzz-push-gateway`), independent of the main relay image.

#### End-to-end flow it implements

1. **Discovery (out of scope, mobile-side):** the mobile app reads a relay's NIP-11 `push` descriptor to learn the gateway's `endpoint`/keys, per `docs/nips/NIP-PL.md`'s "Executor Discovery" section.
2. **Challenge:** app calls `POST /v1/installations/challenges` to get a single-use 32-byte challenge (http.rs:110-133), valid 300 seconds.
3. **Installation enrollment:** app performs Apple App Attest key generation and attestation locally, then calls `POST /v1/installations` with the attestation, its App Attest `key_id`, its raw APNs device token (hex), and the target `app_profile` (http.rs:156-235). The gateway verifies the attestation against Apple's pinned root cert, encrypts the raw token at rest, and returns an opaque `installation_handle` UUID. This is "device registration" in this crate's own terms.
4. **Relay delegation / grant issuance:** app authorizes one specific relay (identified by its 64-hex Nostr pubkey) to request pushes on its behalf, via `POST /v1/delegations`, authenticated by a fresh App Attest assertion (http.rs:295-353). The response is an opaque `endpoint_grant` string — a capability the app then hands to the relay (out of scope here; carried inside the relay's NIP-44-encrypted push lease per NIP-PL) for the relay to store and present on every delivery.
5. **Delivery:** the relay, having matched an event against a stored lease, calls `POST /v1/deliveries/apns` with the `endpoint_grant` and a fresh `request_id`, authenticated with a NIP-98 signed-event header proving the relay's identity (http.rs:553-706). The gateway validates the grant, admits the request under a per-endpoint quota and two independent replay fences, decrypts the real APNs token only at this point, and sends exactly one fixed reconnect payload to Apple.
6. **Endpoint rotation:** when the OS hands the app a new APNs token (rotation, not reinstall), the app calls `POST /v1/installations/endpoint` to atomically swap the encrypted token and bump `endpoint_epoch`, invalidating every previously issued grant across every relay in one step (http.rs:382-437).
7. **Revocation:** the app can revoke one relay's delegation (`POST /v1/delegations/revoke`) or the entire installation (`POST /v1/installations/revoke`) — the latter is the "log out everywhere" / "uninstall" path (http.rs:457-550).
8. **Background retention:** a reaper task, run once at startup and every 300 seconds thereafter (main.rs:64-77), deletes expired challenges, expired replay-fence rows, idle quota rows (`updated_at` older than 1 day), and expired/tombstoned installations and delegations past their retention windows (postgres.rs:340-404).

#### Explicit non-features / limits

- **No application content ever crosses the gateway.** The single APNs payload constant (`APNS_RECONNECT_PAYLOAD`, model.rs:8-9) is sent for every accepted delivery regardless of what event triggered it — the gateway has no concept of message text, sender, channel, or unread count, by design (apns.rs:147-149 comment, and the NIP-PL "Wake Delivery" section: "no un-narrowed filter... byte-bounded content").
- **No FCM/Android or UnifiedPush support.** `AppProfile` has exactly two variants, both iOS/APNs (model.rs:12-16, `BuzzIosProduction`/`BuzzIosSandbox`). `docs/nips/NIP-PL.md`'s "FCM" and "UnifiedPush (optional)" transport-profile sections both state these are "not a conforming v1 public-gateway profile" — this is a documented, intentional limit, not an oversight.
- **No lease storage, matching, or coalescing.** The gateway holds zero knowledge of NIP-PL lease content, subscriptions, filters, or priority classes — that state lives entirely in the relay (`buzz-relay/src/push_runtime.rs`, `crates/buzz-relay/src/handlers/push_lease.rs`, out of this crate's scope). The gateway's only concept of "why send a push" is "a relay presented a valid, unexpired capability."
- **No retry beyond one credential-refresh retry.** As detailed in `push-gateway-business-rules.md`, the gateway performs at most one extra APNs attempt (only for `RefreshCredential`); all other retry/backoff is delegated to the calling relay via the `503 retry` response.
- **No per-relay or per-installation rate limiting**, only a per-physical-endpoint delivery quota (10 deliveries / 10 seconds by default) — see `push-gateway-security.md` for the abuse-surface implications.
- **`--migrate-only` mode has no rollback, dry-run, or down-migration support** — it is strictly "apply pending migrations then grant least-privilege," matching the single forward-only migration file present (`migrations/0001_push_gateway_authority.sql`).

#### Multi-tenancy model

Unlike the main relay (which is explicitly community/tenant-scoped per `AGENTS.md`'s "Channel scoping" section), this gateway's authority state is **deployment-global**: the migration file's own header comment states "This state is intentionally outside relay community tenancy: installations delegate to relay signing keys and may authorize multiple relay deployments" (migration.sql:1-3). One gateway deployment can serve delegations to many independent relay deployments simultaneously; the tenant-equivalent boundary here is `relay_pubkey`, not a `community_id` column — there is no `community_id` anywhere in this crate's schema or types (confirmed: no such field appears in `model.rs`, `authority.rs`, or the migration SQL).

#### Test coverage of features end-to-end

There is no integration or E2E test in this crate (or found elsewhere in the repo via search of `crates/buzz-test-client/**` for `push_gateway`/`apns`, which returned no matches) that exercises the full flow described above (challenge → enroll → delegate → deliver) against a running instance of this service. Each stage is unit-tested in isolation (see the other aspect docs for specific test citations), but the *composition* — e.g. that a grant issued by `delegate` is actually accepted by `deliver`, end-to-end through real HTTP and a real Postgres — is untested. The closest thing to a cross-stage test is `postgres.rs`'s `install_authority` helper (postgres.rs:663-687), which directly inserts an installation and delegation row via raw SQL (bypassing the HTTP handlers entirely) to set up fixtures for the admission-concurrency tests.

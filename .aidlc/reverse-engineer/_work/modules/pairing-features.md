## Module: buzz-pair-relay & buzz-pairing-cli (`crates/buzz-pair-relay`, `crates/buzz-pairing-cli`)
### Aspect: Features

#### What this module group is for, precisely

Within this scope, the delivered feature is: **a secure, human-verified, out-of-band-initiated channel for moving a Nostr secret from one device to another over an untrusted relay**, plus (a) a disposable transport for that channel and (b) a terminal harness to exercise and interop-test it. Neither crate in this scope implements the actual "add a device to my account" UX — that lives in `desktop/src-tauri/src/commands/pairing.rs` and the mobile `mobile/lib/features/pairing/` Dart feature, both outside this scope. What's directly confirmable from `buzz-pair-relay`/`buzz-pairing-cli`:

- **`buzz-pair-relay`** provides only the transport primitive: a minimal, stateless, single-purpose WebSocket router that lets exactly two ephemeral-keyed parties rendezvous and exchange a bounded number of opaque, encrypted messages (module doc, `crates/buzz-pair-relay/src/lib.rs:1-4`). It has zero awareness of "pairing" as a user-facing concept — it would behave identically for any protocol speaking kind:24134-with-a-single-`p`-tag NIP-01 events.
- **`buzz-pairing-cli`** is the only place *in this scope* that drives the actual NIP-AB protocol (via `buzz-core::pairing`) to a human-observable outcome: it can act as either the secret-holding `source` or secret-receiving `target`, and it prints the transferred secret to the terminal (`crates/buzz-pairing-cli/src/main.rs:319-325`) rather than importing it into any secure storage. Its own docs are explicit: "designed for interop testing and NIP submission, not production use" (`crates/buzz-pairing-cli/README.md:3`).

#### Concrete user-facing capability, inferred from the code

Running `buzz-pair source --relay <url> [--nsec <bech32>]` displays a `nostrpair://` URI representing the QR code — the CLI never renders an actual QR image; there is no QR-rendering dependency in `crates/buzz-pairing-cli/Cargo.toml:14-24`. The payload transferred is either a user-supplied bech32 `nsec` or, if omitted, a freshly generated throwaway test key (`resolve_payload`, `main.rs:581-599`; printed notice at `main.rs:596`, "no --nsec provided; using generated test key"). Running `buzz-pair target [--show-secret]` on a second terminal, pasting that URI, and confirming the SAS code on both sides completes the transfer; the received secret is printed only if `--show-secret` is passed (`main.rs:319-325`); otherwise the CLI confirms receipt only by payload type (`nsec`/`bunker`/`nostrconnect`/`custom`) without revealing the value.

The CLI itself only ever *constructs* the `nsec` (raw private key) payload type — `PayloadType::Nsec` is hardcoded in `resolve_payload` (`main.rs:587`, `595`). `bunker`/`connect`/`custom` are defined in the shared `buzz_core::pairing::types::PayloadType` enum (`crates/buzz-core/src/pairing/types.rs:63-71`) and are handled generically by `cmd_target`'s receive path (label-only match at `main.rs:310-316`), but nothing in `buzz-pairing-cli` ever originates a `Bunker`/`Connect`/`Custom` payload to send — the CLI can receive and display any of the four types but can only originate `Nsec` transfers.

#### What this enables at the account level — and the limits of what's confirmable

Per `NIP-AB.md`'s own Motivation section, this protocol exists to let "Users [add] their Nostr identity on multiple devices" via one-time key transfer, as an alternative to pasting a raw `nsec` insecurely or using NIP-46 remote signing. Within this scope, that translates concretely to: linking a new device's ephemeral session to an existing identity by moving the *actual private key material* to the new device — not creating a new identity, not delegating signing authority (that is NIP-46's job, explicitly called out in the spec's Motivation section as complementary, not overlapping). Whether the received key ends up "enrolled under an existing account" server-side is not something this module group does or observes — `buzz-pairing-cli` stops at printing the secret to the terminal; there is no call to any account-provisioning API anywhere in this crate. (The desktop implementation, out of scope, goes further — its `pairing.rs` calls into `AppState`/community provisioning on the target side — but that integration is not owned by these two crates.)

#### Limits, confirmed from the code

- **One secret per session, no batching**: `send_payload`/`handle_payload` each fire exactly once per session (state-machine-enforced — see Business Rules); there is no mechanism to send multiple secrets or files in one pairing run.
- **No QR image rendering**: the "QR code" is a URI string the caller is responsible for rendering/scanning by other means; this crate group only produces/consumes the string.
- **No secure storage on receipt**: `buzz-pairing-cli` never persists the received secret anywhere (keychain, file, etc.) — it is printed to stdout (gated by `--show-secret`), and the process then exits, at which point `Zeroizing<String>`'s `Drop` wipes the in-memory copy (`resolve_payload`'s `Zeroizing::new` wrapping, `main.rs:589`, `596`; `handle_payload`'s return type is `Zeroizing<String>` from `buzz-core`, `crates/buzz-core/src/pairing/session.rs:388-393`). This matches the CLI's stated purpose (interop testing), not production device onboarding.
- **No multi-device fan-out**: exactly one source and one target per session; pairing N devices requires N separate runs (matches `NIP-AB.md`'s own §Limitations: "No multi-device coordination").
- **No revocation**: once a transfer completes, this module group has no way to invalidate it — consistent with `NIP-AB.md`'s explicit "No key revocation" limitation.
- **`buzz-pair-relay` is a pure transport and cannot be repurposed for a different pairing flow without a code change** — it hardcodes `KIND_PAIR = 24134` (`crates/buzz-pair-relay/src/lib.rs:63`) and a single-`p`-tag shape, so it cannot route any other Nostr event kind or fan out to more than one recipient per event.

#### Uncertainty

Whether the delivered feature meets the bar of "production-ready device pairing" cannot be fully assessed from `buzz-pair-relay`/`buzz-pairing-cli` alone, because the account-linking behavior (importing the key into a real client identity store) lives in the desktop/mobile apps, outside this scope. What this analysis can confirm is only the transport and the CLI test harness; claims about the end-user pairing *experience* would require a full read of `desktop/src-tauri/src/commands/pairing.rs` and `mobile/lib/features/pairing/pairing_provider.dart`, which this pass only skimmed for cross-referencing (see Integrations) and does not certify in depth.

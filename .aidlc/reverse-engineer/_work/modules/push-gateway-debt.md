## Module: buzz-push-gateway (`crates/buzz-push-gateway`)
### Aspect: Debt

#### Zero mentions in `ARCHITECTURE.md` — a standalone deployed service missing from the architecture doc

I read all nine numbered sections of `ARCHITECTURE.md` (`## 1.` through `## 9.`) in full. Section 6, "Crate Reference," individually documents eleven crates/components (`buzz-core`, `buzz-auth`, `buzz-db`, `buzz-pubsub`, `buzz-search`, `buzz-audit`, `buzz-workflow`, "Huddle Audio", `buzz-relay`, `buzz-acp`, `buzz-admin`, `buzz-test-client`) — `buzz-push-gateway` is not among them, and grepping the entire file for `push`, `APNs`, `gateway`, or `App Attest` (case-insensitive) returns zero matches. Section 8, "Infrastructure," documents the docker-compose services (Postgres, Redis, Adminer, MinIO, Prometheus) but does not mention the push gateway as a deployed service, even though it ships its own `Dockerfile.push-gateway`, its own Helm chart (`deploy/charts/buzz-push-gateway/`), and its own CI publish lane (`.github/workflows/docker.yml`'s `push-gateway-build` job, `.github/workflows/push-gateway-helm-chart.yml`) — i.e. it is exactly the kind of "deployed infrastructure component" Section 8 is about, and it is absent from it. Section 7, "Security Model," documents authentication/validation/SSRF/audit/access-control/webhook security for the relay in detail but says nothing about App Attest or APNs credential handling, both unique security mechanisms introduced by this crate.

This is not unique to this crate — `ARCHITECTURE.md`'s Crate Reference also omits `buzz-media`, `buzz-persona`, `buzz-dev-mcp`, `buzz-sdk`, `buzz-cli`, `buzz-ws-client`, `buzz-agent`, `sprig`, `buzz-relay-mesh`, `buzz-pair-relay`, `buzz-pairing-cli`, `buzz-conformance`, `git-sign-nostr`, and `git-credential-nostr` — so the document as a whole has not kept pace with the crate list in `Cargo.toml`'s `[workspace] members`. What makes the push-gateway omission more significant than most of those is that it is a separately deployed, separately versioned, network-exposed **service** with its own attack surface (see `push-gateway-security.md`) and its own operational runbook (`docs/push-gateway-deployment.md`), not an internal library crate — a reader of `ARCHITECTURE.md` alone would have no idea this service exists, what it talks to, or that the relay has an outbound dependency on it (`buzz-relay/src/push_runtime.rs`). The feature is at least tracked in `CHANGELOG.md:331` ("feat(push): add public APNs gateway (#1770)"), so its introduction was recorded at commit-log granularity — the gap is specifically that `ARCHITECTURE.md` was never updated to reflect it.

`AGENTS.md`'s own repo map (`crates/` listing under "Repo Structure") also does not list `buzz-push-gateway` among the "Relay + core," "Agent surface," "Clients + interop," or "Tooling + shared" groups — it is entirely absent from that top-level crate inventory too, despite the same file documenting narrower, more internal crates like `buzz-sdk` and `git-sign-nostr`.

#### Duplicated schema DDL with no sync check

As detailed in `push-gateway-data-model.md`, the six `push_gateway_*` tables are defined identically in two places — `crates/buzz-push-gateway/migrations/0001_push_gateway_authority.sql` and the repo-root `migrations/0015_push_gateway_authority.sql` — with no shared source, no code generation, and no test asserting the two stay byte-identical (aside from the trailing `_operator_global_tables` INSERT block, which is an intentional, documented difference). A future column addition applied to only one of the two files would silently desynchronize them; nothing in `just ci`, `just test`, or any CI workflow would catch it. This is pure duplication risk with zero current functional impact (the relay-side copy is inert, per `push-gateway-data-model.md`), but it is exactly the kind of drift that becomes a production incident the day someone forgets the second file exists.

#### Duplicated wire-contract types between this crate and the relay

`crates/buzz-relay/src/push_runtime.rs:32-49` hand-declares its own `DeliveryRequest`/`DeliveryResponse` types that must stay structurally compatible with this crate's `model::DeliveryRequest`/`model::DeliveryResponse` (model.rs:29-39, 154-165) for the HTTP contract between the two services to keep working. There is no shared crate, no OpenAPI/JSON-schema contract test, and no integration test (confirmed in `push-gateway-integrations.md`) verifying the two independently-maintained type definitions actually agree on the wire. A field renamed on one side without the matching rename on the other would compile cleanly on both sides and fail only at runtime, in production, on the first delivery attempt.

#### Untested critical paths

- **Every HTTP handler in `http.rs` is untested at the handler level** (zero `#[test]`/`#[tokio::test]` in the file; no `oneshot`/`ServiceExt` usage anywhere in the crate — see `push-gateway-api-surface.md`). This includes the entire ordering of security-relevant checks in `enroll` (challenge decode → transcript build → attestation verify → challenge consume → token seal → installation create) and in `deliver` (NIP-98 verify → grant open → grant/relay cross-check → admission transaction → profile check → token open → APNs send). A refactor that silently reorders any two of these steps would not be caught by any test in this crate.
- **`token.rs` has zero tests** (confirmed via grep for `#[test]`/`#[tokio::test]` returning no matches in that file) — the AEAD sealing/opening of the raw APNs device token, the one piece of data this crate holds that is closest to a long-lived Apple credential for a real device, is unit-tested nowhere.
- **All six Postgres-backed contract/concurrency tests in `postgres.rs` are `#[ignore]`d and never run in CI** (verified: no workflow under `.github/workflows/**` passes `--ignored`/`--run-ignored` for this package). The `Justfile:291-293` comment asserts a "dedicated CI job below" runs them — I found no such job anywhere in `.github/workflows/`; this comment is itself stale/aspirational relative to the actual CI configuration (see "Stale comment" below).
- **No test exercises the `--migrate-only` argv branch** in `main.rs` (main.rs has no `#[cfg(test)]` module at all).
- **No test exercises `BUZZ_PUSH_BIND_ADDR`/`BUZZ_PUSH_HEALTH_ADDR` parsing**, default values, or invalid-address rejection.

#### "Unused" field carried on the production type

`authority.rs`'s `Installation`/`Delegation` structs carry a `revoked: bool` field that `PostgresAuthorityStore` always constructs as a hard-coded `false` (e.g. `postgres.rs:169`), because every query that builds these structs already filters `WHERE revoked_at IS NULL`. The field is only ever meaningfully read inside the crate's own `MemoryAuthorityStore` test-support implementation. This is not dead code in the `#[allow(dead_code)]` sense (the field is read, just never non-`false` in production), but it is a latent correctness trap: if a future change to `postgres.rs` ever constructs an `Installation`/`Delegation` from a query that does *not* filter on `revoked_at IS NULL`, the hard-coded `false` would silently misrepresent the row's actual state, and nothing would fail loudly (see `push-gateway-data-model.md` for full detail).

#### No `#[allow(dead_code)]`, no `TODO`/`FIXME` markers — genuinely absent, not hidden

I grepped the entire crate for `TODO`, `FIXME`, `#[allow(dead_code)]`, `unimplemented!`, and `todo!` and found zero matches for all of them (the one `#[allow(...)]` in the whole crate is the documented `#[allow(clippy::too_many_arguments)]` at authority.rs:151, discussed in `push-gateway-conventions.md`). This is worth reporting as a genuine absence rather than an oversight in this analysis: unlike several other crates in this repo (per the `buzz-core-debt.md` module analysis, which found real `expect()`/`unreachable!()` usage elsewhere), this crate has no self-flagged shortcuts anywhere in its source.

#### Oversized file / mixed concerns in `http.rs`

`http.rs` is 776 lines and combines seven full request handlers, seven private per-handler transcript structs, several small validation helper functions, `AppState`'s definition, and both router-construction functions in one file with no submodule split (e.g. by "installation lifecycle" vs. "delegation lifecycle" vs. "delivery" vs. "health"). This is within the informal 1000-line ceiling documented elsewhere in AGENTS.md for mobile, but it is the largest non-test-dominated production file in the crate (`postgres.rs` is longer at 952 lines, but over half of that, lines 407-952, is its `#[cfg(test)]` module — see `push-gateway-conventions.md`). Splitting `http.rs` by concern would make the "which checks run before which store call" ordering discussed under "Untested critical paths" easier to audit at a glance per route.

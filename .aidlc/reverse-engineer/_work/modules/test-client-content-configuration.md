#### The `RELAY_URL` default port inconsistency

`e2e_event_reminder.rs`'s default of `ws://localhost:3001` (`:29`) is the only one of the three WebSocket-consuming files in this group that does not default to `:3000`. Its own module doc comment is internally consistent with this (`RELAY_URL=ws://localhost:3001 cargo test ...`, `:16`), so a reader following that file's own instructions will not hit a mismatch. But this diverges from: `TESTING.md`'s entire "Live Local Relay" walkthrough (which stands up a relay on `:3000` and never mentions `:3001`), the crate's own sibling files `e2e_long_form.rs`/`e2e_human_edit_agent_content.rs` (both default `:3000`), and the CI job that actually runs this test (`backend-integration`, `.github/workflows/ci.yml:499` starts the relay on `BUZZ_BIND_ADDR=0.0.0.0:3000` / `RELAY_URL=ws://localhost:3000`, and the "NIP-ER reminder e2e" step explicitly overrides `RELAY_URL: ws://localhost:3000` at `:691-693` — so in CI, the file's own `:3001` default is never actually exercised, it's always overridden). A developer copy-pasting this file's own doc-comment recipe locally would need a relay bound to `:3001`, which nothing else in the documented local-dev flow (`just relay`, `TESTING.md` step 3) produces by default — they would need to either override `BUZZ_BIND_ADDR`/`RELAY_URL` on the relay side (per `TESTING.md`'s port-collision callout) or override `RELAY_URL` to `:3000` on the test-invocation side to match their already-running local relay. This looks like a copy-paste artifact from wherever this file's scaffolding originated rather than an intentional choice — there is no comment anywhere in the file explaining why `:3001` specifically, and no other reminder-specific reason for the relay to be on a different port from every other e2e suite in the crate.

#### Parsed-but-never-read / read-but-undocumented findings

- `BUZZ_E2E_GIT_COMMUNITY_ID` is read only by this test file's own probe helper (`pointer_key`, `:146`) to compute the S3 key it expects the relay to have written to — it does not configure the *relay* at all (the relay's own multi-tenant community resolution comes from the HTTP `Host` header / seeded `communities` table, not this variable). This means the variable only has an effect if a test-runner sets it to match whatever community ID the relay-under-test actually resolved the request to; if it's unset (the common case, including in CI where no `BUZZ_E2E_GIT_COMMUNITY_ID` appears in any workflow env block — confirmed by the same repo-wide grep used elsewhere in this analysis returning no matches outside this test file and the `.aidlc` backup docs) the probe assumes the single-tenant key shape, which is consistent with the CI relay's single seeded `communities` row (`00000000-0000-4000-8000-00000000c0de` for host `localhost:3000`, `.github/workflows/ci.yml:559-563`) — but this consistency is never asserted anywhere; it's an implicit coupling between this test file's key-shape guess and the relay's actual (out-of-scope-to-verify-further-here) S3 key-naming code.
- `GIT_CREDENTIAL_NOSTR_BIN`'s fallback path assumes a specific relative layout (`CARGO_MANIFEST_DIR` two levels up, then `target/release/git-credential-nostr`, `:38-41`) that only works when running from the default (non-`--profile ci`) build location. The CI job that actually runs `e2e_git.rs`-adjacent tests (`relay-e2e`, `.github/workflows/ci.yml:703-741`) always sets `GIT_CREDENTIAL_NOSTR_BIN` explicitly (`:734`) rather than relying on the fallback — but note that CI job runs `e2e_persona`, `e2e_nostr_interop`, and `e2e_relay` tests (`:727-731`), **not `e2e_git`** (confirmed: `e2e_git` does not appear anywhere in that job's test-invocation lines) — so even though CI builds and wires the credential-helper binary and env var, it never actually points them at this file's tests. See Debt.
- No test in this group reads a batch-size, timeout-override, or retry-count env var of its own — timeouts are all hardcoded `Duration` literals in test bodies (e.g. `Duration::from_secs(5)` for most `collect_until_eose` calls, `Duration::from_secs(15)` for the scheduler-delivery test's poll window). This means none of these tests can be tuned for a slower CI environment without editing source.

#### Cross-file inconsistency in HTTP-URL derivation

`e2e_event_reminder.rs` and `e2e_human_edit_agent_content.rs` both derive their HTTP URL from `RELAY_URL` via string replacement (`relay_url().replace("wss://","https://").replace("ws://","http://")`, `e2e_event_reminder.rs:32-38`, `e2e_human_edit_agent_content.rs:29-35` — byte-for-byte identical logic, duplicated). `e2e_git.rs` instead reads a wholly separate env var, `RELAY_HTTP_URL`, with its own independent default — it does not derive from any `RELAY_URL`-equivalent at all. This means a test-runner who sets `RELAY_URL` to point at a non-default relay and expects that to propagate to `e2e_git.rs` as well will be surprised — `e2e_git.rs` needs `RELAY_HTTP_URL` set independently. `e2e_long_form.rs` needs neither `RELAY_HTTP_URL` derivation nor the raw var, since it never makes an HTTP call at all.

## Module: buzz-admin, sprig & countdown-bot (`crates/buzz-admin`, `crates/sprig`, `examples/countdown-bot`)
### Aspect: Debt

#### buzz-admin has zero tests for a 584-line, 8-dependency, destructive-capable CLI

`grep -rn "#\[test\]|#\[cfg(test)\]|#\[tokio::test\]" crates/buzz-admin/` returns no matches — confirmed by two independent search passes plus a direct `list_directory` of `crates/buzz-admin/` showing the crate contains only `Cargo.toml` and `src/main.rs` (no `tests/` directory, no `#[cfg(test)]` block in `main.rs`). This is the single most notable gap in this module group: `main.rs` is 584 lines, declares eight internal crate dependencies (`buzz-db`, `buzz-core`, `buzz-auth`, `buzz-pubsub`, `buzz-search`, `buzz-audit`, `buzz-workflow`, `buzz-media`), and contains at least one genuinely destructive, irreversible-in-effect operation — `remove-member` (which, absent a backup of the roster, permanently removes a membership row and republishes a roster that no longer includes that pubkey) — with **no automated coverage of any kind**: not of argument parsing, not of the `RemoveResult`-to-exit-code mapping, not of `validate_role`/`parse_pubkey_hex`, not of the `reconcile_channels` tag-building logic, not of the same-second bump arithmetic in `publish_membership_list_with_bump`. All of the underlying `buzz-db` functions it calls (`add_relay_member`, `remove_relay_member`, `remove_relay_member_if_role`, etc.) do have unit test coverage at the `buzz-db` level (12 test functions in `crates/buzz-db/src/relay_members.rs`) — but that only proves the DB layer is correct in isolation, not that `buzz-admin`'s CLI-level argument handling, exit-code mapping, or NIP-29 event construction (`reconcile_channels`, which has **no** DB-level equivalent test coverage either, since it's `buzz-admin`-only logic duplicating relay code — see below) are correct. This is worth flagging prominently exactly as the task requested: **a destructive admin subcommand (`remove-member`) has zero test coverage**, and so does every other subcommand in the file.

`sprig` has the same zero-test status (`grep` against `crates/sprig/` returns no matches) for its 53-line dispatch logic — lower stakes given the file's small size and simple logic, but the fail-open fallback behavior described in `ops-misc-security.md` is untested. `countdown-bot` is the only one of the three with any tests (`main.rs:392-436`, three `#[test]` functions covering `command_reply`/`mention_command_reply`), though these cover only the pure reply-string logic, not the WebSocket protocol steps, the `Config::from_env` parsing, or the owner-attestation verification call.

#### buzz-admin duplicates relay logic instead of sharing it — twice

Two separate, non-trivial pieces of `buzz-admin`'s logic are hand-rolled re-implementations of functions that already exist in `buzz-db`/`buzz-relay`, rather than calls to them:

1. **`publish_membership_list_with_bump`** (`main.rs:315-385`, ~70 lines) duplicates `Db::publish_nip43_membership_locked` (`crates/buzz-db/src/lib.rs:3488-3560+`, a `pub async fn` already exported from the exact crate `buzz-admin` depends on). The DB version is strictly better: it wraps the read-build-write cycle in a Postgres advisory-locked transaction (`lib.rs:3498-3510`), which is precisely the mechanism that would close the "same-second domination on concurrent CLI processes" gap that `buzz-admin`'s own module doc comment (`main.rs:14-19`) and `NOSTR.md:311-315` both document as a known, *unfixed* limitation. `buzz-admin` could call `db.publish_nip43_membership_locked(tenant.community(), &relay_keypair)` directly and inherit the lock for free, but instead reimplements the unlocked version. This isn't a hypothetical — the function it should be calling already exists, in the same dependency, doing the same thing, better.
2. **`reconcile_channels`** (`main.rs:461-579`, ~118 lines) duplicates `reconcile_channel_events`/`emit_group_discovery_events` (`crates/buzz-relay/src/handlers/side_effects.rs:2940-2999` and `:954-1050`). Unlike case 1, this duplication is not merely redundant — it is **behaviorally incomplete**: the relay's version additionally emits `topic`, `purpose`, `archived`, `ttl`, `ttl_deadline` tags and DM-participant `p` tags on kind:39000 (`side_effects.rs:996-1023`), none of which `buzz-admin`'s copy produces (`main.rs:504-520`). An operator who reconciles a channel via `buzz-admin` gets a strictly less complete discovery event than the relay would have produced for the same channel. The relay-side function isn't even callable from `buzz-admin` today since it lives in the `buzz-relay` binary crate rather than a shared library — but that's exactly the kind of "extract to `buzz-db` or a shared helper" refactor this duplication argues for. As it stands, any future change to the discovery-event tag set (e.g. adding a new tag) has to be remembered and applied in two places, and history shows that's already failed once (the ttl/topic/purpose/DM-participant tags were added to the relay's version and never backported here — whether by omission or by a scope decision that was never written down anywhere).

Both cases mean `buzz-admin` and the relay can silently drift further apart over time with no test or lint to catch it, since (per the previous finding) there is no test on the `buzz-admin` side to notice a behavioral difference even if one were written for the relay side.

#### Five of eight declared dependencies are dead

`crates/buzz-admin/Cargo.toml:17,19,20,21,22` declare `buzz-auth`, `buzz-search`, `buzz-audit`, `buzz-workflow`, `buzz-media` as dependencies. None of the five is referenced anywhere in `crates/buzz-admin/src/main.rs` — confirmed by grep for each module path individually and in combination, returning zero matches every time, against a file that is the crate's only source file. `sqlx` and `url` (`Cargo.toml:35-36`) are similarly declared-but-unreferenced-by-path (the only appearance of "Url" in the file is inside a comment). This inflates `buzz-admin`'s compile graph and dependency footprint for no functional benefit, and — more importantly for anyone reading the codebase top-down — it actively misleads a reader of `Cargo.toml` into believing `buzz-admin` is integrated with auditing, search, workflows, and media, when it integrates with none of them. This is the same "declared but zero references" pattern already documented elsewhere in this reverse-engineering effort for a different crate (`buzz-auth` declared-but-unused-by `buzz-auth`'s own `tracing` dependency, and `buzz-persona` as a dead dependency of `buzz-acp` per the existing `debt.md`'s DEBT-79) — this module group adds a much larger instance of the same class of debt (five dead deps in one eight-dep manifest, an unusually high dead-to-total ratio).

#### Documentation undercounts buzz-admin's real subcommand surface — in two different documents, two different ways

- **The module inventory** (`.aidlc/reverse-engineer/modules.md`, `buzz-admin` row) describes the subcommand surface as "membership, key-gen, migrate, reconcile" — four categories, and specifically omits any mention of `product-feedback list`, which is a real, fully-implemented seventh subcommand (`main.rs:79-83,101-105,253-258`). "Reconcile" (singular) also undersells that this is one subcommand (`reconcile-channels`) among seven, not a category with siblings.
- **`ARCHITECTURE.md`'s own `buzz-admin` section** lists five subcommands in a table (`add-member`, `remove-member`, `list-members`, `generate-key`, `reconcile-channels`) and omits **both** `migrate` and `product-feedback list` — despite `migrate` being referenced by name elsewhere in the very same document tree (`deploy/compose/README.md`'s "Production notes": "run `buzz-admin migrate` before starting the relay") and in `Justfile:190`. So the CLI's true surface is undercounted by a different subset in each of the two docs that attempt to describe it, and neither undercount matches the other's omissions. Since the task's own briefing hypothesized "membership, key-gen, migrate, reconcile" as the expected surface (attributed to the module inventory) — that hypothesis is **confirmed as an undercount**: the actual surface has seven leaf subcommands, not four, and `product-feedback list` is the one most conspicuously missing from every doc that attempts to enumerate the CLI.

#### Oversized / under-decomposed functions

`reconcile_channels` (`main.rs:461-579`, 118 lines) mixes CLI-level key resolution, a DB query loop, and three separate inline event-construction blocks (39000/39001/39002) in one function with no sub-helpers — each of the three tag-building blocks (`main.rs:504-520`, `:542-555`, `:558-570`) could be its own named function (as the relay's equivalent code does: `emit_addressable_discovery_event` is a shared helper called three times, `side_effects.rs:902-950` called from `:1043-1049,1080-1086,~1120`), which would also make each block independently testable. `publish_membership_list_with_bump` (`main.rs:315-385`, 70 lines) similarly mixes timestamp-bump arithmetic, tag construction, signing, DB write, and Redis publish in one function. Neither is unreasonably long by Rust standards, but both are exactly the kind of "one function doing four things" shape that resists unit testing without extracting the pure pieces (tag-building, bump arithmetic) from the I/O (DB/Redis calls) — which likely also explains why neither has tests today.

#### Stale/misleading precision in comments

`main.rs:445` ("A plain `Url::host_str()` drops the port/brackets") references a hypothetical alternative implementation for explanatory purposes — accurate as written, not stale, but worth noting it could confuse a future reader into thinking `url::Url` is used somewhere in this file when the crate doesn't call it directly at all (it's only invoked indirectly through `buzz_core::tenant::relay_url_authority`). No genuinely stale comments (wrong line numbers, references to removed code, contradicted-by-the-code-below comments) were found in any of the three files during this review — this is a clean mark relative to other debt findings in this codebase (e.g. the existing `debt.md`'s DEBT-81 catalogs a dozen stale comments elsewhere in the agent surface; this module group contributes none to that count).

#### The authorization/audit bypass is undocumented as an intentional trust boundary

Per `ops-misc-security.md`: `buzz-admin` mutates `relay_members` with no per-operator authorization check and with no audit-log entry, bypassing both mechanisms the relay's own WS-based NIP-43 admin-event path enforces. Searching `SECURITY.md`, `NOSTR.md`, `ARCHITECTURE.md`, `CONTRIBUTING.md`, and `docs/admin/README.md` for any statement that this is a deliberate, accepted trust boundary (the way `docs/admin/README.md` explicitly states its own dashboard's trust model: "The human trust boundary remains the private admin ingress ... this endpoint deliberately does not claim to provide it") finds **no equivalent statement anywhere for `buzz-admin`**. The closest the docs come is `NOSTR.md`'s member-management section, which documents *how* to run the commands and their exit codes but never states *who is allowed to* or *that running it bypasses audit* — the security posture has to be reverse-engineered from the code, not read off any doc. This is a real, actionable gap: whether "shell/DB access to the relay host is the security boundary for relay membership" is the *intended* design (plausible — Docker exec access is already a strong trust signal) or an *oversight* (the audit-log crate is declared as a dependency, which could suggest an original intent to wire it up that was never followed through) cannot be determined from the documentation, only guessed at from the unused `buzz-audit` dependency. Recommend either documenting this trust boundary explicitly (mirroring `docs/admin/README.md`'s pattern) or wiring up the audit call that the dependency graph already implies should exist.

The LOC is knowable (437, confirmed by `wc -l`) and non-zero, and the test count is also knowable and non-zero (one `#[cfg(test)] mod tests` block, three `#[test]` fns) — both were entered as blank/dash rather than measured, unlike every other row in the same table. This is a minor, low-impact documentation gap (likely because the inventory's methodology treated `examples/` as out-of-scope for the same measurement pass applied to `crates/`) but it does mean a reader of the inventory table alone would incorrectly conclude `countdown-bot` is untested and dependency-free, when it is neither.

#### Nothing found: no dead code within reachable paths

Beyond the five dead *dependencies* above, no dead functions, unreachable `match` arms, or genuinely unused local variables were found in any of the three `main.rs` files during a full read of each — every function defined in all three files is called from at least one reachable path (`main()`/`run()`/`dispatch()`), and every `match` arm in every enum (`Command`, `ProductFeedbackCommand`, `RemoveResult`, `sprig`'s dispatch `match`) is exhaustively handled with no unreachable branches. This module group's debt is concentrated in *dependencies*, *duplication*, *missing tests*, and *documentation undercounts* — not in dead application code.

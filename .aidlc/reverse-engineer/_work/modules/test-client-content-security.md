## Module: buzz-test-client — content & git E2E (`crates/buzz-test-client/tests`)
### Aspect: Security

#### `e2e_human_edit_agent_content.rs` — the file's entire subject *is* an authorization/provenance boundary

This is the one file in the group where "security" is not a side-concern but the direct subject matter. The mechanism under test has a real attribution angle, but it is narrower than "provenance markers": nothing in the wire format distinguishes an agent-authored kind:9 message from a human-authored one (see Data Model) — attribution/authenticity is derived entirely from *signature identity* plus an out-of-band NIP-OA ownership fact recorded at authentication time (`is_agent_owner`, `crates/buzz-db/src/user.rs:354`). This has a specific, testable security property that the suite proves in both directions:

- **The owner cannot be impersonated.** The NIP-OA `auth` tag is a Schnorr signature over `"nostr:agent-auth:" || agent_pubkey_hex || ":" || conditions` made with the *owner's* private key (`crates/buzz-sdk/src/nip_oa.rs:14-16`, `:113-115`, `:139-160`) — an agent cannot self-assert ownership, and `compute_auth_tag`/`verify_auth_tag` both explicitly reject `owner_pubkey == agent_pubkey` as "self-attestation rejected" (`nip_oa.rs:150-153`, `:222-226`, unit-tested at `nip_oa.rs:328-346`). This file doesn't re-test the signature math (that's `buzz-sdk`'s job, out of scope here), but every one of its owner-path tests depends on that guarantee holding — if self-attestation worked, an agent could grant itself owner-of-itself and the entire "third party cannot" family of tests would need to reconsider what "owner" even means.
- **A human's ability to override an agent's output is a one-way privilege, not mutual.** The tests only prove *owner → agent* authority (edit/delete agent messages, manage agent-owned channels). There is no test in this file (or, per the class list, anywhere flagged in this suite) of the reverse — an agent overriding or silently altering a human's own message under the guise of ownership. The relay-side predicates reviewed (`validate_edit_ownership`, `ingest.rs:797-833`; `validate_standard_deletion_event`, `side_effects.rs:196-233`) are symmetric in code shape (author-or-owner-of-author) but this suite never constructs a scenario where the "author" is a human being overridden by someone claiming ownership of that human — which is structurally impossible under NIP-OA (there is no "owns a human" relationship), so this isn't a gap so much as a non-applicable direction. Worth noting for a reader looking for the boundary: ownership flows one way (human owns agent), and the tests correctly only probe that direction.
- **Revocation is retroactive and closes a specific prior loophole.** The "removed-author" tests (`:826-990`) are the sharpest security-relevant result in this file: they prove that once a human is removed from a private channel, they lose edit/delete rights over their *own* historical messages in that channel, even though `author == actor` for that predicate. The doc comment (`:793-800`) names this as closing a real, previously-exploitable gap ("Option A") where widening the membership-skip list for the owner-bypass **also** widened the self-author fast path, which would have let a removed user keep mutating private-channel history they authored before removal. This is a legitimate access-revocation property: removing someone should retroactively take away their write access to what they left behind, not just block new writes.
- **The owner bypass is scoped precisely, not a blanket "owner can do anything."** Each of the five predicates (40003 edit, kind:5 delete, 9005 delete, 9002 privileged-tag edit, 9008 delete-group) is a *separate* code path with its own owner check — the tests exercise each independently rather than asserting one general "owner_authorized" gate, which matches the relay's actual implementation (five distinct call sites, not one shared function) and correctly avoids conflating them. A gap this analysis cannot confirm or deny from these tests alone: whether the *topic/purpose* branch of kind:9002 (the non-privileged-tag half, `side_effects.rs:526-536`, which only requires plain membership) is also reachable by a non-member owner — no test in this file exercises 9002 with only `topic`/`purpose` tags, only the privileged (`name`/`about`/`archived`/`visibility`/`ttl`) branch is tested (`test_owner_can_edit_agent_channel_metadata` uses `name`, `test_owner_can_archive_agent_channel` uses `archived`). This is a real, unstated coverage gap, not a confirmed bug — the code path exists and is short (a plain membership check), so the risk is low, but it is untested by this file.

No test credentials in this file look like they could be mistaken for real production keys — every identity is `Keys::generate()` (confirmed: `Keys::generate()` appears in fresh, randomly-generated form at every one of the file's key bindings; no hardcoded `nsec`/hex secret key literal anywhere in the file).

#### `e2e_event_reminder.rs` — privacy-by-construction is the security property, not just an access-control check

NIP-ER's own "Security Considerations" section (`docs/nips/NIP-ER.md`, under that heading) states plainly that relays can observe reminder ownership, due times, and lifecycle timing even though content is NIP-44-encrypted, and that a compromised relay or author key defeats the model. This test file does not — and structurally cannot — test the NIP-44 confidentiality guarantee itself, because every reminder body in this file is the literal placeholder string `"nip44-ciphertext-placeholder"` (`:59`, `:81`), never real ciphertext. What it tests instead is the **relay-enforced metadata boundary**: that the relay itself never leaks a reminder's *existence*, *count*, *tags*, or *schedule* to anyone but the authenticated author — which is the one part of the privacy model that is the relay's responsibility rather than the client's encryption. This is exercised unusually thoroughly, across every read surface a client could plausibly use (HTTP query, HTTP count, WS REQ, WS COUNT, mixed-kind filter fan-out omission, live fan-out to an open subscription, and NIP-50 search) — see Business Rules for the per-surface table. The breadth here is a genuine security-testing strength: a metadata leak on any *one* of those seven surfaces would be a real privacy bug (an observer could infer "user X has N reminders due around time Y" without ever decrypting anything), and the suite closes all seven independently rather than testing one and assuming the rest follow the same code path.

One test worth flagging as security-adjacent-but-not-security-critical: `test_reminder_rejected_not_before_above_max_safe_integer` and the horizon-related tests are input-validation hardening (rejecting malformed/out-of-range `not_before`), not confidentiality or authorization tests — they prevent a malformed or hostile client from wedging a degenerate value into storage (e.g. a `not_before` far enough in the future to sit in the scheduler's due-queue indefinitely, or a value that could behave unexpectedly if ever handled with a lossy numeric type downstream), but they are not testing an access-control boundary. No test credentials or hardcoded secrets appear anywhere in this file; every key is `Keys::generate()`.

#### `e2e_git.rs` — git's own trust model is explicitly *not* exercised, and this is a real, named gap

This file does not test anything about git's own cryptographic trust model. Every git invocation in the file explicitly disables commit and tag signing: `-c commit.gpgsign=false -c tag.gpgsign=false` (`:74`, `:76`). Combined with the crate's relationship to `git-sign-nostr` (a sibling crate whose entire purpose is signing git objects with a Nostr key, per the repo-structure section of `AGENTS.md`), this means **there is no end-to-end test anywhere in this workspace that drives a real `git commit`/`git tag` through `git-sign-nostr` as a `gpg.x509.program` and verifies `git log --show-signature` or `git verify-commit` against a live relay** — a gap already identified independently by the prior `git-identity` group's debt analysis (cited verbatim in that group's `git-identity-debt.md:204-210`) and reconfirmed here directly by reading the two `-c ...gpgsign=false` flags myself rather than taking that citation on faith. This test file's authentication story is entirely about *transport* auth (proving the pusher is who they claim to be, via NIP-98/NIP-OA through `git-credential-nostr`) — it says nothing about *content* authenticity (whether a given commit was actually authored/signed by the identity it claims).

What the file *does* test about credential scoping: the credential helper is invoked once per git HTTP request via `credential.helper=<path>` (`:71-73`), and the pushing identity's `nsec` is passed through the `NOSTR_PRIVATE_KEY` environment variable set on the `git` subprocess itself (`:88`), which `git-credential-nostr` reads via `std::env::var("NOSTR_PRIVATE_KEY")` (`crates/git-credential-nostr/src/lib.rs:51-54`). This is a reasonable test-harness pattern (each contender in the concurrent-push test gets its *own* `owner_nsec` clone passed to its own thread, `:395`, `:400`), but it is worth flagging explicitly: the private key transits a **process environment variable**, which on most Unix systems is readable by any process running as the same user via `/proc/<pid>/environ` (Linux) for the lifetime of the subprocess. This is a plausible attack surface in a genuinely multi-tenant or shared-host CI runner, though it is a completely standard pattern for test harnesses and git credential helpers generally (the production `git-credential-nostr` binary supports the identical `NOSTR_PRIVATE_KEY` env var as its primary key-loading path, `git-credential-nostr/src/lib.rs:51-56`, with a keyfile-based fallback that does check file permissions, `check_keyfile_permissions`, `:29-37`) — this is not a test-specific weakness so much as an inherited property of the tool being tested, surfaced here because the test happens to exercise the same code path.

The MinIO/S3 credentials this file falls back to (`buzz_dev` / `buzz_dev_secret`, `:124-127`) are unambiguously dev/test fixtures, not real credentials — they match the values `docker-compose.yml` seeds into the local MinIO container (`MINIO_ROOT_USER=buzz_dev`, `MINIO_ROOT_PASSWORD=buzz_dev_secret`, `docker-compose.yml:108-109`) and are the same well-known dev defaults documented and `sadscan:disable`-annotated elsewhere in the codebase (e.g. `crates/buzz-db/src/lib.rs:249`, `crates/buzz-relay/src/config.rs:411`). They are not annotated with a `sadscan:disable` comment in `e2e_git.rs` itself (`:124-131` has no such annotation) — worth flagging as a minor inconsistency with the rest of the codebase's convention of marking every hardcoded dev-credential literal for the credential scanner, though the actual risk is negligible since these are widely-known, repo-wide dev fixture values, not secrets with any real-world validity.

The concurrent-push test's own owner identity, like every other identity in this group, is `Keys::generate()` (`:338`) — no static test keypair is reused across runs in any of the four files (each `Keys::generate()` call produces a fresh keypair, so there is no risk of a "well-known test key" being mistaken for or reused as a real identity).

#### `e2e_long_form.rs` — no distinct security surface

This file tests content-lifecycle correctness (replacement ordering, deletion routing), not access control — long-form articles (kind:30023) have no author-only or membership restriction in this relay's model (they are global, author-owned, world-readable content, per Data Model), so there is no authorization boundary for this file to test. The one item worth noting under this heading: `test_long_form_malformed_e_plus_a_does_not_delete` is, in effect, an input-sanitization / injection-adjacent test — it proves a specifically malformed tag combination cannot be used to trigger unintended destructive dispatch (silently soft-deleting an addressable coordinate via a code path that was supposed to require a valid `e`-tag decode, not merely an `e`-tag's presence). This is a legitimate defensive-correctness test even though it is not framed as a security test by the file itself.

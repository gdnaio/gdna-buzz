## Module: buzz-admin, sprig & countdown-bot (`crates/buzz-admin`, `crates/sprig`, `examples/countdown-bot`)
### Aspect: Integrations

#### buzz-admin: direct buzz-db calls, bypassing the relay's HTTP/WS pipeline entirely

This is the most architecturally significant fact about this module group. `buzz-admin` links `buzz-db` directly (`crates/buzz-admin/Cargo.toml:15`) and calls its methods in-process — `Db::add_relay_member`, `remove_relay_member`, `remove_relay_member_if_role`, `list_relay_members`, `list_product_feedback`, `migrate`, `get_latest_global_replaceable`, `replace_addressable_event`, `lookup_community_by_host`, `list_channels`, `get_members`, `query_events` (call sites: `main.rs:181,215,217,255,141,338,363,450,483,491,540,557`; definitions in `crates/buzz-db/src/lib.rs:2932,2967,2979,2921,3041,480,1128,3306,656,1598,1571,1095`). There is **no HTTP request, no WebSocket frame, and no relay process involved at all** — `buzz-admin` opens its own Postgres pool (`connect_db`, `main.rs:420-429`, via `Db::new`) and, for member-management commands, its own Redis pool (`connect_member_services`, `main.rs:389-417`, via `deadpool_redis::Config::from_url` + `PubSubManager::new`). The relay does not need to be running for most `buzz-admin` subcommands to work (though `add-member`/`remove-member` publish to Redis, which live relay instances are subscribed to).

This means every one of the relay's per-event pipeline steps that live *outside* `buzz-db` itself is skipped for `buzz-admin`-originated writes:

| Pipeline step (relay's normal path) | Where it lives | Does `buzz-admin` trigger it? |
|---|---|---|
| NIP-42/NIP-98 authentication | `buzz-auth`, invoked by `buzz-relay`'s connection/request handlers | **No** — `buzz-admin` never calls any `buzz_auth` item (confirmed: `grep -rn "buzz_auth" crates/buzz-admin/src/main.rs` returns zero matches) despite declaring `buzz-auth` as a dependency (`Cargo.toml:17`) |
| Audit log entry (`AuditAction::MemberAdded`/`MemberRemoved`) | `buzz-audit`, invoked from `dispatch_persistent_event`/relay handlers | **No** — `grep -rn "buzz_audit" crates/buzz-admin/src/main.rs` returns zero matches, despite `Cargo.toml:20` declaring `buzz-audit`. Confirmed further: no call site anywhere in the repo invokes `AuditAction::MemberAdded` or `MemberRemoved` outside `buzz-audit`'s own unit test (`crates/buzz-audit/src/service.rs:357`) — i.e. **nothing in the codebase**, including the relay's own WS-based NIP-43 admin-event handler (`crates/buzz-relay/src/handlers/relay_admin.rs`, confirmed no `audit` references in that file), currently audits relay-membership changes at all. This is a pre-existing gap in the relay itself, not something `buzz-admin` uniquely introduces — but `buzz-admin` does nothing to close it either. |
| Workflow trigger evaluation (`WorkflowEngine::on_event`) | `buzz-workflow`, invoked only from `crates/buzz-relay/src/handlers/event.rs:545` | **No** — that call site is reachable only through the relay's own EVENT-ingest handler; `buzz-admin` never constructs a `WorkflowEngine` or calls `on_event`. `grep -rn "buzz_workflow" crates/buzz-admin/src/main.rs` returns zero matches, despite `Cargo.toml:21` declaring `buzz-workflow` |
| Search indexing | Postgres **generated column** `search_tsv` (`GENERATED ALWAYS ...`, per `crates/buzz-db/src/migration.rs:586`) | **Yes, incidentally** — because indexing is a DB-level generated column rather than an application-level step, any row `buzz-admin` inserts through `buzz-db` (e.g. the 39000/39001/39002 events in `reconcile-channels`) gets indexed automatically. `buzz-search` itself is never called by `buzz-admin` (`grep -rn "buzz_search" crates/buzz-admin/src/main.rs` returns zero matches, despite `Cargo.toml:19` declaring it) — the crate dependency is simply unused |
| Media handling | `buzz-media` | **No** — `buzz-admin` performs no media operations; `grep -rn "buzz_media" crates/buzz-admin/src/main.rs` returns zero matches despite `Cargo.toml:22` declaring `buzz-media` |
| Redis fan-out to live WS subscribers | `buzz-pubsub`, called from the relay's `dispatch_persistent_event` | **Partially** — only `add-member`/`remove-member`/`reconcile-channels`'s bump-and-republish path calls `pubsub.publish_event` directly (`main.rs:369-375`); this is the **one** integration point where `buzz-admin` does replicate a piece of the relay's normal side-effect chain, using its own `PubSubManager` instance rather than the relay's |

Net result: **five of the eight declared crate dependencies in `crates/buzz-admin/Cargo.toml` — `buzz-auth`, `buzz-search`, `buzz-audit`, `buzz-workflow`, `buzz-media` — have zero references anywhere in `crates/buzz-admin/src/main.rs`.** Verified individually by grep for each module path (`buzz_auth`, `buzz_search`, `buzz_audit`, `buzz_workflow`, `buzz_media`) and by a combined grep, both returning no matches; `main.rs` is the crate's only source file (`crates/buzz-admin/src/`'s only child besides `Cargo.toml` is `src/`, which contains only `main.rs`). Only `buzz-db`, `buzz-core`, and `buzz-pubsub` are actually used. See `ops-misc-debt.md` for the dead-dependency finding and `ops-misc-security.md` for why the missing `buzz-auth`/`buzz-audit` integration matters.

Additionally, `sqlx` and `url` are declared directly in `buzz-admin`'s own `Cargo.toml` (`:35-36`) but never referenced by path (`sqlx::`, `url::`) anywhere in `main.rs` — the file uses `buzz_db`'s and `buzz_core`'s re-exported functionality instead (e.g. `relay_url_authority` is imported from `buzz_core::tenant`, not called via a local `url::Url` parse — the only textual match for "Url" in the file is inside a comment, `main.rs:445`, referencing `Url::host_str()` as something the *helper function* avoids, not something `buzz-admin` calls itself).

#### sprig: integrates by calling into three sibling crates' `run()` — nothing else

`sprig` has exactly three internal-crate integrations, all `path` dependencies (`crates/sprig/Cargo.toml:17-19`): `buzz-acp::run()`, `buzz-agent::run()`, `buzz-dev-mcp::run()` (call sites `crates/sprig/src/main.rs:17,18,41`). It has **zero** external dependencies beyond those three and the Rust standard library — no `tokio`, no `nostr`, no `clap`, nothing (`crates/sprig/Cargo.toml:16-19` lists only the three path deps; confirmed no `[dependencies]` entries beyond them). All actual integration work (relay WebSocket connections, LLM API calls, MCP stdio, git credential/signing helpers) happens inside whichever of the three downstream crates gets dispatched to — `sprig` itself integrates with nothing beyond argv/env inspection and process exit codes.

#### countdown-bot: relay integration via raw WebSocket + buzz-sdk builders, not buzz-cli or buzz-ws-client

`countdown-bot` deliberately does **not** use `buzz-ws-client` (the repo's shared NIP-42 WebSocket client) or `buzz-cli` — its `Cargo.toml` depends only on `buzz-sdk` internally (`examples/countdown-bot/Cargo.toml:12`), plus `nostr`, `tokio-tungstenite`, `futures-util`, `serde_json`, `url`, `anyhow` (`:8-15`). It hand-rolls its own WebSocket connect/AUTH/OK-wait loop (`connect_and_authenticate`, `wait_for_ok`, `wait_for_auth_challenge`, `next_text`, `main.rs:126-136,333-381`) rather than reusing `buzz-ws-client`'s connect/auth/publish helpers — the README states this is intentional, "so the protocol path is easy to inspect in one small file" (README, Notes). This is a deliberate pedagogical choice, not an oversight, but it does mean the example does not exercise (and cannot catch regressions in) `buzz-ws-client`.

It does use `buzz-sdk` for two things: `buzz_sdk::builders::build_profile` (kind:0) and `build_message` (kind:9) (`main.rs:157-162,230-238`; builder signatures `crates/buzz-sdk/src/builders.rs:219-224,537-540`), and `buzz_sdk::nip_oa::{compute_auth_tag, verify_auth_tag, parse_auth_tag}` for the owner-attestation path (`main.rs:98,104,107`; signatures `crates/buzz-sdk/src/nip_oa.rs:146,179,252`). All other events (the `["AUTH", ...]` challenge-response and the kind:9000 self-add) are built with a raw `nostr::EventBuilder` inline rather than through `buzz-sdk` (`main.rs:139-153,174-179`) — an inconsistency in which events go through the SDK and which don't, though a minor one for a one-file example.

No integration with `buzz-workflow`, `buzz-db`, or any HTTP REST endpoint — the bot speaks only the WebSocket NIP-01 protocol (`EVENT`/`REQ`/`AUTH`/`EOSE`/`NOTICE`/`CLOSED` messages), confirmed by the exhaustive match in `handle_relay_text` (`main.rs:199-217`) covering only those five message types.

#### Cross-group note: buzz-admin and countdown-bot never interact

There is no code path connecting `buzz-admin` and `countdown-bot` — they are independent programs in this analysis group only because they happen to share the "ops/misc" bucket in the module inventory, along with `sprig`. No shared state, no shared code beyond both ultimately depending on `buzz-core`/`nostr` (`buzz-admin` via `buzz-core` directly; `countdown-bot` does not depend on `buzz-core` at all — confirmed absent from `examples/countdown-bot/Cargo.toml:7-15` — it gets kind constants implicitly through the `nostr`/`buzz-sdk` crates instead, e.g. hardcoding `Kind::Custom(9)` rather than importing `buzz_core::kind::KIND_STREAM_MESSAGE` (`crates/buzz-core/src/kind.rs:419`), which `countdown-bot` cannot reference since it has no dependency on `buzz-core`).

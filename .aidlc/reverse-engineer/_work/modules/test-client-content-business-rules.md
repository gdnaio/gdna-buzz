| `test_long_form_a_tag_deletion` (`:319-396`) | NIP-09 addressable (`a`-tag) deletion targeting `30023:<pubkey>:<d>` soft-deletes the live row for that coordinate, so a subsequent `REQ` on the same filter returns zero events (`:388-395`). The doc comment (`:301-308`) frames this as a **regression test for issue #714**, where `handle_a_tag_deletion` previously only handled the workflow kind and silently no-op'd for kind:30023 — i.e. this test's entire reason to exist is pinning that one kind's deletion path, not deletion in general. |
| `test_long_form_malformed_e_plus_a_does_not_delete` (`:398-457`) | A kind:5 event carrying **both** a syntactically invalid `e` tag (not 64 hex chars) and a valid `a` coordinate must **not** be routed as an addressable-only deletion — the presence of *any* `e` tag (even a malformed one) makes the deletion ambiguous rather than addressable-only, and the target note must survive. | `test_long_form_set_twice_preserves_published_at` (`:459-537`) | Re-publishing the same `(pubkey, kind, d)` coordinate with an unchanged `published_at` tag but an advanced `created_at` must leave the live row's `published_at` value untouched while `created_at` moves forward — i.e. the relay treats `published_at` as ordinary tag data it stores and returns verbatim, and it is the *client's* responsibility (here, `buzz-cli`'s `build_set_event`) to carry the value forward on update. The test's own comment (`:459-465`) is explicit that this carry rule is "duplicated inline here ... rather than reaching into `buzz-cli`" specifically so the e2e crate stays free of a CLI dependency, and that the rule's correctness is separately unit-tested in `commands::notes::tests`. This is therefore a test of the **relay's tag round-trip fidelity**, not of `buzz-cli`'s carry-forward logic itself. |

#### `e2e_human_edit_agent_content.rs` — exactly what changes when a human edits/deletes agent-authored content

The core invariant under test across all nineteen tests: **ownership, not membership, is the authorization key** for five specific admin operations, and this key is established out-of-band via NIP-OA (`is_agent_owner`), not by anything on the message/channel event itself. Nothing about the *content* changes when a human edits it — there is no "provenance marker" or "attribution tag" added or removed by these operations. What is tested is purely **who is allowed to act**, via five separate per-kind authorization predicates in the relay:

| Predicate (relay source) | Kind | What it allows |
|---|---|---|
| `validate_edit_ownership` (`ingest.rs:763-842`) | 40003 | `event.pubkey` == target's effective author, **or** actor is the NIP-OA owner of that author (`ingest.rs:823-833`, calling `state.db.is_agent_owner`) |
| `validate_standard_deletion_event` (`side_effects.rs:179-238`) | 5 | same author-or-owner rule, for both `e`-tag and `a`-tag deletion targets (`side_effects.rs:196-210` for `a`-tag path, `:221-233` for `e`-tag path) |
| `validate_admin_event` 9005 branch (`side_effects.rs:552-630`) | 9005 (DELETE_EVENT) | event author, channel owner/admin, **or** the owning human of the target message's agent-author (`side_effects.rs:614-628`, `is_agent_owner`) |
| `validate_admin_event` 9002 privileged-tag branch (`side_effects.rs:504-524`) | 9002 (EDIT_METADATA), only for `name`/`about`/`archived`/`visibility`/`ttl` | channel owner/admin, **or** the owning human of *any active owner-role agent in the channel* (`actor_owns_any_owner_agent`, `side_effects.rs:246-264`, called `:513-521`) |
| `validate_admin_event` 9008 branch (`side_effects.rs:631-647`) | 9008 (DELETE_GROUP) | channel owner, **or** the owning human of any active owner-role agent (same `actor_owns_any_owner_agent` helper, `:638-645`) |

Test-by-test mapping to these predicates:

|---|---|---|
| `test_owner_can_edit_agent_message` (`:98-144`) | `validate_edit_ownership`, owner branch | accepted |
| `test_third_party_cannot_edit_agent_message` (`:145-188`) | `validate_edit_ownership`, neither-author-nor-owner | rejected |
| `test_agent_can_self_edit_message` (`:189-225`) | `validate_edit_ownership`, self-author branch | accepted — proves the owner path is additive, not a replacement for self-edit |
| `test_owner_can_delete_agent_message` (`:226-269`) | `validate_admin_event` 9005, owner-of-agent branch | accepted |
| `test_third_party_cannot_delete_agent_message` (`:270-316`) | same, neither branch | rejected |
| `test_owner_can_delete_agent_message_kind5` (`:317-360`) / `test_third_party_cannot_delete_agent_message_kind5` (`:361-407`) | `validate_standard_deletion_event` | accepted / rejected — proves the **same** ownership rule holds for the standard NIP-09 kind (the comment at `:315-316` notes kind:5 is "the deletion kind the desktop app sends", distinct from the NIP-29 admin kind:9005 |
| `test_owner_can_edit_agent_channel_metadata` (`:408-447`) / `test_owner_can_archive_agent_channel` (`:448-483`) | `validate_admin_event` 9002 privileged branch, and specifically **while the owner is not a channel member** (`:415-417` comment) | accepted |

| `test_owner_can_delete_agent_channel` (`:523-557`) / `test_third_party_cannot_delete_agent_channel` (`:558-590`) | `validate_admin_event` 9008 branch, owner not a member | accepted / rejected |
| `test_owner_can_edit_agent_message_in_private_channel` / `..._delete_..._in_private_channel` / `..._edit_metadata_of_private_..._` / `..._delete_private_agent_channel` (`:638-790`) | same four predicates, but on a **private** channel | accepted — see below |
| `test_agent_can_self_delete_channel` (`:791-825`) | 9008, self-owner branch (agent is itself the channel owner) | accepted |
| `test_removed_author_cannot_edit_own_message_in_private_channel` (`:826-909`) / `..._delete_..._` (`:910-990`) | `validate_edit_ownership` / `validate_standard_deletion_event`, self-author branch, re-gated on current membership | rejected after removal |

**The private-channel block is a named regression guard ("Fix 1 regression guard", comment block `:610-616`)** for a specific prior bug: the relay's generic per-event dispatch skips the blanket membership/open-channel gate for kinds `9021, 9007, 40003, 9002, 9005, 9008` (`skip_membership` in `ingest.rs:1796-1801`, comment there: "per-kind validators are the authority ... Bypassing the generic member/open gate here lets the owning human act on private agent channels without being a member"). Before that bypass existed, all four owner-predicates were **unreachable on private channels** because the generic membership check (`check_channel_membership`, `ingest.rs:493-523`) rejected the non-member owner *before* any per-kind validator ran. The four "private-channel coverage" tests (`:638-790`) exist specifically to prove the owner path is reachable even when the owner is not a member of a *private* channel — the comment (`:610-616`) states this explicitly: "Previously all four predicates were unreachable for private channels because `check_channel_membership` rejected non-members before the per-kind validators ran."

**The "removed-author" block is a second, opposite-direction regression guard ("Option A regression guard", comment `:793-800`)**, protecting against an over-widening of the *same-author* fast path. The comment states: "Before Option A, adding 40003/9005 to `skip_membership` also widened the self-author fast-path, allowing removed users to mutate private-channel history." Concretely: `validate_edit_ownership`'s self-author branch (`ingest.rs:797-812`) and `validate_standard_deletion_event`'s self-author branch each **re-check current membership** (`is_member_cached`) even when `author == actor`, and fail with `"restricted: not a channel member"` if the actor was removed and the channel is not `open` (`ingest.rs:805-811`; mirrored in `side_effects.rs:590-611` via `author_delete_can_use_self_delete_path`, which additionally excludes moderation-flagged deletions, `side_effects.rs:2353-2355`). The two tests (`:826-990`) simulate exactly this: agent adds a victim via kind:9000 while the victim is still a member, victim posts a message, agent removes the victim via kind:9001, and the victim's own subsequent edit/delete of their *own* historical message must now be rejected. This proves membership revocation retroactively locks out self-editing of one's own private-channel history — the NIP-OA owner bypass does not create a loophole for a merely-former member to keep editing their own old posts.

No test in this file asserts anything about "attribution tags" being added, removed, or checked on the edited/deleted content itself — the file's name ("human edit of agent content") describes the *scenario*, but the mechanism under test is purely an authorization predicate keyed on the NIP-OA ownership relationship, not a content-provenance marker.

**Scheduler delivery** — `test_scheduler_delivers_due_reminder_to_author_subscription` (`:1141-1177`) proves the relay's background poller (`main.rs:701-...`, `query_due_reminders`) is the delivery path for a reminder that becomes due *after* the author has already drained the historical EOSE — the reminder is submitted with `not_before` a few seconds in the future, before any WebSocket is open (so ingest-time fan-out has zero live recipients and cannot be the delivery mechanism), then the author subscribes and drains EOSE while it is still not due, so it cannot appear as history either. The only remaining path that can deliver it live is the scheduler tick. The test requires `SPROUT_REMINDER_SCHEDULER_INTERVAL_SECS=1` to be set on the relay (stated in the doc comment `:1132-1133`) — without a fast interval the default 10-second tick (`main.rs:701-704`) could still pass but slower, up to the test's 15-second timeout (`:1173`).

Replacement semantics (`test_reminder_replacement_semantics`, `:808-879`) confirm standard NIP-33 `(pubkey, kind, d)` replacement applies to reminders exactly as to any other parameterized-replaceable kind — snoozing (replacing with a later `not_before`) leaves exactly one live version.

#### `e2e_git.rs` — exact operation sequence and what each assertion confirms

`git_clone_push_fetch_force_roundtrip` (`:195-330`) drives a strict sequence, each step gated on the previous succeeding (via the `git()` helper's internal `assert!(out.status.success())`, `:97-104`):

1. **Announce** (kind:30617 HTTP POST) → sleep 2s (`:216-224`) — establishes the repo before any git operation.
2. **Clone** an empty repo (`:227-231`) → assert the local directory exists (`:232`) and the S3 pointer for `(owner, repo)` exists and is captured as `empty_pointer` (`:233`).
3. **Push** an initial commit (`:236-245`) → assert the pointer **advanced** (`assert_ne!(p1, empty_pointer)`, `:246-249`) — this is the test's proxy for Theorem-1-style durability-ordering: a successful push must be observable as a pointer change.
4. **Fresh clone** (`clone2`) observes the exact pushed content and exact SHA (`:255-269`) — this is the test's proxy for Theorem 2 (manifest reconstruction): a reader resolving the new pointer gets everything reachable from it.
5. **Second commit + push + pull** into the *other* existing clone (`:272-288`) → pointer again advances (`assert_ne!(p2, p1)`) and the second clone's `pull` picks up the new SHA — proves incremental (non-fresh-clone) fetch also observes the new state.
6. **Force-push** a rewritten history from a reset point (`:291-309`) → pointer advances again (`assert_ne!(p3, p2)`) and the new SHA differs from the pre-force SHA (`assert_ne!(sha_f, sha2)`).
7. **Clone after force-push** (`clone3`) sees the rewritten content (`:312-320`) — proves force-push is not just accepted but the *served* state is the rewritten one, not a stale cached tree.
8. **Tag push** (`v1.0`) → pointer advances again (`:323-327`) and a subsequent clone (`clone4`) sees the tag (`:328-330`) — proves tags participate in the same manifest-pointer advancement as branch refs.

Every pointer-advancement assertion (`assert_ne!` against the previous `PointerSnapshot`) is a black-box proxy for the object-storage CAS protocol in `docs/git-on-object-storage.md` — the test never inspects the CAS mechanism directly (no assertion on ETags matching a specific value, no assertion of a 412 anywhere in this first test); it only proves *externally observable* effects: git plumbing sees the right content, and the S3 pointer object changes each time a ref-changing push should have happened.

`git_concurrent_push_one_wins_and_repo_recovers` (`:333-453`) is explicitly the regression fence named in `docs/git-on-object-storage.md`'s Scope section ("The checked-in regression fence is the 8-way live CAS race (`e2e_git::git_concurrent_push_one_wins_and_repo_recovers`), which passes against MinIO with no retry layer"). The sequence:

1. Seed a base commit and push it (`:349-361`) — pointer captured as `base_pointer`, SHA as `base_sha`.
2. Clone **8 separate working trees** (`contenders = 8usize`, `:369`), each committing a distinct file (`file-{i}.txt`, `:376-381`) on top of the same base — so all 8 have a common ancestor and would fast-forward if pushed serially, but each proposes a genuinely different tip SHA (`contenders_info`, `:389`).
3. Spawn 8 OS threads (`std::thread::spawn`, `:394-403`), each running `git push` concurrently — "concurrent" here means real OS-thread parallelism issuing `git push` subprocess calls at (approximately) the same wall-clock time against the same relay/repo, not simulated or sequenced concurrency.
4. Collect results: assert **exactly one** thread's push succeeded and the other 7 failed cleanly (`assert_eq!(successes.len(), 1)`, `:415`; `assert_eq!(failures, contenders - 1)`, `:416`) — this is the black-box proof of the "exactly one CAS wins" property (Theorem 3 / `Inv_NoFork` in the spec).
5. The pointer advanced exactly once from `base_pointer` (`:428-431`).
6. A **fresh clone after the race** (`:435-439`) sees a `main` whose SHA equals the *specific* contender that reported success (`assert_eq!(after_sha, winner_sha)`, `:445-447`) and whose log message contains `"contender"` (`:448-452`) — this closes the loop from "one push won" to "the *correct* one's content is what's actually served," which is the linearizability property, not just mutual exclusion.

The race that is being checked for is specifically a **lost update**: the concern is not merely "does the relay crash under concurrent pushes" but "can two pushers both believe they won, or can the wrong one's content end up published, or can the repo end up in a state that matches neither contender." The assertions (`successes.len() == 1`, `after_sha == winner_sha`) directly rule out a torn/forked write. The width of 8 is not arbitrary — `docs/git-on-object-storage.md` states the CI relay is started with `BUZZ_GIT_PROBE_WRITERS=8` (confirmed independently at `.github/workflows/ci.yml:500`, `:657` and `scripts/start-relay-for-tests.sh:161`, and in relay source at `crates/buzz-relay/src/main.rs:473`), i.e. the test's contender count matches the conformance-probe race width the relay validates its S3 backend against at startup.

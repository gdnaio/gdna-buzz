## Module: buzz-test-client — media, managed-agent, mesh-LLM & persona E2E (`crates/buzz-test-client/tests`)
### Aspect: Security

#### Media upload: what is and isn't verified

`e2e_media_extended.rs` verifies a real content-sniffing security property: uploads are classified by **magic-byte detection** (the `infer` crate, per the file's own comments at `:383,404`), not by the client-supplied `Content-Type` header — proven directly by `e2e_media_video.rs:280-321`, where an MP4 body sent with a spoofed `Content-Type: image/jpeg` header is still correctly typed as `video/mp4`. This is the specific security property that prevents a client from disguising a file's real type to bypass a content-type-based filter — and the test proves the *opposite* attack surface exists in a controlled way: **magic bytes win**, so mislabeling cannot cause misclassification, but it also means an "attachment" (PDF, generic binary) upload succeeds on the canonical `/upload` route by design, not by omission (`e2e_media_extended.rs:401-418`).

**MIME-mismatch rejection is not tested.** There is no test in this group that uploads a file whose magic bytes indicate a *dangerous* or *actively blocked* type (e.g. an HTML file, a script, an executable) and asserts rejection — the only two rejection cases in the content-policy matrix are "recognized audio via the standard route" (`:443-455`) and "non-canonical-media via the legacy route" (`:420-433`), neither of which is a MIME-mismatch-with-extension scenario. `grep -n 'text/html\|application/x-|executable\|script' crates/buzz-test-client/tests/e2e_media_extended.rs crates/buzz-test-client/tests/e2e_media.rs crates/buzz-test-client/tests/e2e_media_video.rs` returns zero matches — this group does not test whether the relay would accept an HTML or script payload disguised as media.

**No size-limit rejection is tested anywhere in this group.** `grep -rn 'too large\|MAX_.*BYTES\|max.*size\|payload too large\|413' crates/buzz-test-client/tests/e2e_media.rs crates/buzz-test-client/tests/e2e_media_extended.rs crates/buzz-test-client/tests/e2e_media_video.rs` returns zero matches. The `.env.example` documents relay-side upload admission controls (`BUZZ_MEDIA_MAX_CONCURRENT_UPLOADS`, `BUZZ_MEDIA_MAX_CONCURRENT_UPLOADS_PER_PUBKEY`, `BUZZ_MEDIA_UPLOADS_PER_MINUTE` — `.env.example` under "Media Upload Admission") but none of those controls, nor any file-size cap, is exercised by any test in `e2e_media.rs`, `e2e_media_extended.rs`, or `e2e_media_video.rs`. The zero-byte and 1000-byte "random bytes" fixtures (`e2e_media_extended.rs:457-494`) test the *lower* bound of acceptance, not an upper one. This is a genuine coverage gap for a security-relevant property (unbounded upload size / rate) that this crate's own `.env.example` documents as configurable.

**Blossom auth grammar is thoroughly tested as an authorization boundary**, which is itself a security property: wrong event kind, missing `t`/`expiration` tags, expired `expiration`, empty content, and a `server`-tag mismatch are all proven to be rejected with 401 (`e2e_media_extended.rs:220-380`), and a hash mismatch between the signed `x`-tag and the actual uploaded body is rejected (`e2e_media.rs:273-295` — note the function is misnamed `test_upload_hash_mismatch_returns_400` but both its doc comment and its `assert_eq!` check 401, not 400; see Debt).

**Same-origin enforcement for `imeta` is a tested security property.** `test_ws_invalid_imeta_external_url` (`e2e_media_extended.rs:593-658`) proves the relay rejects a message whose `imeta` `url` field points at an attacker-controlled external host (`https://evil.com/...`) rather than the relay's own `/media/` path — this is the control that prevents a chat message from presenting arbitrary third-party content as if it were relay-hosted, verified-media. `e2e_media_video.rs:567-645` extends the same idea to the poster/thumbnail field specifically (a video's own URL cannot be reused as its own poster), which is a data-integrity check adjacent to, but distinct from, the same-origin check.

#### Managed-agent: secret-leakage checks, and their explicit scope limit

`test_managed_agent_round_trips_only_projected_fields` (`e2e_managed_agent.rs:186-263`) is this group's most explicit security-shaped test: it asserts that published managed-agent content never contains any of 8 secret-shaped substrings (`private_key_nsec`, `private_key`, `nsec1`, `auth_tag`, `env_vars`, `backend`, `backend_agent_id`, `provider_binary_path`, `:236-246`) or 6 runtime-shaped substrings (`runtime_pid`, `last_started_at`, `last_stopped_at`, `last_exit_code`, `last_error`, `relay_url`, `:249-262`). This is a **relay round-trip fidelity check**, not the secret-exclusion guard itself — the test's own doc comment says so explicitly (`:186-193`): the input content is a hand-built, already-secret-free literal, so the test can only prove "the relay does not inject secrets it wasn't given," not "the projection function correctly strips secrets from a real record." That second, stronger property is verified by a desktop-side unit test, confirmed present at `desktop/src-tauri/src/managed_agents/agent_events.rs:249` (`content_excludes_secrets_and_runtime_fields`) and `:390` (`from_event_drops_injected_secret_and_harness_keys`) — outside this crate and outside this analysis group's scope, but real and locatable.

No test in `e2e_managed_agent.rs` touches the trust/permission boundary of a spawned agent **subprocess** — there is no subprocess in this file at all (see Integrations). The file's "managed-agent" security surface is entirely about *what the relay stores and returns*, not about process isolation, environment-variable scoping, or credential handling at spawn time.

#### Mesh: membership gate and no-secrets-in-discovery-note checks

`e2e_mesh_llm.rs` verifies exactly two mesh-adjacent security properties, both about the kind:30003 discovery note, and both conditional on live infrastructure being present:

1. **No secrets in the published discovery note.** `trust_member_reads_mesh_status` lowercases the entire content and asserts it does not contain `nsec`, `secret`, `/users/`, `/home/`, `runtime_dir`, or `local_path` (`e2e_mesh_llm.rs:154-163`) — this is a genuine check that a status broadcast meant for peer discovery doesn't leak the publishing machine's private key or local filesystem layout.
2. **Membership gates visibility.** `trust_nonmember_read_denied` asserts a non-member identity receives zero kind:30003 events for a REQ that a member would see (`:174-217`), and treats an outright connection refusal as an equally valid "denied" outcome (`:185-189`).

Both tests **skip silently** (return without any assertion) if `MEMBER_NSEC`/`STRANGER_NSEC` are unset (`:95-97`, `:182-184`) — so in an environment without those two env vars configured, this file provides **zero** security assertions on any run, `#[ignore]`d or not. There is no CI job that sets these variables (see Configuration/Debt), so in practice this file's security coverage has never executed in CI.

The deeper mesh-routing security question raised by the task framing — whether `buzz-agent`'s "Auto" collective-routing state machine (`resolve_openai_model`/`observe_mesh_virtual_model`) could be tricked into leaking a request to an untrusted collective, or whether the model-substitution is itself an information-disclosure risk (a caller asking for `auto` gets silently rerouted to `mesh` with no visible record per the prior `agent-llm-debt.md:` finding #12) — is **not addressed by this file at all**. `e2e_mesh_llm.rs` never imports or references `buzz-agent`, never constructs a request containing the literal model string `auto`, and never asserts anything about which model actually served a completion. Its `live_agent_completes_chat_over_mesh` test only checks that *some* non-empty response comes back from a mesh-client's local OpenAI-compatible port — it does not distinguish "served locally" from "served by a remote mesh peer" in the response itself, so even when this test runs with real infrastructure, it cannot detect a mesh-routing regression that silently serves from the wrong place.

Assertion #3 from the file's own acceptance matrix ("untrusted Mesh owner cannot infer with a leaked join token") is explicitly **not implemented in this file** — the matrix table states it is covered by a separate hardware harness / `mesh_admission_smoke` example (`e2e_mesh_llm.rs:33`), confirmed to be a distinct binary (`crates/buzz-relay/examples/`, invoked by `Justfile`'s `mesh-e2e-admission` recipe) rather than anything in this crate.

#### Persona: authorization-boundary coverage is this file's core subject

Unlike the other five files, `e2e_persona.rs`'s dominant theme (see Business Rules) **is** a security/authorization property: the author-only-unless-shared read gate. This is tested exhaustively across every read surface (WS REQ, WS COUNT, WS live fan-out, HTTP `/query`, HTTP `/count`) and in both directions (a foreign reader is denied; the author is never denied their own data) — this is one of the most thorough authorization-boundary test suites in this analysis group.

One gap: the persona `content` field itself is never treated as sensitive by any test — no test asserts that a persona's `system_prompt` or other content fields are hidden from a foreign reader when unshared. The *entire event* (including content) is gated as a unit; there's no finer-grained "metadata visible, content hidden" property tested or apparently intended, consistent with the NIP-AP model where a persona is either visible (all fields) or not (per `docs/nips/NIP-AP.md`).

#### Test credentials

No file in this group hardcodes a real-looking private key, nsec, or token. Every identity is either `Keys::generate()` (ephemeral, per-test) or read from an env var whose value is never itself embedded in the file (`RELAY_URL`, `RELAY_HTTP_URL`, `TEST_IMAGE_PATH`, `MEMBER_NSEC`, `STRANGER_NSEC`, `MESH_OPENAI_BASE` — see Configuration). Placeholder hash-like strings are obviously synthetic repeated-character literals, not real digests or keys: `"f".repeat(64)` (`e2e_media.rs:279`), `"0".repeat(64)` (`e2e_media.rs:301`), `"a".repeat(64)`/`"b".repeat(64)` (`e2e_media_extended.rs:624`, `:690`). The module doc-comment examples that show `MEMBER_NSEC=nsec1... STRANGER_NSEC=nsec1...` (`e2e_mesh_llm.rs:24`) are truncated placeholders, not usable keys. `X-Pubkey` headers sent by `e2e_persona.rs`'s HTTP-bridge helpers (`:49`, `:71`, `:95`, `:1524`) rely on the relay's documented dev-mode auth fallback (`TESTING.md`'s configuration table: "`BUZZ_REQUIRE_AUTH_TOKEN` — When true, REST requires NIP-98 (no `X-Pubkey` fallback)") rather than a real NIP-98 signature — meaning these HTTP-bridge tests only prove the persona-gate behavior under the relay's dev-mode auth posture, not under a production-hardened (`BUZZ_REQUIRE_AUTH_TOKEN=true`) configuration. No test in this file sets that variable or exercises the NIP-98-required path.

## Module: buzz-test-client — content & git E2E (`crates/buzz-test-client/tests`)
### Aspect: Features

From an external reader's perspective — someone who has never seen the relay's internals but wants to know "what can I rely on as a Buzz user/agent/integrator" — each file proves out a distinct user-facing capability.

#### Publishing and maintaining long-form articles (`e2e_long_form.rs`)

A user (or agent) can write a Medium/Substack-style long-form article — title plus Markdown body — publish it once, and then keep editing it in place under a stable identifier (the `d` tag / slug) without accumulating duplicate copies: republishing under the same slug replaces the old version everywhere clients query it (`test_long_form_nip33_replacement`), and the system is safe against out-of-order network delivery of an edit (`test_long_form_stale_write_rejected`) — an article can't be accidentally reverted by a delayed older copy arriving late. Articles are personal/global content, not tied to any one channel or workspace room, even if a client mistakenly tags one with a channel reference (`test_long_form_stray_h_tag_ignored`). An author can retract an article entirely via standard deletion and have it disappear from every subsequent read (`test_long_form_a_tag_deletion`) — and this deletion is specifically robust against a particular malformed-input edge case that could otherwise let an attacker-crafted deletion event slip through unintended dispatch logic (`test_long_form_malformed_e_plus_a_does_not_delete`). Finally, the system preserves the true "originally published" timestamp across edits (`test_long_form_set_twice_preserves_published_at`), so readers and feeds can distinguish "written on" from "last touched on" — the kind of distinction a blog or RSS reader needs to sort and display correctly.

#### Humans staying in control of their AI agents' channel activity (`e2e_human_edit_agent_content.rs`)

A human who owns an AI agent operating inside Buzz can correct, delete, or manage that agent's output and the channels it created — even from outside the channel entirely, and even if the channel is private — without needing to be added as a member first. Concretely: fix a typo or bad output in something the agent said (edit), remove an agent message that shouldn't have been sent (delete, via either the desktop app's standard delete or the admin-level delete), rename or archive a channel the agent spun up on its own, and shut down a channel the agent created if it's no longer needed. This is proven to work identically whether the channel is open or private, which matters because an agent might create a private working channel and the human overseeing it still needs full control without formally joining. At the same time, the tests prove the boundary is tight: a random third party who is neither the agent nor its owner cannot do any of this, and — importantly — if a *human team member* is later removed from a private channel, they lose the ability to edit or delete even their own old messages there, so "ownership of an agent" is a distinct, narrower privilege from "current membership," and removing someone's access is not undermined by a leftover self-edit loophole.

#### Private, schedulable reminders that don't leak to other channel members (`e2e_event_reminder.rs`)

A user can set a personal reminder — "notify me about this at time X" — that the relay stores and will actively push back to them when it becomes due, even if they weren't watching at the moment it fired (the relay's scheduler catches up and delivers it). The relay enforces sensible input rules up front (a reminder needs exactly one due-time, due-time must be a clean unsigned integer within a sane range, and if there's also an expiry, the expiry can't be before or at the due-time) so malformed reminders are rejected immediately with clear reasons rather than silently misbehaving later. Critically, reminders are private: no other user — not even someone in the same channel, not even via a broad search or a filter that mixes reminder-kind events with ordinary chat messages — can see that a reminder exists, when it's due, or its contents. This is proven across every read surface a client might use (live subscription, one-shot query, count, search), not just the obvious ones. A user can also "snooze" a reminder (replace it with a later due-time) and the system correctly treats that as one evolving reminder rather than two separate ones.

#### Real git hosting with correct behavior under concurrent writers (`e2e_git.rs`)

A user can host a real git repository on Buzz and interact with it using the standard `git` CLI — clone, commit, push, pull, force-push, and tag — exactly as they would against GitHub or any other git host, with no special client tooling beyond a credential helper that handles authentication transparently. Everything that git guarantees locally (fresh clones see the latest pushed state, force-pushed history is what subsequent clones actually get, tags survive a round trip) holds true against Buzz's storage backend, which under the hood is not a persistent disk but an object store. The standout guarantee, proven under real concurrent load rather than just asserted: if multiple pushes race to update the same branch at the same time, exactly one wins cleanly, the other pushers are told they lost (so they know to pull and retry, exactly like a normal git remote's non-fast-forward rejection), and the repository ends up in a fully consistent state matching the winner — never corrupted, never split-brained, never silently missing the winning content.

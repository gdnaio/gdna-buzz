## Module: buzz-test-client — core protocol, status & team E2E (`crates/buzz-test-client`)
### Aspect: Conventions

#### Test structure conventions (shared across all four test files)

Every test file opens with a module-level doc comment explaining that tests are `#[ignore]`d by default (requiring a live relay) and giving the exact `cargo test ... -- --ignored` invocation, plus (except `nip42_host_binding_live.rs`) a `relay_url()` helper reading `RELAY_URL` with a `ws://localhost:3000` fallback. `sub_id(name)` (`e2e_relay.rs:32-34`, `e2e_user_status.rs:23-25`, `e2e_team.rs:24-26`) is reimplemented identically in each file rather than shared via the harness: `format!("e2e-{name}-{}", uuid::Uuid::new_v4())` (or the team variant's `e2e-team-{name}-{}`) — a small, harmless duplication (three near-identical private functions), consistent with the sibling `test-client-content`/`test-client-conformance` groups' own observation that this crate favors per-file self-containment over a shared test-utilities module.

Every test follows the same four-beat structure: connect (`BuzzTestClient::connect`), act (send/subscribe), assert (`ok.accepted`/`events.len()`/message substring), disconnect (`client.disconnect().await.expect(...)`). `.expect("<description>")` rather than `.unwrap()` is used almost universally for fallible harness calls — the description string becomes the panic message, which is the crate's de facto assertion-failure convention (there is no custom test macro or assertion helper anywhere in this group).

#### Naming conventions

Test function names follow `test_<subject>_<expected_outcome>` almost without exception: `test_nip29_put_user_nobody_blocks`, `test_private_channel_non_member_cannot_invite`, `test_membership_notification_requires_own_p_filter`. A handful of tests in `e2e_relay.rs` break the `test_` prefix pattern by using a plain descriptive name preceded by a doc comment instead of a `test_` prefix embedding the assertion (e.g. none observed breaking this in the current file — all 38 functions in `e2e_relay.rs` do carry the `test_` prefix), so the convention is consistently honored within this group (contrast with the two-host file below).

`nip42_host_binding_live.rs` breaks from the `test_` prefix convention entirely — its four functions are named `nip42_matching_host_accepted_a`, `nip42_cross_host_rejected_a_relay_tag_on_b_connection`, etc., with no `test_` prefix. This is likely intentional to visually group them by protocol concept rather than by the generic "test" word, but it is a real, visible inconsistency against the other three files in this same group (and the crate's other 12 test files, which all use `test_` prefixes) — see Debt.

#### `#[ignore]` attribute style

Three of the four files use bare `#[ignore]` (`e2e_relay.rs`, `e2e_user_status.rs`, `e2e_team.rs`). `nip42_host_binding_live.rs` uses `#[ignore = "requires two-host multi-tenant relay"]` on all four of its tests — the only file in this group (and, per a repo-wide grep in the sibling groups' prior analyses, one of the few in the crate) to attach a reason string. This is a strictly better pattern (the reason shows up in `cargo test` output even without `--ignored`), and its inconsistent adoption across this group's own four files (3 bare vs. 1 annotated) is a minor missed opportunity rather than a functional problem.

#### Fixture/helper function conventions

- **Event builders** are consistently named `<noun>_event` or `build_<noun>_event`: `build_user_status_event` (`e2e_user_status.rs:30-42`), `team_event`/`team_event_at`/`team_delete_event` (`e2e_team.rs:33-46`). `e2e_relay.rs` instead names its equivalents by verb-first action: `create_test_channel`, `create_private_channel_ws`, `add_member_ws`, `add_member_with_role_ws` — a genuine naming-convention split between "nouns describe what's built" (status/team files) and "verbs describe what's done" (relay file), though both are internally consistent within their own file.
- **WS-suffix disambiguation**: `e2e_relay.rs` suffixes several helpers with `_ws` (`create_private_channel_ws`, `add_member_ws`, `add_member_with_role_ws`) specifically to distinguish them from the file's own HTTP-door equivalents (`create_test_channel` goes over HTTP; the `_ws` ones go over the WebSocket `EVENT` path) — a locally useful, non-crate-wide convention that only this file needs, since it's the only file in this group mixing both transports.
- **Timestamp-explicit variants**: both `e2e_user_status.rs` (inline in `test_user_status_stale_write_rejected`) and `e2e_team.rs` (`team_event_at`, a dedicated helper) construct events with `.custom_created_at(Timestamp::from(...))` rather than relying on wall-clock `sleep`s to establish ordering for NIP-33 replacement/stale-write tests — `e2e_team.rs` factors this into a named helper while `e2e_user_status.rs` inlines it once; neither uses a real sleep for its stale-write test specifically (though `test_user_status_nip33_replacement`, a different test in the same file, does use a 1-second `tokio::time::sleep` at `:157` to establish ordering instead of an explicit timestamp) — so the same file uses *both* techniques for near-identical purposes in two different tests.

#### Kind-literal convention: hardcoded, not imported

Every kind number in this group is a local `const` (`KIND_USER_STATUS: u16 = 30315`, `e2e_user_status.rs:16`; `TEAM_KIND: u16 = 30176`, `e2e_team.rs:14`) or an inline `Kind::Custom(N)` literal — never `buzz_core::kind::KIND_*`. This matches the identical observation already made for the sibling `test-client-content` group's files and appears to be a crate-wide convention (deliberate or not) rather than something specific to this group.

#### `rustls` crypto-provider installation is inconsistent across this group's own two bin targets

`wamp_bench.rs:18-20` installs the **`aws_lc_rs`** provider (`rustls::crypto::aws_lc_rs::default_provider()`); `mention.rs:10` installs the **`ring`** provider (`rustls::crypto::ring::default_provider()`) — two different cryptography backends, chosen inconsistently, for what is architecturally the same problem (a `rustls::crypto::CryptoProvider` must be installed once per process before any TLS-capable connection, even a plain `ws://` one, per `mention.rs`'s own comment: "rustls needs a CryptoProvider even for plain ws:// connections"). Every other crate in the repository that faces this same problem (`buzz-relay`, `buzz-admin`, `buzz-cli`, `buzz-dev-mcp`, `buzz-acp`) pins `ring` explicitly via `Cargo.toml` feature flags with a comment explaining the ambiguity (e.g. `crates/buzz-relay/Cargo.toml:54-58`: "Both aws-lc-rs and ring are compiled in transitively, so rustls can't auto-select one — we install ring explicitly in main()"). `buzz-test-client`'s own `Cargo.toml:25` declares a bare `rustls = "0.23"` with no `default-features = false` and no feature selection at all — the two bin targets then independently reach for two *different* providers at runtime, rather than following the rest of the repo's established "pin `ring` via Cargo features, document why" pattern. This works today only because each binary's `main()` calls its own provider installer exactly once before any TLS-relevant code runs, and the two binaries never run in the same process — but it is a real, visible drift from an otherwise-consistent repo-wide convention, and a future third bin target copying either file as a template has a 50/50 chance of picking the "wrong" (i.e., inconsistent-with-siblings) provider. `src/main.rs` (`buzz-test-cli`) and `src/lib.rs` install no provider at all, which is fine only because neither ever opens a `wss://` connection in this group's usage (all examples and defaults use `ws://localhost:3000`).

#### Emoji in operator-facing output

`wamp_bench.rs` avoids emoji entirely (structured JSON output only). `mention.rs` and `main.rs` both use `✅`/`❌` prefixes on success/failure println output (`mention.rs:34,36`; `main.rs:70,73` and similar) — consistent with each other, and a reasonable convention for a human-run CLI tool, but notably different from the plain-text, log-line style the automated test files use for their `panic!`/`assert!` messages.

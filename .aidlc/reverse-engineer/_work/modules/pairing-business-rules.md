## Module: buzz-pair-relay & buzz-pairing-cli (`crates/buzz-pair-relay`, `crates/buzz-pairing-cli`)
### Aspect: Business Rules

#### Roles and who proves what

**Source** holds the secret and initiates by displaying a QR code; **target** scans it and receives the secret (`Role` enum, `crates/buzz-core/src/pairing/session.rs:48-55`; mirrored in the CLI's `Cmd::Source`/`Cmd::Target`, `crates/buzz-pairing-cli/src/main.rs:47-68`). Identity proof is QR-secret-possession-based, not conventional signature-based authentication: the target proves it scanned the correct QR by deriving `session_id = HKDF(session_secret)` and including it in the `offer` message; the source accepts the offer only if the received `session_id` constant-time-matches its own derivation (`handle_offer`, `session.rs:171-177`, using `ct_eq` from `crypto.rs:126-129`). A wrong or absent `session_secret` produces a non-matching `session_id`, and the offer is silently discarded (`PairingError::InvalidSessionId`, `session.rs:176`) — the source keeps waiting rather than erroring out, up to the session timeout.

The CLI enforces this as a retry loop, not a single check: `cmd_source`'s offer-wait loop explicitly discards non-matching or wrong-type events and keeps looping (`main.rs:148-155`, comment: "silently discard junk per NIP-AB §Event Validation item 7"). This matches the NIP's requirement that out-of-order/invalid messages must never trigger an `abort` (`crates/buzz-core/src/pairing/NIP-AB.md`, §Event Validation item 7) — an `abort` in response to junk would let a relay-side observer probe session state.

#### Single-offer, single-payload, single-completion — enforced by state, not an explicit counter

- **Source accepts at most one `offer`**: `handle_offer` requires `SessionState::Waiting` (`session.rs:150-152`) and transitions to `Confirming` on success (`session.rs:194`); any further `offer` fails `expect_state` and is discarded by the CLI's loop. The source also locks `peer_pubkey` to the *first* accepted offer's sender (`session.rs:181-182`); every later method (`validate_event_from_peer`, `session.rs:681-694`) rejects events from a different pubkey.
- **Payload is sent/received exactly once**: `send_payload` requires `Transferring` and transitions to `PayloadExchanged` (`session.rs:229-231`, `250`); a second call fails `expect_state`. `handle_payload` on the target likewise requires `Transferring` (`session.rs:390`) and also advances state, so a duplicate delivery is rejected twice over — by the state guard, and independently by the processed-event-ID dedup below. Directly exercised by `reject_duplicate_payload` (`session.rs:1091-1118`).
- **At most one `complete` is processed**: `handle_complete` requires `PayloadExchanged` (`session.rs:255`); once `Completed`, a replayed `complete` fails the state guard (test: `duplicate_event_id_is_rejected`, `session.rs:1148-1183`).

#### Duplicate-event handling is a separate rule layered on top of the state machine

Per `NIP-AB.md` §Duplicate Event Handling, every successfully processed event ID must be remembered so relay re-delivery of the same ID is silently discarded — independent of the state-transition guards, because a relay may redeliver the *same* event while the session is still in a state that would otherwise accept it. Implementation: `processed_ids: HashSet<[u8;32]>` on `PairingSession` (`session.rs:100-102`), checked in `validate_event_basics` (`session.rs:640-645`) and populated only by `record_event` (`session.rs:676-679`), which every handler calls **after** full acceptance — never speculatively. This ordering has a dedicated regression test: `speculative_abort_does_not_poison_dedup` (`session.rs:1186-1211`) proves that probing an event with `handle_abort()` — which the CLI does on *every* inbound event via `check_for_abort` (`crates/buzz-pairing-cli/src/main.rs:403-411`) — must not mark that event processed if it isn't actually an abort, otherwise the real handler would then wrongly treat the legitimate message as a duplicate. `complete(success:false)` is a documented exception: it aborts the session but is deliberately **not** recorded, since per spec it was "received but not successfully processed" (`session.rs:262-269`; test `complete_failure_aborts_without_recording`, `session.rs:1269-1317`).

#### SAS verification is the MITM defense, and it is a dual, asymmetric gate

1. Both sides independently compute `sas_code` from `HKDF(ecdh_shared, session_secret)` (`crypto.rs:70-75`) — the source as soon as it accepts the offer (`session.rs:186-190`), the target immediately at session construction since it already knows the source's pubkey from the QR (`session.rs:290-292`).
2. The **source's** confirmation gates sending anything sensitive: only after the human confirms SAS match does `confirm_sas()` run and set `Transferring`, the state `send_payload()` requires. The CLI enforces this by literally blocking on a y/n prompt before calling `session.confirm_sas()` (`main.rs:158-173`).
3. The **target's** confirmation is a second, independent gate: even after cryptographically verifying `sas-confirm` (`handle_sas_confirm`, `session.rs:329-372`), the target lands in `AwaitingConfirmation`, not `Transferring` — `handle_payload` stays unreachable until the user separately calls `confirm_target_sas()` (`session.rs:376-381`). The CLI mirrors this: it prints the SAS and calls `read_yes_no()` before calling `session.confirm_target_sas()` (`main.rs:288-300`). Proven by `target_must_confirm_sas_before_payload` (`session.rs:1056-1089`), which shows a payload event received before user confirmation is explicitly rejected, not merely buffered by luck.
4. Enforcement of "reject rather than proceed" is unconditional on mismatch: both CLI flows abort the whole session with `AbortReason::SasMismatch` on a `n` answer (`main.rs:163-169`, `main.rs:292-298`) — there is no retry-the-comparison path.

#### Transcript binding is a detection mechanism, not a prevention gate — and the comments say so

`sas-confirm`'s `transcript_hash` binds `session_id ‖ source_pk ‖ target_pk ‖ sas_input` (`crypto.rs:89-105`). The target verifies it in constant time (`ct_eq`, `session.rs:355-358`) and, on mismatch, transitions straight to `Aborted` and returns `PairingError::TranscriptMismatch` (`session.rs:359-361`) — a distinct, harder failure than a generic rejection. The CLI treats this specially: rather than silently looping past it like other invalid messages, `cmd_target` explicitly catches `TranscriptMismatch`, sends `abort(SasMismatch)`, and prints a security warning about a possible MITM attack (`main.rs:270-284`). Per `NIP-AB.md`'s own §Design Rationale ("Why transcript binding"), this is documented as a **consistency check**, not the actual MITM defense — the source may already have sent the payload by the time a mismatch is caught, since it does not wait for any acknowledgment before sending `payload` right after `sas-confirm` (confirmed in code: `cmd_source` calls `confirm_sas()` then immediately `send_payload()` with no wait in between, `main.rs:173-178`).

#### Session expiry rules

`DEFAULT_TIMEOUT = 120s` from creation (`session.rs:43`), checked reactively via `check_expired()`/`is_expired()` at the top of nearly every mutating method (`session.rs:698-703`, `476-478`, e.g. invoked at `session.rs:150`). This is a **soft, call-triggered** expiry, not a background sweep — an idling session does not self-terminate; the *next* call into it fails with `SessionExpired` (test: `expired_session_rejects_operations`, `session.rs:1129-1145`). Layered on top, the CLI enforces its own **per-step** timeouts, considerably shorter than the session lifetime and not derived from any shared constant: 10s waiting for `EOSE` (`main.rs:145`, `249`), 120s waiting for the offer (`main.rs:149`) or the sas-confirm (`main.rs:267`), and only 60s waiting for the payload (`main.rs:305`) or the final `complete` (`main.rs:184`) — none of these read `DEFAULT_TIMEOUT`, so a change to the session-level timeout in `buzz-core` would not automatically propagate to the CLI's wait windows (see Debt).

The relay-side `CONN_TIMEOUT` (also 120s, `crates/buzz-pair-relay/src/lib.rs:59`) is an unrelated, independently-configured rule — it bounds the WebSocket connection's lifetime at the transport layer with no knowledge of pairing-protocol state; it fires regardless of what step the two peers are on.

#### Single-use pairing codes — enforced by ephemeral keys, not an explicit "used" flag

Nothing in this code tracks "has this QR code been used." Reusability is prevented structurally: a fresh `session_secret` and ephemeral keypair are generated per `new_source()` call (`session.rs:113-114`), so re-displaying an *old* QR would require the *same* source process to still hold that exact expired-or-completed `PairingSession` object in memory — and once `Completed`/`Aborted`, both `abort()`/`handle_abort()` explicitly refuse to regress the state (`session.rs:431-435`, `449-453`; tests `local_abort_after_completed_is_rejected` and `reject_abort_after_completed`, `session.rs:871-897`, `933-983`). A brand-new `new_source()` call is a brand-new session with a brand-new secret; there is no server-side registry of "spent" codes because there is no server-side registry of codes at all (see Data Model — the relay never sees plaintext session secrets).

#### Rate limiting on pairing attempts

There is **no** pairing-specific rate limit anywhere in `buzz-core::pairing` or `buzz-pairing-cli` — a user can run `buzz-pair source` in a fresh process as many times as desired, each generating a new session with a fresh 120s window. The only rate limiting in this module group is `buzz-pair-relay`'s generic, protocol-agnostic per-connection limits: `RATE_MSG_MAX = 20` per `RATE_WINDOW = 10s` (`lib.rs:67-68`, enforced at `lib.rs:648-652`), `RATE_EVENT_MAX = 10` per window (`lib.rs:69`, enforced at `lib.rs:783-788`), plus the hard per-connection session cap `MAX_EVENTS_PER_CONN = 6` (`lib.rs:73`, enforced at `lib.rs:792-800`). These are relay-transport protections against one WebSocket connection being abused, not business rules about how many pairing *sessions* a device may attempt — a new WebSocket connection resets all of these counters, since they live on stack-local `RateWindow`/`u32` variables inside `handle_conn` (`lib.rs:625-633`), not in `Relay`'s shared state.

#### Rules enforced only by comment/convention, not by a runtime check

- **"At most one live subscriber per `#p`"** doubles as a proxy for "one active pairing party per ephemeral key" but is purely a relay routing invariant (checked inside the `REQ` handler, `lib.rs:757-765`) — nothing stops a party from disconnecting and re-subscribing under the *same* ephemeral pubkey and continuing, since the relay has no concept of "this p-value belongs to a pairing session in state X."
- **"Relays SHOULD treat kind:24134 as ephemeral / delete after delivery"** (`NIP-AB.md` §Event Kind) is a SHOULD directed at general-purpose Nostr relays; `buzz-pair-relay` satisfies it trivially (it never persists anything), but the production `buzz-relay` path (used when pairing through the main relay, per the CLI's NIP-42 support) is out of scope here and was not independently verified in this pass.
- **"session_secret must never be logged"** is not enforced by any lint or wrapper at the boundary where it is displayed: `println!("{qr_uri}")` (`main.rs:126`) is an intentional, user-facing display — the whole point of the QR flow — not a leak, but it does mean the secret transits the terminal's scrollback/history for the CLI's interactive mode, beyond the one printed caveat "do not share beyond the target device" (`main.rs:125`).

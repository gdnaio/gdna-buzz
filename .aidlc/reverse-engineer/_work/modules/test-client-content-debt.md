## Module: buzz-test-client — content & git E2E (`crates/buzz-test-client/tests`)
### Aspect: Debt

#### CI coverage summary — the pattern is NOT uniform across this group, correcting the prior assumption

The task's framing (mirroring the `git-identity` group's finding for `e2e_git.rs`) asked whether the same "zero CI coverage" pattern holds for the other three files. It does **not**, uniformly. Verified directly:

| File | `#[ignore]`d? | Wired into any CI job? | Evidence |
|---|---|---|---|
| `e2e_long_form.rs` | yes, all 8 tests (`grep -c '#\[ignore\]'` → 8 of 8) | **no** | `grep -rn 'e2e_long_form' .github/ Justfile scripts/` → zero matches |
| `e2e_event_reminder.rs` | yes, all 29 tests | **yes** | `.github/workflows/ci.yml:337-347` (archives the test binary via `cargo nextest archive ... --test e2e_event_reminder`) and `:682-693` (`backend-integration` job runs `cargo nextest run --archive-file ... -E 'binary(e2e_event_reminder)' --run-ignored ignored-only`, with `RELAY_URL: ws://localhost:3000` set) |
| `e2e_human_edit_agent_content.rs` | yes, all 19 tests | **no** | `grep -rn 'e2e_human_edit_agent_content' .github/ Justfile scripts/` → zero matches |
| `e2e_git.rs` | yes, both tests (`:196`, `:334`) | **no** | `grep -rn 'e2e_git' .github/ Justfile scripts/` → zero matches (the one hit inside `.github/` search space is `.aidlc/` backup analysis prose, not a workflow file) |

So three of the four files (`e2e_long_form.rs`, `e2e_human_edit_agent_content.rs`, `e2e_git.rs`) match the zero-CI-coverage pattern the prior `git-identity` analysis found for `e2e_git.rs` specifically. **`e2e_event_reminder.rs` is the exception** — it is the one file in this entire group that actually runs automatically, on every push and on every PR that touches `rust`-filtered paths (`backend-integration` job condition: `github.event_name == 'push' || needs.changes.outputs.rust == 'true'`, `.github/workflows/ci.yml:568`). This is a materially different risk profile from the other three: a regression in NIP-ER's write validation, author-only read gating, or scheduler delivery would be caught by CI; an equivalent regression in long-form articles, agent-ownership authorization, or git-on-object-storage would not be caught by anything automated — a human would have to remember to run those suites manually against a local relay.

This means the earlier framing in the task prompt ("mirroring the pattern already confirmed for `e2e_git.rs` in prior analysis") is only two-thirds correct for this group, and the correction is itself the most significant finding of this analysis: **19 of the 19 tests protecting the human-can-override-agent authorization boundary — arguably the most security-sensitive rule set in this entire group — have zero automated regression protection**, identical in that respect to `e2e_git.rs`'s CAS-race regression fence, which at least has `docs/git-on-object-storage.md` explicitly calling out its manual-only status as a known, named risk (the spec's own "parked, not closed" framing). No equivalent acknowledgment exists anywhere for `e2e_human_edit_agent_content.rs` or `e2e_long_form.rs` going unrun in CI.

#### `TESTING.md` doesn't mention any of the four files, or the crate's own per-test-file CI wiring, by name

`TESTING.md`'s guidance is uniform and file-agnostic: "Neither task runs the E2E suites in `buzz-test-client` — those are marked `#[ignore]` and require a running relay: `cargo test -p buzz-test-client -- --ignored`" — true as a blanket statement, but it gives a reader no indication that `e2e_event_reminder.rs` specifically *does* run in CI (just not via `just test`/`just test-unit`, and not via that exact command either — CI uses `cargo nextest run -E 'binary(e2e_event_reminder)'`, a different invocation shape than the doc's suggested `cargo test -p buzz-test-client -- --ignored`, which would run *all* ignored tests in the crate including the three files with no CI coverage, not just the reminder file). A reader trying to reproduce CI's actual reminder-test coverage locally by following `TESTING.md`'s literal instructions would run all four files' tests, not just the one CI actually checks — harmless locally, but it means `TESTING.md` cannot be used to infer which of these four files' failures would currently block a merge.

#### `git-credential-nostr`/`GIT_CREDENTIAL_NOSTR_BIN` is built and wired in CI but never pointed at `e2e_git.rs`

The `relay-e2e` CI job (`.github/workflows/ci.yml:703-741`) downloads the pre-built `git-credential-nostr` binary, `chmod +x`s it, and exports `GIT_CREDENTIAL_NOSTR_BIN` (`:734`) — all the scaffolding `e2e_git.rs`'s own doc comment says is required to run it — but the job's actual test invocations (`:729-731`) run `e2e_persona`, `e2e_nostr_interop`, and two named tests inside `e2e_relay` (`invite`, `nip43_membership_snapshots_are_rejected`). None of those are `e2e_git.rs`. So the env var and binary are fully staged and available in that CI job's environment, and the only thing missing to actually run `e2e_git.rs`'s two tests there is one more `cargo test -p buzz-test-client --test e2e_git -- --ignored --nocapture` line (plus, per the git-on-object-storage backend requirement, MinIO — which is *not* started by the `relay-e2e` job's own service list, unlike `backend-integration`, which does start `minio`/`minio-init`, `.github/workflows/ci.yml:577`). This is the most actionable, lowest-effort fix identified in this analysis: the missing piece isn't "build the tooling," it's "start MinIO in this job and add the test invocation" — everything else is already assembled.

#### Setup/teardown boilerplate duplicated across files instead of living in the shared harness

The harness (`buzz_test_client::BuzzTestClient` in `lib.rs`) has **no HTTP capability at all** — `reqwest` is a `[dev-dependencies]` entry in `Cargo.toml` (`:31`), consumed only by individual test files, never by `lib.rs`. This has led to the same POST-to-`/events`-with-`X-Pubkey`-header pattern being hand-rolled independently in at least three places:

| Reimplementation | File | Lines |
|---|---|---|
| `submit_event_http(client, keys, event) -> (bool, String)` | `e2e_event_reminder.rs` | `:92-116` |
| `post_event(event: &nostr::Event)` (panics on non-2xx rather than returning a result) | `e2e_git.rs` | `:47-59` |
| inline block inside `create_agent_owned_channel` / `create_private_agent_owned_channel` | `e2e_human_edit_agent_content.rs` | `:47-65`, `:610-622` — byte-for-byte structurally identical to `create_agent_owned_channel`'s block, itself duplicated once *within this same file* |

All three build the same `POST {relay_http_url}/events` request with an `X-Pubkey` header carrying the signer's hex pubkey and a JSON body of the signed event — differing only in whether the result is returned as a tuple, panicked on, or asserted inline. A fourth near-identical implementation exists in this crate's other e2e files outside this group's scope (`e2e_media.rs`, `e2e_media_extended.rs`, `e2e_media_video.rs` all define their own `relay_http_url()` with the same default, per the Configuration doc's citations) — this is a crate-wide pattern, not unique to this group, but this group alone contributes three of the reimplementations. None of the four files in this group call `BuzzTestClient::send_event` when an HTTP path is available and easier to reach for, even in files (`e2e_human_edit_agent_content.rs`) that otherwise use the WebSocket harness extensively for everything else — the two transports are mixed within a single file with no documented rule for when to use which.

The `relay_http_url()` derivation itself (`.replace("wss://","https://").replace("ws://","http://")`) is duplicated verbatim between `e2e_event_reminder.rs:32-38` and `e2e_human_edit_agent_content.rs:29-35` — an eight-line function copy-pasted rather than factored into the shared harness or a small shared test-utility module.

`create_agent_owned_channel` (`:38-72`) and `create_private_agent_owned_channel` (`:591-624`) in `e2e_human_edit_agent_content.rs` are the same function with one tag value changed (`"open"` vs `"private"`) — 34 lines duplicated for a one-token difference; a `visibility: &str` parameter would collapse these to one function.

#### Oversized files, and what's actually driving the size

`e2e_event_reminder.rs` (1,178 lines, 29 tests) and `e2e_human_edit_agent_content.rs` (991 lines, 19 tests) are both large. In both cases the size is mechanical repetition of a small set of setup steps (generate keys, build event, submit, assert) across many near-identical scenarios, not any single overly-complex test. This is a legitimate structural debt even though no single function is unreasonably long: a change to the setup shape (e.g. if `submit_event_http`'s signature needed to change, or if channel-creation needed a new required tag) would require touching a large fraction of the file's 20-30 call sites rather than one shared helper. Neither file is protected by any file-size lint (see Conventions) — nothing will flag further growth.

#### Untested paths within what these files claim to cover

- **`e2e_git.rs`'s own module doc claims coverage of "clone / push / fetch / force-push / tag"**, but no invocation of literal `git fetch` appears anywhere in the file (confirmed: `grep -n '"fetch"'` inside the arg arrays returns no matches) — the file uses `git pull` (`:280`) wherever the doc's prose says "fetch." `pull` performs a fetch-then-merge internally, so the underlying wire protocol path is exercised, but a reader relying on the doc comment to know "there's a standalone fetch test" would be imprecise; there is no test that fetches without also merging/checking-out, and no test of `git fetch` followed by inspecting `FETCH_HEAD` or a remote-tracking ref directly.
- **`e2e_git.rs` never queries or asserts on kind:30618** (`KIND_GIT_REPO_STATE`, the relay-signed ref-state event NIP-34/the relay's own git module emits after a successful push, per `docs/git-on-object-storage.md`'s Implementation Correspondence section: "kind:30618 derived after CAS ... Emission is conditional on `manifest_changed`"). This file's assertions are 100% git-plumbing-plus-direct-S3; it never subscribes to or queries for the Nostr-visible ref-state notification at all (confirmed: `grep -n '30618'` in this file returns no matches). This is a real, previously-unflagged coverage gap: the spec document treats 30618 emission as a first-class, provable behavior ("30618 emission happens after `cas_publish` returns `Ok` and before the success `Response` is constructed"), but nothing in this e2e file — the closest thing this repository has to a live end-to-end proof of the git-store's behavior — checks that the event is actually published, contains the right refs, or arrives before/after the git response as the spec requires. If 30618 emission silently broke, none of this group's tests, nor (per this group's read-only scope) any test this analysis has visibility into, would catch it.
- **`e2e_git.rs` never exercises repo-id validation or the per-pubkey repo quota.** Both test repo names (`format!("e2e-git-{}", std::process::id())`, `:203`; `format!("e2e-git-concurrent-{}", std::process::id())`, `:341`) are simple, always-valid identifiers well under any length limit — there is no test here of an invalid repo id being rejected, or of the `BUZZ_GIT_MAX_REPOS_PER_PUBKEY` quota (default 100, per cross-referenced configuration analysis) being enforced. This may be intentionally out of scope for a *client protocol* e2e test (repo-id validation is arguably `buzz-cli`'s or the relay unit-test suite's job), but it means this file's "full manifest-pointer CAS commit path" framing in its own doc comment slightly overstates what it covers — the CAS *commit* path is thoroughly covered; the repo-*lifecycle* edge cases (bad names, quota) are not.
- **`e2e_long_form.rs` never exercises `summary`, `image`, or `t` (topic) tags** — every article built by `build_long_form_event` carries only `d` and `title` plus whatever `extra_tags` a given test adds (confirmed: no test in this file adds a `summary`, `image`, or `t` tag). NIP-23's fuller tag surface (as summarized generically in the relay's `KIND_LONG_FORM` doc comment) is untested here. This may be intentionally minimal (those tags are presumably relay-agnostic passthrough data with no special validation), but it's worth naming as an absence.
- **`e2e_long_form.rs`'s stray-`h`-tag test proves only half the property it names.** As detailed in Business Rules, `test_long_form_stray_h_tag_ignored`'s own comment (`:169-180`) explicitly says the *write* side (global storage despite the tag) is proven, but the *read* side (that an `#h`-scoped query does *not* return the article) is a "pre-existing limitation" the test does not close the loop on and explicitly defers as a follow-up. This is unusually transparent self-documentation of a coverage gap (the test author flagged it themselves), but it means the test's name overstates what's actually verified — "stray h tag ignored" is true for storage, not for read-side filtering.
- **`e2e_human_edit_agent_content.rs` never tests the non-privileged half of kind:9002** (the `topic`/`purpose` branch, which only requires plain channel membership, `side_effects.rs:526-536`) under the owner-bypass scenario — see Security for detail. Also untested: what happens when an agent has **multiple** owners, or when ownership itself is revoked (there is no kind:9002/analogous "remove NIP-OA ownership" event tested anywhere in this file — only channel membership removal is tested, not ownership revocation).

#### Dead code / unused harness surface

`BuzzTestClient::close_subscription` (`lib.rs:159-163`) is never called by any of the four files in this group (see API Surface) — not dead code in the crate overall (other e2e files outside this group's scope may call it), but worth noting from this group's vantage point: every subscription in these four files is torn down implicitly via `disconnect()` rather than explicitly closed first, so this group never exercises the `CLOSE` message path end-to-end.

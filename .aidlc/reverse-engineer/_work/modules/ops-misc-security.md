## Module: buzz-admin, sprig & countdown-bot (`crates/buzz-admin`, `crates/sprig`, `examples/countdown-bot`)
### Aspect: Security

#### buzz-admin bypasses the relay's authorization AND audit path — confirmed precisely

`buzz-admin` calls `buzz-db` functions directly, in-process, against Postgres — it never goes through the relay's WebSocket or HTTP surface (see `ops-misc-integrations.md` for the full call-site evidence). This means it bypasses two independent security-relevant mechanisms that every other way of changing relay membership goes through:

1. **Authorization.** The relay's own WebSocket-based path for the identical operation — the NIP-43 admin events (kind:9030 add-member, kind:9031 remove-member, kind:9032 change-role) — enforces an explicit permission matrix requiring the *sender* to already be an authenticated relay member with role `admin` or `owner` before any mutation is allowed (`crates/buzz-relay/src/handlers/relay_admin.rs:8-13` doc comment, enforced at `:147,176,226,285`). `buzz-admin`'s `add-member`/`remove-member` commands have **no equivalent check on the operator running the CLI** — the only "authorization" a caller of `buzz-admin add-member` needs is knowledge of `DATABASE_URL`, `REDIS_URL`, and `BUZZ_RELAY_PRIVATE_KEY` (`connect_member_services`, `main.rs:389-417`; required-env doc in `NOSTR.md:230-236`). There is no pubkey-based, role-based, or credential-based gate inside `buzz-admin` itself — anyone who can execute the binary with those three environment variables set can add or remove any member (except the owner) at any role up to `admin`. Compare: the WS path additionally forbids an `admin` sender from granting the `admin` role (`relay_admin.rs:187-189`, "only owner can grant admin role"); `buzz-admin`'s `add-member --role admin` has no such restriction because there is no "sender role" concept at all — whoever runs the CLI implicitly has owner-equivalent authority over membership.
2. **Audit.** Confirmed by exhaustive grep (see `ops-misc-integrations.md`): `buzz-admin` never calls anything in `buzz-audit`, and no code path anywhere in the repository — including the relay's own `relay_admin.rs` WS handler — calls `AuditAction::MemberAdded` or `MemberRemoved` outside a unit test. So membership changes made via `buzz-admin` are audited exactly as much as membership changes made any other way today: **not at all**. This is a pre-existing gap in the relay's audit coverage, not a `buzz-admin`-specific regression, but it is worth stating precisely: an operator cannot use the hash-chain audit log (`buzz-audit`, described in `SECURITY.md`'s "Append-Only Audit Log" section as designed "for SOX-grade compliance and eDiscovery") to answer "who added this relay member and when" through *either* code path, and `buzz-admin` declaring `buzz-audit` as a dependency (`Cargo.toml:20`) without using it does nothing to close that gap despite superficially suggesting the crate is audit-aware.

Search indexing is the one side-effect that *is* preserved, because it is implemented as a Postgres generated column (`search_tsv`) rather than an application-level step — any row `buzz-admin` writes through `buzz-db` is indexed identically to a relay-written row (see `ops-misc-integrations.md`).

#### How does an operator authenticate to run buzz-admin at all?

There is **no credential check inside `buzz-admin` itself** for any subcommand. The de facto trust boundary is entirely external to the binary:

- In the documented Compose deployment, `buzz-admin` runs via `docker compose exec relay buzz-admin ...` (`NOSTR.md:227-234`) or `./run.sh add-member ...` (`run.sh:89-96`), which requires the operator to already have `docker` access to the host running the relay container. `buzz-admin` inherits the relay container's `DATABASE_URL`/`REDIS_URL` environment automatically in that case (`deploy/compose/compose.yml:12-13`); `BUZZ_RELAY_PRIVATE_KEY` is set from `.env` (`compose.yml`'s `env_file: - .env` plus `deploy/compose/.env.example:27`).
- In local dev, `just setup`/`_ensure-migrations` runs `cargo run -p buzz-admin -- migrate` directly on the developer's machine against whatever `DATABASE_URL` is configured (`Justfile:189-190`), with no auth step at all.
- There is no separate "admin token," no pubkey-based operator identity, and no interactive confirmation prompt before a destructive action (e.g. `remove-member` executes immediately on a valid parse, no "are you sure?" step, `main.rs:194-251`).

So the honest answer to "is this a credential check or is it implicitly-trusted shell/DB access" is: **it is implicitly trusted access to the deployment's `DATABASE_URL` + `REDIS_URL` (+ `BUZZ_RELAY_PRIVATE_KEY` for member-management commands), with no additional gate.** This is architecturally consistent with `docs/admin/README.md`'s description of the *separate* read-only web dashboard's trust model ("the human trust boundary remains the private admin ingress ... VPN/source-IP admission is not per-operator identity") — the same pattern (network/infra-level trust, no per-operator identity or authorization check in the tool itself) recurs here, but for a **write-capable, membership-mutating** tool rather than a read-only dashboard, which is a meaningfully higher-stakes instance of the same pattern. Nothing in `SECURITY.md`, `NOSTR.md`, `ARCHITECTURE.md`, or `docs/admin/README.md` states this trust model explicitly for `buzz-admin` — it has to be inferred from the code. See `ops-misc-debt.md` for whether this is documented as an intentional boundary anywhere.

#### The same-second-race has a narrow security-adjacent consequence

Because `publish_membership_list_with_bump` reads-then-writes without a lock (`main.rs:315-385`, contrasted with the relay's locked equivalent in `ops-misc-business-rules.md`), two concurrent `buzz-admin` invocations against the same community can result in one publish silently losing (its `replace_addressable_event` call returns `was_inserted = false` because the other write already claimed that `created_at` second, `main.rs:363-368`). The practical effect is a stale kind:13534 roster being served to live clients after an add/remove that appeared to succeed (exit code 0) — a membership-list staleness/consistency issue, not a privilege-escalation vulnerability, but worth flagging under Security because a stale roster that *omits* a just-removed member's absence, or *omits* a just-added member's presence, is a data-integrity-adjacent correctness gap in a security-relevant list. The code's own module doc comment already flags the race (`main.rs:14-19`); this analysis confirms the mechanism precisely (unlocked read-then-write vs. the DB layer's advisory-locked equivalent).

#### sprig: argv[0]-based dispatch — no injection surface, but no allowlist safety net either

`sprig`'s dispatch key is `Path::new(&argv0).file_name()`, lowercased (`crates/sprig/src/main.rs:9-14`). This is not attacker-controllable in any way that matters: `argv[0]` is supplied by whatever launched the process (the shell, exec(), or a symlink's target name) — there is no way for remote/network input to influence it, and it is never parsed as a path to open, a command to shell out to, or a format string. It is purely a `match` key against four literal strings, so there is no path-traversal, command-injection, or format-string surface here. The one genuine risk is the *permissive* wildcard fallback: any name that isn't `"buzz-acp"`, `"buzz-agent"`, or `"sprig"` — including a typo, an unexpected symlink name, or literally anything else — silently starts `buzz_dev_mcp::run()` (`main.rs:41`), which in turn opens either a shell/file-editing MCP server over stdio or one of five further sub-dispatches (`rg`, `tree`, `buzz`, `git-credential-nostr`, `git-sign-nostr`, `crates/buzz-dev-mcp/src/lib.rs:149-152`). There's no explicit "unrecognized personality, refuse to run" error path the way `sprig`'s own direct-invocation arm has (`main.rs:32-37`) — the fallback is fail-*open* to the most powerful of the personalities (a shell/file-edit-capable MCP server) rather than fail-closed. Given the binary is only ever installed with operator-controlled symlinks (per its own README: "Installers can create links with: `ln -s sprig buzz-acp`", `main.rs:47-52`), the practical exposure is low, but it's worth noting the fallback direction is toward more capability, not less.

#### Secret handling across the three

- `buzz-admin`: reads `BUZZ_RELAY_PRIVATE_KEY` from the environment (`connect_member_services`, `main.rs:396-401`) and parses it with `Keys::parse` — the raw secret is held in memory only as a `nostr::Keys` value and is never logged or printed. `generate-key` deliberately prints a freshly generated secret key to stdout (`main.rs:134-137`) — this is the intended bootstrap UX (operator is expected to copy it into `BUZZ_RELAY_PRIVATE_KEY`/a secrets store immediately), not a leak, but it does mean the secret transits the terminal/shell history/CI log of whatever invoked `generate-key`, with no redaction.
- `sprig`: no secret handling at all — it never reads any credential-shaped env var itself (only the three downstream crates it dispatches to do, e.g. `NOSTR_PRIVATE_KEY`/`BUZZ_PRIVATE_KEY`/`ANTHROPIC_API_KEY` per `scripts/build-sprig.sh`'s bundled README "Configure" section).
- `countdown-bot`: reads `BUZZ_BOT_PRIVATE_KEY` and, in owner-attested mode, `BUZZ_OWNER_PRIVATE_KEY` (`required_env`, `main.rs:86-95`), both parsed via `Keys::parse` and never printed — only the *public* key is ever `eprintln!`'d (`main.rs:38-40`, `eprintln!("countdown-bot pubkey: {}", ...)`). The owner-attestation flow itself is a legitimate NIP-OA delegation pattern (docs at `docs/nips/NIP-OA.md`) rather than a raw secret share — the owner key signs a scoped, reusable capability tag rather than being transmitted or reused directly by the bot.

None of the three write secrets to disk, log files, or any persistent store beyond what the operator's own shell/environment already does.

#### Test coverage of this aspect

Zero automated tests exist for any of the security-relevant behavior described above: `buzz-admin`'s missing authorization gate, its missing audit integration, and the same-second race are all confirmed by code reading, not by a failing/passing test (there are no tests in `crates/buzz-admin/` at all). `sprig`'s fail-open fallback dispatch is likewise untested. `countdown-bot`'s auth-tag verification path (`buzz_sdk::nip_oa::verify_auth_tag`, called at `main.rs:104`) is tested at the `buzz-sdk` crate level (outside this module's scope) but `countdown-bot`'s own test module (`main.rs:392-436`) does not exercise it.

## Module: buzz-push-gateway (`crates/buzz-push-gateway`)
### Aspect: Security

#### Device/client authenticity: Apple App Attest

Installation-scoped operations (`enroll`, `delegate`, `rotate_endpoint`, `revoke_delegation`, `revoke_installation`) are authenticated by Apple App Attest, not by a bearer token or API key. `AppAttestVerifier::new` (app_attest.rs:37-45) hard-fails construction unless the supplied root cert PEM's SHA-256 digest exactly matches a pinned constant, `APPLE_APP_ATTEST_ROOT_PEM_SHA256` (app_attest.rs:11-14) — an operator cannot point the service at a substitute or self-signed root even by misconfiguring the mounted file path; the byte-for-byte pin is checked in-process at startup, not just documented. `docs/push-gateway-deployment.md` independently states the same fingerprint in prose ("exact PEM-file SHA-256 `c778d09ac341f7fd9f8f3b19e2b815af6aed4ad4490e1e92c05cb355212a5013`"), and I confirmed this string matches the byte array in `app_attest.rs:11-14` when hex-encoded — no drift between the doc and the code's pinned constant.

Attestation verification (`verify_attestation`, app_attest.rs:47-73) delegates the actual chain-of-trust cryptography to the external `appattest` crate (`Attestation::from_cbor_bytes(...).verify(challenge, app_id, key_id_b64, root_pem)`, app_attest.rs:63-69) and additionally bounds the CBOR blob to `MAX_ATTESTATION_BYTES` = 16 KiB (app_attest.rs:9, 56-58) and asserts the decoded key id is exactly 32 bytes (app_attest.rs:70-72) before trusting it. Assertion verification (`verify_assertion`, app_attest.rs:75-100) bounds the CBOR to `MAX_ASSERTION_BYTES` = 1024 bytes (app_attest.rs:10, 82-84) and independently extracts the `signCount` via a hand-rolled, closed two-field CBOR map parser (`assertion_counter`, app_attest.rs:118-136) that rejects any unexpected key (app_attest.rs:129) or wrong-length `authenticatorData` (app_attest.rs:132-134) before the underlying `appattest` library's own verification runs. The module's own doc comment is explicit about the residual trust gap: "It does not prove an Apple-issued binding between that key and the APNs token; accepting the directly submitted token is the protocol's explicit bootstrap assumption" (app_attest.rs:2-5) — this is a named, accepted risk rather than an oversight, and it is echoed in `docs/nips/NIP-PL.md`'s enrollment section.

Each App Attest operation additionally binds to a fresh, single-use, server-issued 32-byte challenge (never client-generated) with a 300-second TTL, consumed exactly once via a database-enforced `DELETE ... WHERE id=$1 AND challenge_hash=$2 AND expires_at >= $3` requiring exactly one affected row (postgres.rs:122-129). Every mutating request also signs a route-specific transcript containing a fixed `audience` URL string (see `push-gateway-business-rules.md`), so a signed payload cannot be replayed against a different route even if the challenge were somehow reused.

#### APNs signing credential storage and use

The APNs provider key (`.p8`) is read once at process startup from a file path (`BUZZ_PUSH_APNS_KEY_PATH`, main.rs:39, `fs::read(&c.apns_key_path)?`) and parsed into an in-memory `p256::ecdsa::SigningKey` (apns.rs:177-178); the raw PEM bytes are not retained beyond that parse (the `p8` byte slice passed to `ApnsTransport::token` is not stored on the struct — only the derived `SigningKey` is, apns.rs:161-171). The signed JWT is cached in a `Mutex<Option<CachedJwt>>` for 50 minutes (apns.rs:151-154, 195-198) to avoid re-signing on every request; the cache is cleared, not the key, on `refresh_credential()` (apns.rs:264-269). Nothing in this crate writes the `.p8` key material, the derived `SigningKey`, or the JWT to a log line, metric label, or error message — I grepped every `tracing::`/`error(`/`ErrorBody`/metrics call site in `apns.rs`, `main.rs`, and `config.rs` for interpolation of key-related variables and found none; the sole `tracing::warn!` call in the crate (main.rs:76) is a static string with no interpolated fields at all. In deployment, the key is mounted read-only from a Kubernetes Secret at `/run/buzz/apns/provider.p8` (`deployment.yaml`, `apnsKey.secretName`/`apnsKey.secretKey` in `values.yaml`) with `readOnlyRootFilesystem: true` and all Linux capabilities dropped on the container (`deployment.yaml`'s `securityContext`).

#### Secrets reaching logs or error messages — checked, not found

I specifically checked whether any of the following could reach an HTTP response body or log line: the raw APNs device token, the App Attest private-key material (never held by the server at all — only the public key is stored), the AEAD grant/token keys, or the APNs provider key. `error()` (http.rs:52-54) and `authority_error()` (http.rs:83-90) only ever return one of a small closed set of static `&'static str` codes (see `push-gateway-api-surface.md`) — there is no code path in `http.rs` that interpolates a request field, a decrypted plaintext, or a database error message into a response body. `postgres.rs`'s `db(sqlx::Error) -> AuthorityError` (postgres.rs:71-73) discards the `sqlx::Error` entirely rather than logging or returning any part of it, so a SQL error (which could in principle include bound-parameter values in some drivers' debug formatting) never reaches the client or a log. This is a deliberate, structurally-enforced property, not merely a convention followed by discipline.

#### Input validation on HTTP-facing fields

Every request body is parsed through `strict_json::from_slice`, which rejects duplicate JSON object keys at any nesting depth and trailing data after the document (strict_json.rs:76-81; see `push-gateway-business-rules.md`). Every request struct in `model.rs` is `#[serde(deny_unknown_fields)]`, so an unexpected extra field is a hard `400 invalid_request`, not silently ignored. Field-level validation is manual (no `validator`-style derive crate is used) but consistently applied before any state mutation: hex-string fields are checked with closed-character-class predicates (`valid_endpoint` http.rs:55-61, `valid_relay_pubkey` http.rs:62-66) that additionally reject uppercase hex (`!b.is_ascii_alphabetic() || b.is_ascii_lowercase()` in `valid_endpoint`, enforcing lowercase-only even though `is_ascii_hexdigit()` alone would accept uppercase) — this closes a canonicalization ambiguity that could otherwise let the same logical token/pubkey be represented two different ways in storage/replay-fence keys. Numeric bounds (epoch/generation `>= 1`, lifetime ranges) are checked inline in each handler before any store call. The public HTTP body-size ceiling (`MAX_REQUEST_BYTES` = 8192, enforced by `RequestBodyLimitLayer`, http.rs:747) and the grant/ciphertext-specific ceilings (`MAX_GRANT_BYTES` = 4096, `MAX_CIPHERTEXT_BYTES` = 2048) bound every attacker-controlled buffer before it is parsed or decrypted, mitigating decompression-bomb-style or unbounded-allocation attacks against the JSON/CBOR/AEAD parsers.

#### Rate limiting and abuse controls

Two independent, narrow mechanisms exist; there is no general-purpose rate limiter:
1. **Concurrency limit**, not a rate limit: `ConcurrencyLimitLayer::new(256)` on the public router (http.rs:748) bounds in-flight requests across *all* routes and *all* callers combined to 256 — it does not distinguish one caller from another, so 256 concurrent requests from a single relay can exhaust the same budget as 256 different relays.
2. **Per-endpoint delivery quota**: `push_gateway_endpoint_quotas`, keyed by `token_fingerprint` (SHA-256 of profile+token, `endpoint_fingerprint`, http.rs:96-102), default 10 admitted deliveries per rolling 10-second window (see `push-gateway-configuration.md`), enforced atomically in the admission transaction (postgres.rs:320-321).

**Gap I can confirm from the code:** there is no rate limit keyed on relay identity, source IP, or installation identity for the mutating installation/delegation endpoints (`challenge`, `enroll`, `delegate`, `rotate_endpoint`, `revoke_*`). A single caller (or many callers behind the concurrency cap) can call `POST /v1/installations/challenges` an unbounded number of times; each call performs one `getrandom::fill`, one INSERT, and returns 200 — there is no per-IP or per-key throttle on challenge issuance, and I found no reference to `tower_governor`, a Redis-backed limiter, or any other rate-limiting crate in `Cargo.toml`'s dependency list. Postgres itself becomes the only backpressure mechanism for this path. `docs/push-gateway-deployment.md` documents this quota policy explicitly as "Buzz policy hypotheses, not Apple-published limits" for the delivery path only — it makes no claim about, and does not mention, any rate limit on the installation/delegation endpoints, which is consistent with the code.

#### TLS

The process itself speaks plain HTTP internally — I grepped `main.rs`/`http.rs` for `rustls`/`TlsAcceptor`/`axum_server`/`native_tls` and found no matches; `axum::serve(listener, public)` (main.rs:113) binds a bare `tokio::net::TcpListener` with no TLS layered on top in-process. TLS for the public `https://push.buzz.xyz` endpoint is terminated upstream, at the Kubernetes Gateway API layer: the Helm chart's `httproute.yaml` defines a `gateway.networking.k8s.io/v1` `HTTPRoute` attaching to an externally referenced `Gateway` (`.Values.httpRoute.parentRefs`), and the chart ships no TLS certificate/keypair resources of its own — TLS termination is entirely the referenced `Gateway`'s responsibility, outside this crate and outside this chart. Outbound calls to Apple (`ApnsTransport`) use `reqwest` configured workspace-wide with the `rustls` feature (root `Cargo.toml:93`, `features = ["json", "rustls"], default-features = false`), so the outbound APNs leg is TLS via rustls, not plaintext, and not OpenSSL.

#### `strict_json.rs` as a defense against parsing ambiguity

`strict_json.rs`'s role is explicitly anti-ambiguity, not injection-prevention in the SQL/XSS sense (there is no templating or string concatenation into SQL anywhere in this crate — every `postgres.rs` query uses `sqlx::query(...).bind(...)` parameter binding, except the intentionally-controlled DDL/grant statements in `apply_migrations_and_grants`, which validate `runtime_role` against a strict PostgreSQL-identifier character class before interpolating it via `AssertSqlSafe`, postgres.rs:24-30, 36-53). Its actual security value is closing the classic "duplicate JSON key" ambiguity class: standard `serde_json` deserialization silently keeps the *last* occurrence of a duplicate key, which means a naive validator that inspects one occurrence and a naive deserializer that uses another could disagree about what a request "means" (a parser-differential class of bug). By rejecting any document with a repeated key at any depth (strict_json.rs:59-68) before the target type is ever populated, this module removes that entire ambiguity class for every request body and for the decrypted grant plaintext (grant.rs:92). It is also used to enforce that trailing garbage after a JSON document is rejected (`deserializer.end()?`, strict_json.rs:80) — a raw `serde_json::from_slice` would silently ignore trailing bytes.

#### Cross-keyring isolation (grant vs. token AEAD keys)

`Config::from_map` explicitly rejects any overlap between the grant keyring and the token keyring, checking both key-id equality and raw-key-byte equality (config.rs:96-102): `if grant_keys.iter().any(|grant| token_keys.iter().any(|token| grant.id == token.id || grant.key == token.key))`. This is a deliberate defense against a single compromised or misconfigured key being usable to both mint delivery capabilities *and* decrypt custody-held APNs tokens — the doc comment on the `Config` struct states this as a hard requirement: "These keys MUST NOT be reused for externally presented delivery capabilities" (config.rs:29-31). Tested by `cross_keyring_id_or_material_reuse_fails_startup` (config.rs:271-280).

#### What I could not verify

- I did not verify the `appattest` crate's own internal implementation for vulnerabilities — it is treated as a trusted external dependency for the purposes of this analysis, per the scope of this document (crate-level review of `buzz-push-gateway`'s own code).
- I could not verify from static analysis alone whether the Kubernetes NetworkPolicy resources (`networkpolicy.yaml`, `migration-networkpolicy.yaml`) are actually enforced by the target cluster's CNI — NetworkPolicy enforcement depends on the CNI plugin, and the chart's own comments acknowledge this ("Kubernetes NetworkPolicy cannot allow DNS names... Production operators must narrow these CIDRs").

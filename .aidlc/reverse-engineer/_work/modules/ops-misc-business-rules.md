## Module: buzz-admin, sprig & countdown-bot (`crates/buzz-admin`, `crates/sprig`, `examples/countdown-bot`)
### Aspect: Business Rules

#### buzz-admin: add-member

1. Role must be `"member"` or `"admin"` — `"owner"` is explicitly rejected with a message pointing at `RELAY_OWNER_PUBKEY` instead (`validate_role`, `main.rs:290-301`). Any other string is rejected as invalid (`main.rs:298-300`).
2. Pubkey must parse as a bech32 `npub` or 64-char hex via `nostr::PublicKey::parse` (`parse_pubkey_hex`, `main.rs:303-308`); invalid input exits 1 (`main.rs:166-171`).
3. Insert is idempotent: `db.add_relay_member` returns `Ok(true)` if newly inserted, `Ok(false)` if the pubkey already existed for that community — the existing role is **not** overwritten on a re-add (`main.rs:179-184`; same idempotent-no-overwrite behavior is independently documented for the relay's own WS-based add-member path at `crates/buzz-relay/src/handlers/relay_admin.rs:195-198`, so the two code paths agree on this rule even though they don't share code).
4. After a successful (or no-op) DB write, the CLI always attempts to republish the kind:13534 roster; a publish failure is only a **warning**, not a command failure — the process still exits 0 (`main.rs:186-189`). This means `add-member` can report success while live clients never see the updated roster until the next successful publish.
5. Tenant is resolved once per invocation from `RELAY_URL` (`resolve_admin_tenant`, `main.rs:439-458`) and is fixed for the whole command — there is no cross-community "add to every community" mode (explicitly called out in the function's doc comment, `main.rs:433-437`).

#### buzz-admin: remove-member

1. If `--role` is supplied, it is validated the same way as `add-member`'s role (`main.rs:195-200`).
2. Two different DB calls depending on whether `--role` was passed: `remove_relay_member_if_role` (atomic role-conditional delete) vs. plain `remove_relay_member` (`main.rs:213-219`). Both are single-statement `DELETE ... WHERE role <> 'owner'` (or `= expected_role`) with a follow-up read only to classify the zero-rows-affected case (`crates/buzz-db/src/relay_members.rs:196-224` and `:242-276`) — this is TOCTOU-safe by construction, not by a separate lock, per the doc comments at `relay_members.rs:193-195` and `:236-241`.
3. The relay owner can **never** be removed via this command, regardless of the `--role` filter — enforced at the SQL level (`role <> 'owner'` in the `DELETE`, `relay_members.rs:198-199`) and surfaced as exit code 3 with an explicit pointer to `RELAY_OWNER_PUBKEY` (`main.rs:233-239`). This is a hard rule with no override flag.
4. Role-filtered removal can race with a concurrent role change: if the target's role changed between when the operator looked it up and when this command runs, the delete affects zero rows and the CLI reports `RoleMismatch` (exit 4) rather than removing the member — this is the intended atomicity guarantee, described explicitly in the DB function's doc comment (`relay_members.rs:236-241`).
5. Same republish-is-best-effort rule as `add-member`: a failed roster republish after a successful removal is only a warning (`main.rs:248-251`).

#### buzz-admin: NIP-43 membership-list republish — the same-second race

`publish_membership_list_with_bump` (`main.rs:315-385`) enforces exactly one ordering rule to defeat *serial* invocations landing in the same wall-clock second: `custom_created_at = max(now, newest_existing_created_at + 1)` (`main.rs:340-345`, doc comment `:309-313`). This rule is explicitly documented as **not** solving the concurrent case: "two near-simultaneous adds can read the same newest timestamp and collide on the bumped second" (module doc comment, `main.rs:16-19`, restated verbatim in `NOSTR.md:311-315`). The stated mitigation is operational, not code-level: `run.sh` only ever invokes one `add-member`/`remove-member` per `docker compose exec` at a time (`deploy/compose/run.sh:89-94`), and operators are told to add `sleep 1` between loop iterations and never use `xargs -P` (`run.sh` help text, `:118-121`; `NOSTR.md:314-315`). This is a business rule enforced **only by operator discipline and documentation**, not by any lock in `buzz-admin` itself — contrast with the relay's own equivalent path, `Db::publish_nip43_membership_locked`, which *does* hold a Postgres advisory transaction lock across the whole read-build-write cycle (`crates/buzz-db/src/lib.rs:3498-3510`) and therefore has no such race. See `ops-misc-security.md` and `ops-misc-debt.md` for the consequences.

#### buzz-admin: reconcile-channels

1. Relay signing key resolution order: `--relay-key` flag → `BUZZ_RELAY_PRIVATE_KEY` env → freshly generated ephemeral key, with an explicit warning printed to stderr in the ephemeral case that events signed this way "won't be verifiable after this run" (`main.rs:465-479`).
2. Idempotency rule: for each channel, the command first queries for an existing kind:39000 event keyed by that channel's UUID as the `d` tag (`main.rs:487-497`); if found, the channel is skipped and counted separately (`skipped`, `main.rs:499-502`). This mirrors the relay's own internal reconciler (`reconcile_channel_events`, `crates/buzz-relay/src/handlers/side_effects.rs:2940-2999`), which uses the identical existence check (`side_effects.rs:2960-2971`) — the two implementations enforce the same idempotency rule independently, via duplicated (not shared) code. See `ops-misc-debt.md`.
3. Per-channel tag-building rules for the three emitted kinds (metadata/admins/members) are re-derivations of the relay's `emit_group_discovery_events` (`side_effects.rs:954-1050`) with **one silent divergence**: the relay's version additionally emits `topic`, `purpose`, `archived`, `ttl`, and `ttl_deadline` tags (`side_effects.rs:1004-1023`) and, for DM channels, embeds participant `p` tags directly into kind:39000 (`side_effects.rs:996-1002`); `buzz-admin`'s version has none of these — it emits only `d`/`name`/`about`/`private-or-public`/`hidden`(for dm)/`closed`/`t` (`main.rs:506-520`). A channel reconciled by `buzz-admin` therefore produces a **less complete** discovery event than one reconciled by the relay's own path for the same channel, even though both are "idempotent" in the narrow sense of "won't run twice." This is a real behavioral gap, not just a style difference — an operator who runs `buzz-admin reconcile-channels` on a DM channel gets a kind:39000 missing the participant `p` tags the relay would have included.
4. Unlike the relay's advertised NIP-70 protection convention used elsewhere in this same file for kind:13534 (`main.rs:353`, `["-"]` tag) and used by the relay's own `emit_addressable_discovery_event` implicitly through `replace_addressable_event`'s locking (not a `["-"]` tag there, since 39000/39001/39002 are not marked protected anywhere in either implementation) — neither `buzz-admin`'s nor the relay's version of the 39000/39001/39002 emitters adds a `["-"]` tag. This is consistent between the two, so it is not a divergence, just worth noting for completeness: these NIP-29 discovery kinds are not NIP-70-protected in either code path.
5. No transaction wraps the three `replace_addressable_event` calls per channel (`main.rs:521-576`) — a crash or error between the 39000 write and the 39001/39002 writes can leave a channel with a subset of its discovery events. There is no rollback or retry-on-partial-failure logic.
6. Summary counts (`reconciled`, `skipped`, total) are printed but the command does not fail (non-zero exit) if individual per-channel operations error — every `?` inside the per-channel loop propagates immediately via `anyhow::Result<()>` at the function level (`main.rs:461`), so the **first** error aborts the whole run and any channels processed before it keep their partial state; there is no "continue on error, report failures at the end" behavior, unlike the relay's own reconciler which logs-and-continues per channel (`side_effects.rs:2972-2986`).

#### buzz-admin: migrate, generate-key, product-feedback list

- `migrate` is a direct, unconditional call to `db.migrate()` (`main.rs:139-143`) with no dry-run, no confirmation prompt, and no check for whether migrations are already applied (idempotency is delegated entirely to `sqlx`'s migration runner). No business rule beyond "run whatever is pending."
- `generate-key` has no business logic — it calls `nostr::Keys::generate()` and prints both keys plus a hint to set `BUZZ_PRIVATE_KEY` (`main.rs:132-138`). It does not persist the key anywhere or register it as a relay member.
- `product-feedback list` clamps `--limit` to `1..=1000` at the `clap` parser level (`main.rs:103`, defaulting to 100) and otherwise applies no additional filtering — it returns feedback **across every community in the deployment**, not scoped to the tenant resolved from `RELAY_URL` (confirmed: `cmd_list_product_feedback` never calls `resolve_admin_tenant`, `main.rs:253-258`, and the underlying `product_feedback::list` query has no `community_id` predicate at all, `crates/buzz-db/src/product_feedback.rs:89-96`). This is a deliberate deployment-wide (not tenant-scoped) query, consistent with the subcommand's own doc comment "Inspect deployment-wide Buzz product feedback" (`main.rs:79`) and the table comment "deployment product inbox; community_id is provenance only" (`migrations/0017_product_feedback.sql:23-24`) — not a bug, but worth flagging because every other subcommand in this file *is* tenant-scoped.

#### sprig: dispatch rule

The entire business rule is: lowercase `argv[0]`'s basename, then match against exactly `"buzz-acp"`, `"buzz-agent"`, `"sprig"`, else fall through to `buzz-dev-mcp` (`crates/sprig/src/main.rs:16-42`, table in `ops-misc-api-surface.md`). There is no allowlist/denylist, no signature check on the binary path, and no distinction between "recognized alias I should refuse" and "unrecognized name" — every name that is not one of the three literals is treated identically: hand off to `buzz_dev_mcp::run()`. The only place an explicit *error* is produced is inside the `"sprig"` arm itself (direct invocation with no symlink and no args: `"error: invoke Sprig via a personality symlink"`, `main.rs:27`; or an unrecognized option to `sprig` itself: `"error: unknown Sprig option or personality: {other}"`, `main.rs:34-36`). Invoking the binary as anything else — including typos, or names like `rm`, `curl`, etc. — silently starts the developer MCP server (or one of *its* sub-dispatches) rather than erroring. See `ops-misc-security.md` for why this matters.

#### countdown-bot: command grammar and reply logic

1. Two trigger grammars, tried in order (`event_reply`, `main.rs:252-256`):
   - **Prefix command**: first whitespace token is exactly `!countdown` or `!fib`, second token is the argument (`command_reply`, `main.rs:258-268`). Any other first token yields no reply.
   - **Mention command**: only checked if the first grammar didn't match, and only if the event has a `p`-tag equal to the bot's own pubkey (`event_mentions_bot`, `main.rs:279-286`); then scans all adjacent 2-token windows in the content for `["countdown", n]` or `["fib", n]` (`mention_command_reply`, `main.rs:270-277`). Both `p`-tag presence AND the phrase are required — text alone (e.g. `"fib 8"` with no `@mention` and no p-tag) does not trigger the mention path, matching the README's explicit note that "Mention commands require both text ... and a `p` tag" (`examples/countdown-bot/README.md`, Notes section).
2. Both `n` arguments are bounded to `1..=100` inclusive (`parse_bounded`, `main.rs:311-320`); out-of-range or non-numeric input produces a fixed help string rather than silence or an error frame — the bot always replies to a recognized command word, even on bad input.
3. `!countdown N` counts down `N..=1` then appends `🚀` (`countdown_reply`, `main.rs:288-298`). `!fib N` computes the first `N` Fibonacci numbers ascending then **reverses** them before joining (`fib_reply`+`fibonacci_countdown`, `main.rs:300-330`) — i.e. it always prints descending order regardless of how many terms, by design ("this example is a countdown bot", README Notes section).
4. The bot never replies to its own messages, and ignores any event timestamped before the bot's own startup time (`maybe_reply`, `main.rs:226-229`, comparing against `started_at` captured once in `main()` at `main.rs:46`) — this prevents both feedback loops and replaying old messages on reconnect/restart.
5. Auth-mode business rule: `BUZZ_BOT_AUTH_MODE` must be exactly `"standalone"` or `"owner-attested"`; any other value is a hard startup error (`Config::from_env`, `main.rs:107-109`). In `"owner-attested"` mode, the code prefers a precomputed `BUZZ_AUTH_TAG` if it is set and non-blank, and only falls back to computing a fresh tag from `BUZZ_OWNER_PRIVATE_KEY` if the env var is unset or blank (`main.rs:95-102`) — this precedence is enforced by code, not just documented.
6. Channel self-add (`announce_channel_membership`) is explicitly best-effort: a rejection (e.g. on a private channel where the bot isn't pre-authorized) is caught and logged as informational, not propagated as a startup failure (`main.rs:181-189`) — the bot continues running and subscribing even if it couldn't announce itself as a channel member.

All of the above are enforced purely in application code with no external validation; there is no server-side rule in the relay that specifically recognizes "this is the countdown-bot" — from the relay's perspective it's an ordinary authenticated Nostr client publishing ordinary event kinds.

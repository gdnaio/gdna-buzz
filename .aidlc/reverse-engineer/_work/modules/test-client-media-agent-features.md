## Module: buzz-test-client — media, managed-agent, mesh-LLM & persona E2E (`crates/buzz-test-client/tests`)
### Aspect: Features

From an external reader's perspective — someone who has never seen the relay's internals — this is what each file collectively proves the product can do.

#### Media upload and retrieval (Blossom protocol)

Across `e2e_media.rs` and `e2e_media_extended.rs`: a user or agent can upload an image (JPEG, PNG, GIF, WebP) to the relay using a self-signed Blossom authorization event, get back a stable content-addressed URL, and retrieve the exact bytes later via plain HTTP GET/HEAD — including a thumbnail variant (`e2e_media.rs:174-182`). Uploads are idempotent and safe under concurrency: two people uploading the same file get the same URL (`e2e_media.rs:186-224`, `e2e_media_extended.rs:495-521`). The upload endpoint also accepts arbitrary non-media files (PDF, generic binary) as file attachments, while a separate legacy endpoint is deliberately narrower and only accepts image/video (`e2e_media_extended.rs:420-455`) — so the product supports both "post an image" and "attach a file" as distinct capabilities with different acceptance rules. Unauthorized or malformed upload attempts are cleanly rejected (401) rather than silently accepted or crashing.

Messages posted to a channel can reference an uploaded image via a structured `imeta` tag, and the relay validates that the reference actually points at media hosted on the relay itself rather than an arbitrary external URL (`e2e_media_extended.rs:522-712`) — this is the feature that prevents a chat message from linking out to attacker-controlled content while claiming to be an in-relay attachment.

#### Video upload and streaming playback

`e2e_media_video.rs` proves the product can host video, not just images: a user can upload an MP4 through the same Blossom flow, and the relay correctly identifies it as video regardless of what content-type header the client claims (`:280-321`) — so a mislabeled upload still gets stored and served correctly. Crucially, video playback supports HTTP range requests (`:322-364`), which is the feature that makes browser/native video players able to seek and stream rather than downloading the whole file first. A message can carry both a video and a distinct poster/thumbnail image, and the product enforces that the poster must actually be an image, not the video file reused as its own poster (`:567-645`) — protecting the chat UI from rendering a broken thumbnail.

#### Managed AI agents as durable, discoverable relay objects

`e2e_managed_agent.rs` proves that a configured AI agent (name, system prompt, model, provider, who it responds to) can be published to the relay as a first-class, queryable object addressed by the agent's own public key — and that this object updates in place (publishing a new version supersedes the old one) and can be permanently removed (a single delete event un-publishes it). It also proves a safety property end users care about: the agent's public definition never carries its private key, auth tokens, environment variables, or internal runtime state (`:186-263`) — so anyone who can read an agent's public profile cannot extract secrets from it, even though the underlying config object on the agent owner's machine does contain those secrets.

#### Shared compute (mesh LLM) — membership-gated discovery and live inference

`e2e_mesh_llm.rs` describes (and partially proves) a "shared compute" feature: desktop users in the same relay-backed community can share GPU/LLM capacity with each other. A member can see who on the mesh is offering compute and how to reach them, without exposing filesystem paths or secret keys (`:92-171`); someone who is not a member of the relay cannot see any of this (`:174-217`). When two peers are actually connected through a mesh, one peer's agent can send a chat completion that gets served by the other peer's model (`:219-268`) — the promise being "borrow a friend's GPU transparently through your usual chat interface." Only the discovery/visibility half of this feature is verified by default; the actual cross-machine inference and multi-node model-splitting halves are documented, runnable-on-demand acceptance tests that require real hardware and are not proven by any automated run in this repository (see Integrations and Debt).

#### AI personas — reusable, shareable agent blueprints with fine-grained visibility

`e2e_persona.rs` proves the product's largest single feature surface in this group: a user can define an agent "persona" (a named, versioned configuration blob) once and reuse it, personas can be updated in place with old versions cleanly retired, and slugs are validated so persona names stay predictable and URL/identifier-safe (`:381-561`). The standout capability is **selective sharing**: a persona is private to its creator by default, and the creator can flip a single flag to make it visible to everyone else on the relay — and this sharing/unsharing takes effect consistently everywhere a client might ask (a one-time query, a live "tell me when something changes" subscription, a count, and both the WebSocket and plain-HTTP APIs) (`:622-1234`). This is the feature that lets a workspace curate which agent personas are "public" building blocks versus personal experiments, with the relay itself enforcing the boundary rather than trusting every client to filter correctly. A companion set of tests proves this sharing boundary holds correctly even under pagination pressure — a shared persona doesn't get crowded off the first page of results by newer private ones (`:1410-1554`).

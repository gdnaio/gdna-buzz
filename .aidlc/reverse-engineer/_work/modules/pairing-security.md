## Module: buzz-pair-relay & buzz-pairing-cli (`crates/buzz-pair-relay`, `crates/buzz-pairing-cli`)
### Aspect: Security

#### Third-party observation/hijacking of the pairing exchange

The relay itself never sees plaintext: every `kind:24134` event's `content` is NIP-44-v2 ciphertext produced by `build_event` (`crates/buzz-core/src/pairing/session.rs:568-573`), and `buzz-pair-relay` only structurally sanity-checks that ciphertext's shape (`validate_nip44_content`, `crates/buzz-pair-relay/src/lib.rs:343-411`) without ever decrypting it — it has no access to either party's private key. This matches the module doc's claim "No persistence. No auth. No history." (`lib.rs:1-4`) for the relay's own knowledge, but the actual anti-hijacking defense is layered, not relay-provided:

1. **`p`-tag scoping** limits delivery to whichever single connection currently holds the live subscription for that exact 32-byte value (`deliver_single`, `lib.rs:160-210`) — a third party would need to guess or intercept the recipient's ephemeral pubkey to even receive the ciphertext.
2. **Session-secret possession proof** (the `session_id` check in `handle_offer`, `session.rs:171-177`) prevents a party who only observed relay traffic — not the QR code — from completing a valid offer, since `session_id` is derived from a secret that never appears on the wire in cleartext or in any form recoverable from ciphertext alone.
3. **SAS visual comparison** is the actual, spec-acknowledged MITM defense (see Business Rules) — an attacker who races the legitimate target to submit an `offer` causes the source to compute a *different* SAS code (its ephemeral pubkey differs), which a human is expected to notice and reject. This is a **procedural/human control**, not a cryptographic impossibility — the code cannot enforce that the user actually looks at both screens; it can only refuse to proceed past `Confirming`/`AwaitingConfirmation` until the CLI's `read_yes_no()` returns `true` (`crates/buzz-pairing-cli/src/main.rs:161`, `main.rs:291`).

#### Out-of-band code entropy

The QR-encoded `session_secret` is 32 bytes of CSPRNG output (`rand::fill`, `session.rs:114`) — 256 bits, far beyond brute-force range. The **user-facing** verification code (the SAS) is intentionally much shorter: 6 decimal digits, `sas_code = be_u32(sas_input[0..4]) % 1_000_000` (`crypto.rs:70-75`), i.e. ~19.9 bits of entropy. This is a deliberate, spec-documented tradeoff (`NIP-AB.md` §Design Rationale, "Why 6-digit decimal SAS?") — the SAS only needs to resist a single real-time race attempt per session (bounded by the 120s session timeout and the single-offer-acceptance rule), not offline brute force, since it is never transmitted or stored; it exists only to be visually compared once. No test in this module group exercises actual SAS-collision resistance statistically — the relevant guarantee is argued analytically in the spec doc, not empirically verified here.

#### Session-token unguessability

The "session token" in this protocol is really the **ephemeral pubkey** used as the `#p` filter/tag value — a fresh secp256k1 public key generated per session (`Keys::generate()`, `session.rs:113`, `287`). This is unguessable by construction (a uniformly random 256-bit curve point) and never reused across sessions. `buzz-pair-relay` adds no additional session-token concept of its own — it routes purely by whatever 64-hex-char value appears in `#p`, so the "unguessability" of the routing key is entirely a property of `buzz-core::pairing`'s key generation, not of the relay.

#### TLS requirements

Neither crate enforces TLS in code. `buzz-pair-relay` binds a plain `TcpListener` (`crates/buzz-pair-relay/src/main.rs:17-19`) with no TLS acceptor anywhere in its dependency tree (no `rustls`/`native-tls`/`tokio-rustls` in `Cargo.toml:18-30`) — the module doc is explicit that this is intentional and delegated: "This binary binds **loopback only** and MUST run behind a reverse proxy... that: ... Terminates TLS" (`lib.rs:8-13`). This is a reasonable, documented deployment-time constraint for a sidecar, but it is **not enforced by the binary itself** — nothing in `main.rs` checks or warns if `BUZZ_PAIR_RELAY_BIND_ADDR` is set to a non-loopback address (it happily binds `0.0.0.0:5000` if configured that way), and the Helm chart does exactly this: `value: "0.0.0.0:{{ .Values.pairingRelay.service.port }}"` (`deploy/charts/buzz/templates/pairing-relay.yaml:37-38`) — the shipped Kubernetes deployment sets a bind address the code's own doc comment says it "MUST" avoid, relying entirely on the Service/network layer for loopback-equivalent isolation.

`buzz-pairing-cli` connects to whatever scheme the `--relay`/QR URL specifies (`ws://` or `wss://`), with no enforcement that production use requires `wss://` — `qr.rs`'s validator accepts either scheme equally (`qr.rs:227-230`, `"wss" | "ws" => {}`), so a downgraded QR URI (`ws://` instead of `wss://`) is silently accepted by the decoder. The confidentiality of the payload does not depend on transport TLS (NIP-44 encryption is end-to-end regardless of transport), but metadata — timing, connection patterns, and the fact that pairing is happening at all — would be exposed to network observers on a plain `ws://` link. This is consistent with `NIP-AB.md`'s own "No relay confidentiality" limitation, but the code does not nudge users away from `ws://` in any way (no warning printed by the CLI when the relay URL scheme is `ws://`).

#### Replay protection

Two independent layers are present in this module group:

1. **Relay-level dedup**: `buzz-pair-relay` rejects any event whose 32-byte `id` has already been seen, via `reserve_id`/`unreserve_id` on `seen_ids: Vec<([u8;32], Instant)>` (`lib.rs:135-155`), checked *after* signature verification per "Tightening #7" (comment at `lib.rs:811`) — the ordering is deliberate so an attacker can't use a dedup-rejection response as a free oracle for whether an ID exists without also forging a valid signature. Entries expire after `ENTRY_TTL = 300s` (`lib.rs:86`), and the structure fails closed (rejects new IDs) once at `DEDUP_CAP = 1024` even after eviction (`lib.rs:143-145`) rather than silently overwriting old entries — a deliberate fail-closed choice per its own doc comment (`lib.rs:77-78`).
2. **Session-level dedup + cryptographic binding**: `buzz-core::pairing::session`'s `processed_ids: HashSet<[u8;32]>` (`session.rs:100-102`) catches redelivery within a session, and — independent of any explicit ID tracking — a replayed event from a *different* session cannot decrypt under the current session's ephemeral keys (NIP-44 conversation-key binding) and would also fail the `p`-tag-matches-my-ephemeral-pubkey check (`validate_event_basics`, `session.rs:631-663`), since a different session uses entirely different ephemeral keys. `NIP-AB.md`'s own §Replay Protection frames these two mechanisms (`p`-tag binding, NIP-44 key binding) as independently sufficient, with ID-based dedup as defense-in-depth — the code matches this framing.

Freshness is a third, related control: `buzz-pair-relay` rejects any event whose `created_at` is more than `FRESHNESS_SECS = 120` seconds from the relay's wall clock in either direction (`validate_event`, `lib.rs:453-460`, using the constant declared at `lib.rs:89`) — this bounds how old a captured-and-replayed (but still validly signed and not-yet-deduped, e.g. post-TTL-eviction) event could be before the relay refuses it, independent of the in-memory dedup set's own 300s TTL.

#### Does "ephemeral" hold up? What persists that shouldn't

Within `buzz-pair-relay`, the "ephemeral" claim holds up structurally: no field of `Relay` is written to disk, a database, or any external store (confirmed via `Cargo.toml` — no storage dependency exists to write to), and every in-memory structure (`subs`, `seen_ids`, `delivered`) is scoped to the process lifetime with TTL-based eviction on top. A pod restart or crash discards everything instantly and completely.

Within `buzz-core::pairing::session::PairingSession`, "ephemeral" is enforced defensively via `zeroize` on `Drop` for `session_secret`, `session_id`, and `sas_input` (`session.rs:731-738`), and the ECDH shared secret is explicitly zeroized immediately after use in both `handle_offer` (`session.rs:187`) and `new_target` (`session.rs:291`) rather than waiting for `Drop`. The one **documented, acknowledged gap** is in `build_event`'s own doc comment (`session.rs:544-558`): the serialized JSON plaintext is explicitly zeroized after encryption (`plaintext.zeroize()`, `session.rs:576`), but the doc comment concedes two residual copies cannot be zeroized — `serde_json::to_string`'s intermediate allocator buffers, and `nip44::encrypt`'s internal copy of the plaintext it reads — because both are inside third-party/allocator internals the crate doesn't control. This is honestly disclosed rather than silently ignored, which is a point in the implementation's favor, but it means the "nothing sensitive survives in memory" claim is best-effort, not an absolute guarantee, and this analysis cannot independently verify actual runtime memory contents to confirm or refute the residual-copy claim.

`buzz-pairing-cli`'s own secret handling: the resolved payload is wrapped in `Zeroizing<String>` from the moment it's read (`resolve_payload`, `main.rs:589`, `596`), and `send_payload`'s internal clone inside `PairingMessage::Payload` is explicitly zeroized after the call regardless of success or failure (`session.rs:227-251`, a deferred-`?` pattern specifically to guarantee this). One notable **non-gap that looks like a gap at first glance**: the CLI prints the QR URI (embedding the raw `session_secret` in hex) directly to stdout (`main.rs:126-127`) — this is not a bug, it's the intended mechanism (the whole point is for a human or camera to read it), but it does mean the secret transits the terminal's scrollback/history for the lifetime of that terminal session, outside this code's control and not called out beyond "do not share beyond the target device" (`main.rs:125`).

#### Rate limiting / abuse controls on session creation

`buzz-pair-relay` enforces only **connection-and-transport-level** limits, not pairing-session-level ones: `MAX_CONNS = 128` global concurrent WebSocket connections (`lib.rs:61`, enforced at `lib.rs:950-955`), `RATE_MSG_MAX = 20`/`RATE_EVENT_MAX = 10` per 10-second window *per connection* (`lib.rs:67-69`, `lib.rs:648-652`, `783-788`), and `MAX_EVENTS_PER_CONN = 6` as a hard lifetime cap per connection (`lib.rs:73`, `792-800`) — sized, per its own comment, to "enough for one full pairing from each direction" (`lib.rs:72`). There is no limit on how many *new* WebSocket connections a single IP or client can open in sequence — each fresh connection resets all the above counters, since they're stack-local to `handle_conn`, not attributed to any client identity (`lib.rs:625-633`) — and no limit at all on how many pairing sessions `buzz-core::pairing`/`buzz-pairing-cli` will let a process create. Abuse mitigation for connection *volume* is explicitly deferred to the reverse proxy layer, per the module doc: "Enforces HTTP read timeouts (mitigates slowloris at the TCP layer)" is listed as the proxy's job, not the relay's (`lib.rs:11`).

The per-`#p` delivery budget (`MAX_DELIVERED_PER_P = 12`, `lib.rs:76`, enforced inside `deliver_single`, `lib.rs:178-184`) is a targeted abuse control specifically against a compromised/malicious publisher trying to flood a single recipient's ephemeral key with events beyond what one pairing round needs — but it is scoped per-`p`-value, so an attacker generating many distinct `p`-tag values (each of which, per the single-live-subscriber-per-`#p` rule, would need its own subscriber to matter) gains nothing from this control alone; it is a resource-exhaustion cap, not an authentication or authorization control.

#### Uncertainty and what the test suite does not verify

The 1,393-line integration suite for `buzz-pair-relay` thoroughly exercises transport-level defenses (connection caps, rate limits, frame-size limits, timeouts, malformed-input handling, dedup, freshness — see Conventions/Debt for the itemized list) using **synthetic, minimally-shaped events**: `make_signed_event` (`tests/integration.rs:142-177`) constructs a real Schnorr-signed kind:24134 event with a real NIP-01 commitment hash, but its `content` field is a fabricated byte pattern that merely *passes the structural NIP-44 shape check* (`make_nip44_content`, `tests/integration.rs:130-137`: version byte `0x02` plus fixed filler bytes) — it is not a real NIP-44 ciphertext produced by `nip44::encrypt`, and it does not decode to any `PairingMessage`. **No test in this module group's own test suites exercises the full cryptographic pairing flow through `buzz-pair-relay`** — that end-to-end proof (real ECDH, real SAS derivation, real transcript-hash verification, real NIP-44 encrypt/decrypt) exists only in `buzz-core::pairing::session`'s own unit tests (e.g. `happy_path_full_protocol`, `session.rs:761-823`), which do **not** route events through any relay — `PairingSession` methods there are called directly, in-process, with no WebSocket, no `Relay`, no network I/O. This means "does the relay correctly ferry a real pairing session end-to-end" is not directly tested anywhere in this repository — it is tested in two disjoint halves (relay transport mechanics with fake payloads; protocol crypto correctness with no transport) that never meet in a single automated test. The manual/`expect`-driven E2E script referenced in `buzz-pairing-cli/README.md` (`.scratch/e2e-pair-local.sh`) would be the closest thing to that missing integration proof, but it is not present in the repository (confirmed by `file_search`) and cannot be run in CI.

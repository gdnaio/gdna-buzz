## Module: buzz-pair-relay & buzz-pairing-cli (`crates/buzz-pair-relay`, `crates/buzz-pairing-cli`)
### Aspect: Conventions

#### Error handling

`buzz-pair-relay` deliberately avoids a typed error enum for its protocol-validation paths — every validator returns `Result<T, &'static str>` (`validate_filter`, `lib.rs:312`; `validate_event`, `lib.rs:418`; `verify_event_sig`, `lib.rs:521`; `validate_nip44_content`, `lib.rs:343`; `deliver_single`, `lib.rs:160`; `reserve_id`, `lib.rs:135`), with the string literal doubling as the wire-facing rejection reason (e.g. `format!("error: {reason}")` at `lib.rs:737`, `format!("invalid: {reason}")` at `lib.rs:861`). This is a pragmatic, low-ceremony choice appropriate for a crate this size, but it means error variants aren't matchable — callers can only string-compare, which the integration suite does extensively (`resp[3].as_str().unwrap_or("").contains(...)`, repeated throughout `tests/integration.rs`). `buzz-pairing-cli`, by contrast, defines a conventional `thiserror`-derived `CliError` enum (`main.rs:74-97`) with `#[from]` conversions for `PairingError`, `tungstenite::Error`, `serde_json::Error`, and `io::Error` — the two crates in this group take opposite approaches to error typing, which is defensible given their different roles (a hot-path wire validator vs. a CLI with a handful of failure modes), but it is a visible convention split within one "module."

`buzz-core::pairing` sits in between: a proper `#[derive(Error)]` enum `PairingError` (`crates/buzz-core/src/pairing/mod.rs:34-79`) with semantic variants (`InvalidQr`, `InvalidSessionId`, `SasMismatch`, `TranscriptMismatch`, `UnexpectedMessage{expected,got}`, `SessionExpired`, `Nip44`, `Json`, `InvalidPubkey`, `SigningError`) that callers *can* match on — and `buzz-pairing-cli` exploits this in exactly two places where it matters: catching `PairingError::TranscriptMismatch` specifically to escalate to a security warning (`main.rs:271-284`) and matching on `UnexpectedMessage{ref got, ..}` containing `"success=false"` to distinguish target-reported failure from generic protocol noise (`main.rs:192-198`) — a string-matching-inside-an-enum-variant workaround because `PairingMessage::Complete{success:false}` doesn't get its own `PairingError` variant.

No `unwrap()`/`expect()` appears in either crate's non-test production code — confirmed by scanning both `lib.rs`/`main.rs`: the only `unwrap`-family calls live inside `#[cfg(test)]` modules or `tests/integration.rs` (e.g. `secp.generate_keypair(...).unwrap()`-style test helpers), consistent with `AGENTS.md`'s "Do not introduce new `unwrap()` or `expect()` in production paths" rule. `buzz-pair-relay`'s production code favors `unwrap_or`/`unwrap_or_else`/`?`/`match` throughout (e.g. the timestamp fallback at `lib.rs:452-456`, `.unwrap_or(0)`).

#### Logging

`buzz-pair-relay` logs exclusively via `eprintln!` — no `tracing`, despite the workspace pinning `tracing`/`tracing-subscriber` at the root (`Cargo.toml:66-67`) and every other server crate (`buzz-relay`, `buzz-auth`, etc.) using it. Log call sites: connection open/close (`lib.rs:970-974`, `lib.rs:230-234`), rate-limit hits (`lib.rs:649`), accept-loop and upgrade errors (`lib.rs:1006`, `lib.rs:990`), and the startup banner (`lib.rs:1001-1003`). This is a deliberate minimality choice consistent with the crate's "as few dependencies as needed" posture (no `tracing` in `Cargo.toml:18-30`), but it is inconsistent with the rest of the workspace's observability conventions: the connection-open/close lines print raw `conn_id`/`active` counts with no request-id correlation, no log level, and no way to filter via `RUST_LOG` (the pattern the rest of the repo relies on — e.g. `deploy/compose/.env.example:21`'s `RUST_LOG=buzz_relay=info,...` has no `buzz_pair_relay=` equivalent because `eprintln!` never touches the `tracing` filter at all).

`buzz-pairing-cli` similarly uses plain `println!`/`eprintln!` for all user-facing output — appropriate for an interactive terminal tool, unlike the relay's case.

#### Unsafe code and lint posture

Neither crate contains `unsafe` blocks — confirmed by scanning both `lib.rs`/`main.rs` for the keyword (zero occurrences). `buzz-core`'s crate root enforces `#![deny(unsafe_code)]` and `#![warn(missing_docs)]` (`crates/buzz-core/src/lib.rs:1-2`), which governs the `pairing` module's public API surface too (every `pub` item in `session.rs`/`crypto.rs`/`qr.rs`/`types.rs`/`mod.rs` carries a doc comment, consistent with the `missing_docs` warning). **Neither `buzz-pair-relay/src/lib.rs` nor `buzz-pairing-cli/src/main.rs` declares an equivalent `#![deny(unsafe_code)]` or `#![warn(missing_docs)]` at the crate root** — a real gap in these two crates specifically: `buzz-pair-relay`'s `pub struct Relay` and its `pub fn new()`/`run_server` are documented (doc comments present at `lib.rs:104`, `120`, `999`), but nothing *enforces* that discipline the way `buzz-core`'s lint attribute does. `AGENTS.md`'s workspace-wide rule "No `unsafe` code" is currently satisfied by omission, not by a compiler gate, in these two crates.

#### File-size and function-size discipline

`buzz-pair-relay/src/lib.rs` is 1,025 lines in a single file with no submodules — every constant, `Relay`, `Sub`, `ConnGuard`, `RateWindow`, all validators, `handle_conn`, `http_service`, and `run_server` live in one flat namespace. `handle_conn` alone spans `lib.rs:620-909` (~290 lines), driven by one large `match verb.as_str()` with deeply nested `match`/`if let` chains, particularly in the `EVENT` branch (`lib.rs:771-864`, ~94 lines for one match arm). This is large for a single function by most conventions, though it is a state machine over WebSocket frames — splitting the match arms into separate functions would require threading 6+ pieces of connection-local mutable state (`sub_id`, `events_attempted`, `msg_rate`, `event_rate`, `tx`, `relay`) through new signatures, a defensible tradeoff, but the function has no doc comment explaining its overall shape, only inline `//` comments at decision points.

`buzz-pairing-cli/src/main.rs` is 623 lines, also a single file, but reads as more decomposed: `cmd_source`/`cmd_target` (`main.rs:114-201`, `203-333`) are each roughly 90-130 lines with a clear linear narrative (connect → subscribe → wait EOSE → loop-until-message → confirm → send → wait-complete), and shared helpers (`publish_event`, `wait_for_event`, `wait_for_eose`, `parse_relay_event`, `parse_auth_challenge`) are each under 25 lines. Neither file approaches the mobile app's documented 1,000-line/file ceiling (`AGENTS.md`'s mobile section) — that guard is Flutter-specific and does not apply to Rust crates in this repo, and no equivalent Rust file-size lint was found for `crates/`.

#### Doc-comment discipline

Both crates are well-documented at the item level: every `const`, every public function, and most private helpers in `buzz-pair-relay/src/lib.rs` carry a `///` doc comment explaining intent (e.g. the elaborate module-level security-model doc at `lib.rs:1-27`, or the step-by-step doc on `verify_event_sig`, `lib.rs:513-520`). `buzz-pairing-cli/src/main.rs` documents its module purpose and usage pattern at the top (`main.rs:1-13`) and gives most functions at least a one-line doc comment. This is markedly better doc coverage than the missing crate-root lint enforcement (above) would suggest — the discipline exists in practice, it's just not compiler-enforced in these two crates specifically.

#### Test organization — and the 1,393-vs-1,025-line ratio

`buzz-pair-relay` has **zero** unit tests inside `src/lib.rs` — no `#[cfg(test)]` block appears anywhere in that file (confirmed by search). All testing for this crate lives in the separate `tests/integration.rs`, which is 368 lines *longer* than the source it tests (1,393 vs 1,025). This inverts the typical Rust convention (small `#[cfg(test)] mod tests` blocks next to the code, occasionally supplemented by integration tests) — here the black-box integration suite *is* the entire test suite, with 51 `#[tokio::test]` functions (verified via `grep -c "async fn test_" tests/integration.rs` → 51), each spinning up a real `Relay` on a random port (`start_relay()`, `tests/integration.rs:32-38`) and driving it through real WebSocket connections via `tokio_tungstenite::connect_async`. See Debt for what this ratio does and doesn't imply about actual coverage, and Security for what the tests do and don't exercise cryptographically.

By contrast, `buzz-core::pairing::session` keeps the conventional pattern: an 18-test `#[cfg(test)] mod tests` block at the bottom of `session.rs` (`session.rs:756-1319`, ~560 of the file's 1,315 lines) alongside 755 lines of implementation — unit tests co-located with the code, not in a separate `tests/` directory. `buzz-pairing-cli` has **no tests of its own at all** — a search for `#[cfg(test)]`/`#[test]` in `crates/buzz-pairing-cli/` returns zero matches. Its correctness is exercised only indirectly, via `buzz-core::pairing`'s own unit tests plus the manual/`expect`-scripted `e2e-pair-local.sh` procedure described in its README (`crates/buzz-pairing-cli/README.md:80-88`) — a script that does not exist in the repository (confirmed: `file_search` for `e2e-pair-local.sh` returns zero results; it likely lived under the gitignored `.scratch/` directory per `.gitignore:27-28`, meaning the documented E2E procedure is not reproducible from a fresh checkout).

#### Naming and structural conventions

Both crates follow the workspace's general Rust naming conventions (`snake_case` functions, `SCREAMING_SNAKE_CASE` constants, `CamelCase` types) with no deviations found. `buzz-pair-relay` groups its security-hardening increments as numbered "Tightening #N" inline comments (`#1` through `#8`, e.g. `lib.rs:421`, `634`, `783`, `803`, `811`, `831`) referencing a design/review history not otherwise documented in this crate — there is no summary block, README, or changelog entry that enumerates all eight tightenings as a set, so a reader who encounters "#6" in isolation (`lib.rs:454`, the freshness-window check) has no in-crate index of the other seven.

No CLI flag overrides any of these four — they are environment-only. This is a smaller configuration surface than the flags table in `ops-misc-api-surface.md` might suggest; the two surfaces (per-subcommand flags vs. process-wide env vars) are independent and both must be satisfied for the member-management commands.

**Parsed-but-never-read / undocumented:** none found for `buzz-admin` specifically — all four env vars it reads are used at the read site with no dead branches. However, `RELAY_URL`'s *reuse* by `buzz-admin` for tenant resolution (as opposed to only the relay's own bind config) is not documented anywhere outside the source code's own comments (`main.rs:431-448`) — an operator reading `.env.example`'s comment on `RELAY_URL` ("Public WebSocket URL — used in NIP-42 auth challenges", `.env.example:48`) would have no reason to know that changing it also changes which community `buzz-admin` operates on. This is a real (if minor) documentation gap: `RELAY_URL` is a dual-purpose variable and only one purpose is documented.

**CLI flags** (see `ops-misc-api-surface.md` for the full table) are all documented via `clap`'s own `--help` derivation (doc comments on each field, `main.rs:44-105`), which is self-consistent by construction since `clap` generates `--help` text from those same doc comments.

#### sprig: configuration surface is argv only — no environment variables of its own

`sprig`'s `main.rs` contains no `std::env::var` calls at all (confirmed by inspection of the full 53-line file — only `std::env::args()` calls appear, at `main.rs:9,19,26`). It reads no configuration beyond `argv[0]` (dispatch key) and, only in the `"sprig"` direct-invocation arm, `argv[1]` (`-V`/`--version`/`-h`/`--help`, `main.rs:19-37`). All actual environment-variable configuration happens inside whichever of `buzz-acp`/`buzz-agent`/`buzz-dev-mcp` gets dispatched to — out of scope for this crate. The bundled release README (generated by `scripts/build-sprig.sh:143-166`) documents the *downstream* crates' env vars (`BUZZ_AGENT_PROVIDER`, `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `NOSTR_PRIVATE_KEY`, `BUZZ_PRIVATE_KEY`, `BUZZ_RELAY_URL`) for end-user convenience, but none of these are read by `sprig`'s own code.

Build-time configuration for `sprig` itself lives in `Cargo.toml`/CI, not runtime env vars:

| Setting | Value | Where |
|---|---|---|
| Independent versioning (`sprig-v*` tags, not the workspace version) | `version = "0.1.0"` | `crates/sprig/Cargo.toml:1-5` |
| Release build profile | `[profile.sprig]`: `opt-level = "z"`, `lto = "fat"`, `codegen-units = 1`, `panic = "abort"`, `strip = true` | root `Cargo.toml` (workspace-level `[profile.sprig]` block) |
| Release targets | `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl` | `.github/workflows/sprig.yml:34-38` |
| Release trigger | push to `main` (rolling `sprig-latest`) or tag `sprig-v*` (versioned) | `.github/workflows/sprig.yml:18-21` |

All six of `countdown-bot`'s own env vars are documented in its README with worked examples for both auth modes — this is the best-documented configuration surface of the three programs in this group. None of these six variables appear in the repo-root `.env.example` or `deploy/compose/.env.example` (confirmed: grepping the whole repo outside `examples/countdown-bot/` for `BUZZ_BOT_PRIVATE_KEY`, `BUZZ_BOT_AUTH_MODE`, `BUZZ_CHANNEL_ID` finds no hits beyond the example itself and one unrelated Python benchmark harness field name), which is reasonable since `countdown-bot` is a standalone example the operator runs separately from the main relay stack, not a service configured through the relay's own `.env`.

**Two relay-side variables `countdown-bot`'s README says are required for the owner-attested path to work, but which are configured on the relay, not on the bot:**

| Variable | Required value | Where documented |
|---|---|---|
| `BUZZ_REQUIRE_RELAY_MEMBERSHIP` | `true` (for closed relays) | README "Relay requirements for this path"; also `deploy/compose/.env.example:17` |
| `BUZZ_ALLOW_NIP_OA_AUTH` | `true` | README "Relay requirements for this path"; also `deploy/compose/.env.example:18` |

Both are genuinely documented in both places (the example's README and the production `.env.example`), so this is a correctly cross-referenced pair, not a gap.

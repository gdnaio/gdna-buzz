## Module: buzz-pair-relay & buzz-pairing-cli (`crates/buzz-pair-relay`, `crates/buzz-pairing-cli`)
### Aspect: Debt

#### Is NIP-AB documented anywhere outside AGENTS.md's one-line description? — Yes, extensively. This is the opposite of a debt finding.

Contrary to what a one-line `AGENTS.md` description might suggest, **NIP-AB is unusually thoroughly specified** for a repo-internal protocol: `crates/buzz-core/src/pairing/NIP-AB.md` is an 800+-line, NIP-style specification covering versioning, terminology, the full event/message schema, a step-by-step protocol walkthrough, normative pseudocode, a security-considerations section, design rationale, and a test-vector appendix. It is accompanied by `crates/buzz-core/src/pairing/NIP-AB.spthy`, a Tamarin formal-verification model whose proved lemmas (executability, SAS-gating, payload secrecy, MITM resistance, dual-consent buffering, etc.) are summarized in `NIP-AB.md`'s own §Formal Verification. `buzz-pairing-cli` additionally ships its own `README.md` documenting subcommands, quick-start, and a full local-relay E2E testing recipe. So: **the protocol itself is not underdocumented** — the opposite of the "zero specification documentation" scenario flagged as a possible finding. The real, narrower gap is architectural placement, not protocol documentation:

- **`ARCHITECTURE.md`** — the repo's system-design document — never mentions `buzz-pair-relay`, `buzz-pairing-cli`, NIP-AB, or pairing at all (confirmed: zero matches for "24134" or "sidecar" across the whole file, and it documents the main relay's HTTP surface, `AppState`, `ConnectionState`, and protocol constants in detail elsewhere). Root `README.md` does at least name both crates in its crate index ("**Git & pairing** — `git-sign-nostr` / `git-credential-nostr` ... `buzz-pair-relay` / `buzz-pairing-cli` (relay pairing)", `README.md:211`), so it isn't invisible at the top level — it's specifically the mid-level architecture doc that omits it.

#### Contradiction between code and docs: the "legacy `/pair` path" does not exist in buzz-relay

`desktop/src-tauri/src/commands/pairing.rs` defines a `PairingRelay::LegacyPath` variant (`pairing.rs:473-479`) and a `resolve_pairing_relay_url` function that constructs a URL by appending `/pair` to the main relay's own host (`pairing.rs:514-529`) when the main relay's NIP-11 document advertises NIP-43 but no dedicated `pairing_relay_url`. The Helm chart's own README repeats this framing — "Buzz clients connect directly to the dedicated endpoint" implies a fallback exists (`deploy/charts/buzz/README.md:66-68`), and the chart's `values.yaml` comment says "clients use it instead of the legacy same-host `/pair` convention" (`values.yaml:190-192`). **This route does not exist.** A full read of `crates/buzz-relay/src/router.rs` (the authoritative route table for the main relay) shows no `/pair` path anywhere, and a case-insensitive grep for "pair" across every file under `crates/buzz-relay/` returns zero matches. Any client that falls back to the `LegacyPath` branch would construct a URL the main relay will 404 on. Either this fallback was never implemented server-side, or it was removed from `buzz-relay` without updating the client-side/doc references that still describe it as a live convention — this analysis cannot determine which from the code alone, only that the two sides currently disagree.

#### Duplication: the NIP-44 envelope sanity-checker exists at least twice, arguably three times, with non-identical units

`validate_nip44_content` in this crate (`crates/buzz-pair-relay/src/lib.rs:343-411` — base64 alphabet check, ≥99-decoded-byte length check, `0x02` version-byte check) overlaps functionally with `buzz-core::observer::content_looks_like_nip44` (`crates/buzz-core/src/observer.rs:21-23`, `53-55`, using named constants `NIP44_MIN_CONTENT_LEN = 132`/`NIP44_MAX_CONTENT_LEN = 87_472`, both **base64-character-length** bounds) and with `buzz-relay::handlers::ingest::validate_engram_nip44_content` (`crates/buzz-relay/src/handlers/ingest.rs:1110-1160`+), which performs the identical base64-alphabet/≥99-decoded-byte/`0x02`-prefix logic as `buzz-pair-relay`'s version, byte-for-byte in structure (same variable names, same control flow), strongly suggesting one was copied from the other, though neither file's comments cross-reference the other. Because `buzz-pair-relay` deliberately does not depend on `buzz-core` (see Integrations), it cannot share `NIP44_MIN_CONTENT_LEN`/`NIP44_MAX_CONTENT_LEN` even if it wanted to — its own version instead expresses the minimum as `≥ 99` **decoded bytes** (`1 version + 32 nonce + 32 min ciphertext + 32 MAC + 2 padding`, comment at `lib.rs:340-341`), a different unit (decoded bytes vs. base64 character count) than `buzz-core::observer`'s `132`-character minimum. This makes it hard to verify by inspection alone that all validators would accept/reject the exact same set of inputs — a genuine correctness-adjacent duplication risk, not just a style nit.

#### Duplication: NIP-42 auth handshake and EOSE-wait logic reimplemented three times, with a confirmed timing drift

`buzz-pairing-cli::handle_nip42_auth`/`parse_auth_challenge`/`wait_for_eose` (`crates/buzz-pairing-cli/src/main.rs:416-478`, `480-488`, `529-558`) is structurally near-identical to `desktop/src-tauri/src/commands/pairing.rs`'s `handle_nip42_auth`/`parse_auth_challenge`/`wait_for_eose` (`pairing.rs:383-449`, `554-561`, `563-586`) — same 3s challenge-wait timeout, same 5s OK-wait timeout (verified: both read `Duration::from_secs(3)` and `Duration::from_secs(5)` at their respective call sites), same string-contains check for `"OK"` in the response. The mobile Dart implementation (`mobile/lib/features/pairing/pairing_socket.dart`) is a third, independent reimplementation of the same NIP-42 challenge/response choreography — `_desktopPairingAuthChallengeGrace = Duration(seconds: 3)` matches the Rust side, but `_pairingAuthOkTimeout = Duration(seconds: 8)` (`pairing_socket.dart:9-10`) does **not** match the Rust side's 5s OK-wait — a small but real, confirmed behavioral drift between three independently-maintained copies of what should be the same handshake. None of the three shares a common library for this: `buzz-ws-client` exists in the workspace specifically as (per `AGENTS.md`) the "Shared NIP-42 WebSocket client," but neither `buzz-pairing-cli` nor the desktop pairing command depends on it — confirmed absent from both `Cargo.toml`s (`crates/buzz-pairing-cli/Cargo.toml:14-24`, and no `buzz-ws-client`/`buzz_ws_client` reference anywhere in `desktop/src-tauri/Cargo.toml`). This is the single largest concrete duplication finding in this module group by line count and by risk — three independently-maintained copies of security-relevant handshake logic that have already drifted on a timeout value.

#### Stale/misleading doc comment: `CONN_TIMEOUT`'s `pub(crate)` visibility does not actually grant "test access"

`pub(crate) const CONN_TIMEOUT: Duration = Duration::from_secs(120);` carries the doc comment "Hard per-connection lifetime. `pub(crate)` for test access." (`crates/buzz-pair-relay/src/lib.rs:58-59`). `pub(crate)` visibility does **not** extend to `tests/integration.rs`, because Rust integration tests under `tests/` are compiled as a separate, external crate that can only see the library's `pub` (not `pub(crate)`) surface. Confirmed by reading the test that would need this constant, `test_120s_timeout` (`tests/integration.rs`, advances virtual time via `tokio::time::advance(Duration::from_secs(121))`): it hardcodes the literal `121` rather than referencing `CONN_TIMEOUT + 1`, i.e. the test does not and structurally cannot use the constant the doc comment claims it's exposed for. If `CONN_TIMEOUT` is ever changed, this test's hardcoded `121` (and its duplicate in `test_cancellation_immediate`) must be updated by hand, and nothing will fail to compile to remind whoever makes that change — a latent test-drift risk directly caused by the doc comment's incorrect premise.

#### Unused Cargo feature: clap's `env` feature

`crates/buzz-pairing-cli/Cargo.toml:19` enables `clap`'s `env` feature, but no `#[arg(env = "...")]` attribute exists anywhere in `main.rs`'s `Cli`/`Cmd` definitions (`main.rs:40-72`) — confirmed by inspecting every `#[arg(...)]` attribute in the file. This is compiled-in-but-unused: extra dependency surface and compile time for a capability the code never exercises. Minor, but a one-line fix either way (drop the feature, or use it).

#### Dependency version skew: two secp256k1 majors in the same dependency graph

The root `Cargo.lock` resolves **two** versions of `secp256k1`: `0.29.1` (pulled in transitively by the `nostr` crate that both `buzz-pairing-cli` and `buzz-core` depend on, confirmed at `Cargo.lock:7725-7726`) and `0.31.1` (the version `buzz-pair-relay` pins directly, `crates/buzz-pair-relay/Cargo.toml:28`, with `rand`/`std` features re-enabled in `[dev-dependencies]` at `Cargo.toml:34`; confirmed at `Cargo.lock:7736-7737`). This is exactly the situation `deny.toml`'s `[bans] multiple-versions = "warn"` (`deny.toml:90-91`) is designed to flag — it's a warning, not a CI-failing error, so it doesn't block merges, but it means `buzz-pair-relay`'s hand-rolled Schnorr verification (`verify_event_sig`, `lib.rs:521-555`) and `buzz-core`/`nostr`'s signature handling live on two independently-versioned copies of the same cryptographic library, which could in principle diverge in bugfix/security-patch timing. Given this module's whole security model rests on correct signature verification (`lib.rs:19-21`), a future `secp256k1` security advisory affecting only one of the two resolved versions would need to be checked against both dependency edges separately.

#### Documented-but-missing test tooling: e2e-pair-local.sh

`crates/buzz-pairing-cli/README.md:80-88` documents an automated local E2E script, `.scratch/e2e-pair-local.sh`, including its expected behavior and three configurable env vars (`RELAY_URL`, `TEST_TIMEOUT`, `SOURCE_CONFIRM_DELAY_MS`). This file does not exist in the repository — a `file_search` for `e2e-pair-local.sh` returns zero results. `.scratch/` is explicitly gitignored (`.gitignore:27-28`, "Scratch / working files (AI reviews, notes, drafts)"), so this script — if it was ever written — was never committed, meaning the README's "Run the E2E test" instructions are not reproducible from a fresh clone. This is the one documented reproduction path for actually validating the full cryptographic protocol against a live relay (see Security), and it is not available.

#### Untested critical path: no automated test drives real NIP-44/ECDH/SAS crypto through buzz-pair-relay

As detailed in Security: `buzz-pair-relay`'s 51-test integration suite uses synthetic filler bytes that merely satisfy the *structural* NIP-44 shape check (`make_nip44_content`, `tests/integration.rs:130-137`), never a real `nip44::encrypt` ciphertext; conversely, `buzz-core::pairing::session`'s unit tests exercise the real crypto end-to-end but entirely in-process, with no relay, no WebSocket, no network I/O. No test in this repository — as far as this analysis could determine — sends a genuine, fully-encrypted, real-key-derived pairing message *through* an actual `buzz-pair-relay` instance and asserts the receiving side decrypts it correctly. This gap is exactly where the missing `e2e-pair-local.sh` script would have lived.

#### CI coverage gap: the integration suite and the CLI are compiled/linted but never executed in CI

`buzz-pair-relay`'s `tests/integration.rs` and `buzz-pairing-cli`'s `main.rs` are type-checked and clippy-linted on every PR via `cargo clippy --workspace --all-targets -- -D warnings` (`Justfile:106-107`, the `rust-lint` CI job's `just clippy` step) — so a compile error or clippy violation in either crate does fail CI. However, **the 51 integration tests are never actually executed by any CI job**: `just test-unit` (the only Rust test step in the `unit-tests` CI job, `.github/workflows/ci.yml`'s `unit-tests` job) is scoped to `-p buzz-core -p buzz-auth --lib`, `-p buzz-db --lib`, `-p buzz-conformance`, and `-p buzz-push-gateway` only (`Justfile:275-296`) — `buzz-pair-relay` and `buzz-pairing-cli` are not among them. The other Rust-test-running CI jobs (`backend-integration`, `relay-e2e`) are likewise scoped to specific packages/binaries (`buzz-relay`, `buzz-test-client`, `git-credential-nostr`) that never mention `buzz-pair-relay` or `buzz-pairing-cli` by name — confirmed by grepping every `.github/workflows/*.yml` file for `buzz-pair-relay`/`buzz-pairing-cli`/`buzz-pair`: zero matches. The infra-free path that eventually would cover them — `just test` → `scripts/run-tests.sh all` → `run_integration_tests`'s `cargo test --test '*'` at the workspace root, a glob that would sweep in `buzz-pair-relay`'s `tests/integration.rs` — is never invoked from any workflow file either. **Practical effect**: this crate's entire, sizeable test suite (the one this analysis brief specifically flagged as unusually large relative to its source) currently only runs when a developer manually invokes `just test` or `cargo test -p buzz-pair-relay` locally; a regression caught only by that suite would not be caught by the standard CI gate. By contrast, `buzz-core::pairing`'s unit tests (session/crypto/qr/types) *do* run in CI via `just test-unit`'s `-p buzz-core --lib` step — so the crypto/state-machine core is CI-gated, but the relay-transport integration suite and the CLI (which has no tests at all) are not.

#### Zero tests for buzz-pairing-cli itself

No `#[test]`/`#[cfg(test)]` block exists anywhere in `crates/buzz-pairing-cli/` (confirmed by search). Functions with non-trivial logic and no direct test coverage include `resolve_payload` (bech32 nsec validation branch, `main.rs:581-599`), `parse_relay_event`/`parse_auth_challenge` (hand-rolled JSON-array message parsing, `main.rs:560-579`, `480-488`), and `check_for_abort` (the speculative-probe pattern that `buzz-core::pairing::session` has a dedicated regression test for on its own side, but whose *usage* by the CLI has no test). Given this crate has zero automated tests of its own, its correctness currently depends entirely on manual two-terminal runs plus the missing `e2e-pair-local.sh`.

#### Minor: unindexed "Tightening #N" comments

`buzz-pair-relay/src/lib.rs` references "Tightening #1" through at least "Tightening #8" as inline justifications for specific hardening decisions (`lib.rs:421`, `454`, `472`, `488`, `634`, `783`, `803`, `811`, `831`). No comment block, README, or changelog entry in this crate enumerates what all N tightenings are as a set — a reader who encounters "#6" in isolation (`lib.rs:454`, the freshness-window check) has no way to see the other seven without grepping the whole file. Low severity, but the kind of implicit tribal-knowledge comment a short summary block near the existing module-level security-model doc (`lib.rs:19-27`) would resolve cheaply.

#### Minor: `Relay::default()` is dead code

`impl Default for Relay` (`lib.rs:114-118`) delegates to `Relay::new()`, but nothing in either the crate or its test suite calls `Relay::default()` — every call site uses `Relay::new()` directly (`main.rs:24`, `tests/integration.rs:36`). Likely added to satisfy a `clippy::new_without_default` lint rather than for any functional need; harmless, but unused public API surface worth noting.

#### Oversized function (cross-reference to Conventions)

`handle_conn` (`lib.rs:620-909`, ~290 lines) is the single largest function in this module group and contains the entire message-dispatch state machine for one WebSocket connection in one `match` block. No file-size or function-size lint applies to Rust crates in this repo the way `mobile/scripts/check-file-sizes.mjs` applies to Flutter, so nothing flags this automatically; it is dense enough that a future contributor adding a ninth "tightening" would be editing an already-packed function.

## Module: buzz-test-client — content & git E2E (`crates/buzz-test-client/tests`)
### Aspect: Conventions

#### File size

| File | Lines | Relative to group |
|---|---|---|
| `e2e_long_form.rs` | 538 | smallest |
| `e2e_git.rs` | 475 | — |
| `e2e_human_edit_agent_content.rs` | 991 | large |
| `e2e_event_reminder.rs` | 1,178 | largest in this group, and largest of any single test file cited in this analysis |

`AGENTS.md`'s "Common Gotchas" §7 imposes a hard 1000-line ceiling on mobile Dart widget files, enforced by `mobile/scripts/check-file-sizes.mjs` via `just mobile-check`. No equivalent lint exists for Rust test files anywhere in `Justfile` (confirmed: no `check-file-size`-style recipe references `crates/` or `.rs`), so `e2e_event_reminder.rs` at 1,178 lines and `e2e_human_edit_agent_content.rs` at 991 lines are not flagged by any tooling, unlike an equivalently-sized mobile file would be. Both are large for a single `#[tokio::test]`-per-scenario integration file, but the size is substantially explained by the sheer count of near-identical scenarios (29 tests in the reminder file, 19 in the ownership file) rather than by any one function being unusually long — see Debt for whether that repetition itself is a maintainability cost.

#### Test naming

Three of the four files use a consistent `test_<subject>_<condition/verb>` naming scheme for every `#[tokio::test]` function: `test_long_form_accepted`, `test_reminder_rejected_duplicate_not_before`, `test_owner_can_edit_agent_message`, etc. (verified: `e2e_long_form.rs` 8/8, `e2e_event_reminder.rs` 29/29, `e2e_human_edit_agent_content.rs` 19/19 functions annotated `#[tokio::test]`/`#[ignore]` start with `test_`). `e2e_git.rs` breaks this convention: its two test functions are named `git_clone_push_fetch_force_roundtrip` and `git_concurrent_push_one_wins_and_repo_recovers` — no `test_` prefix, and the name reads as an action/scenario description rather than a `test_<subject>_<outcome>` assertion statement. This is a minor, cosmetic inconsistency (Rust's test harness does not care about the prefix), but it means a grep for `fn test_` across this group would miss `e2e_git.rs` entirely.

Naming otherwise carries real information in this group: `e2e_event_reminder.rs` suffixes tests with the transport they exercise (`_http`, `_ws`) when the same rule is checked over both surfaces (e.g. `test_author_can_query_own_reminders_http` vs `test_author_can_subscribe_to_own_reminders_ws`), which makes the read-path coverage table in Business Rules straightforward to reconstruct from names alone.

#### Section banners

`e2e_human_edit_agent_content.rs` uses seven `// ─── <Section> ───` banner comments (`:95`, `:223`, `:313`, `:404`, `:519`, `:630`, `:818`) to group its 19 tests by the kind under test (40003, 9005, kind:5, 9002, 9008) plus two dedicated regression sections ("Private-channel coverage (Fix 1 regression guard)", "Removed-author rejection tests (Option A regression guard)"). This is the only file in the group that uses this banner style; the other three rely purely on doc comments above each function and file ordering. The banners double as inline documentation of *why* a cluster of tests exists (naming the specific bug/fix each guards against), which is more informative than the plain `///` doc comments on most individual tests in the other files.

#### Doc-comment discipline

All four files carry a module-level `//!` doc comment describing scope and how to run the suite (`e2e_long_form.rs:1-19`, `e2e_event_reminder.rs:1-17`, `e2e_human_edit_agent_content.rs:1-19`, `e2e_git.rs:1-16`), each including a copy-pasteable `cargo test ... -- --ignored` invocation. Per-test `///` doc comments are present on nearly every test in three of the four files (29 in `e2e_long_form.rs`, 24 in `e2e_event_reminder.rs`, 27 in `e2e_human_edit_agent_content.rs` — counts include some multi-line comments spanning more than one `///` line, so these are not exactly "one comment per test," but every test observed during review had at least one line of doc above it). `e2e_git.rs` has only 6 `///`-style lines total — its two tests are documented by the *module*-level doc comment describing the overall scenario, plus in-line `//` comments at each numbered step (e.g. `:227` "1. Clone the empty repo.", `:236` "2. Push an initial commit.") rather than a per-test doc block, which fits its "one long scenario per test" shape better than a `///` summary would.

Several individual doc comments do more than describe *what* the test does — they explain *why* the test exists and name concrete prior bugs or design decisions, which is unusually good for e2e test comments: `test_long_form_a_tag_deletion`'s comment names "issue #714" and the specific prior no-op behavior (`e2e_long_form.rs:301-308`); `test_long_form_malformed_e_plus_a_does_not_delete` explains the exact routing-predicate hazard it guards ("keyed on 'no e tags present' rather than 'no valid e-ids decoded'", `:311-317`); `test_reminder_not_before_max_safe_integer_rejected_too_far_in_future`'s comment cites two separate line numbers in an external spec doc (`NIP-ER.md:60`, `:130`, `e2e_event_reminder.rs:789-791`) to justify why a structurally-valid value is still expected to be rejected; the private-channel and removed-author sections in `e2e_human_edit_agent_content.rs` each open with a multi-line comment explaining the exact prior bug shape ("Fix 1", "Option A") before the first test in the section.

#### Error handling and assertion style

None of the four files contain `unwrap_or_default`-style silent error swallowing on the *assertion* side — failures always come from `.expect("<message>")` (91 combined across three files, plus `e2e_git.rs`'s 8) or explicit `assert!`/`assert_eq!`/`assert_ne!` with a descriptive failure message that typically echoes back the server's own error string (e.g. `assert!(ok.accepted, "relay should accept kind:30023: {}", ok.message)`, a pattern repeated in some form at nearly every `send_event`/`submit_event_http` call site across all three non-git files). This means a CI failure's assertion message alone usually surfaces the *relay's* rejection reason, not just "assertion failed," which is good practice for diagnosing a flake vs. a real regression at a glance.

`e2e_git.rs` diverges structurally here too: its `git()` helper (`:95-105`) centralizes the "did the subprocess succeed" assertion once, dumping both `stdout` and `stderr` on failure (`:99-103`), rather than each call site repeating an `.expect(...)`. This is a reasonable adaptation to the subprocess-based nature of the file (there are far more git invocations than there would be sensible individual `.expect()` messages for), but it does mean a failure inside `git_status`-driven code (used only for the intentionally-racing pushes, `:394-403`) is *not* auto-asserted — those results are collected and checked manually afterward (`:405-421`), which is correct for that specific test (it expects most of the 8 to fail) but is a different failure-reporting shape from the rest of the file.

Three of the four files use `panic!("expected X, got: {other:?}")` in `match` fallthrough arms when asserting on an enum variant (`e2e_event_reminder.rs` 3 occurrences: `:661`, `:1053`, and inside a match at `:938`-adjacent code path; none in the other two Nostr-event files, which instead use `assert!`/`assert_eq!` throughout). `e2e_git.rs` also uses 3 `panic!`s, but inside its own helper functions (`GitS3Probe::pointer`/`require_pointer`/`assert_manifest_exists`, `:167`, `:181-184`, `:191`) rather than inline in test bodies — a slightly different idiom (panic-as-assertion inside a reusable probe vs. panic-as-fallthrough inside a `match`).

#### Lint attributes, `unsafe`, and crate-wide conventions

None of the four files carry any file-level `#![...]` attribute or any `#[allow(...)]` — confirmed by direct search (`grep -n '#!\[|#\[allow|clippy::'` across all four returns no matches). This means they inherit whatever lint configuration applies to the `buzz-test-client` package as a whole; the crate's `src/lib.rs` does declare `#![deny(unsafe_code)]` and `#![warn(missing_docs)]` (`lib.rs:1-2`), but those attributes are scoped to the library crate root and do not automatically extend to separate integration-test binaries under `tests/` (each file under `tests/` is compiled as its own crate root) — `missing_docs` in particular would not fire against test functions even if it did apply, since `#[test]`/`#[tokio::test]` functions are not part of any public API surface. No `unsafe` blocks appear in any of the four files. This is consistent with the repo-wide "No `unsafe` code" rule in `AGENTS.md`, though for these files the rule is moot rather than actively enforced by a visible attribute.

#### RAII / cleanup pattern

`e2e_git.rs` is the only file in this group managing real filesystem side effects (cloned working trees), and it does so with a small hand-rolled RAII guard: `struct TempDir(PathBuf)` with a `Drop` impl that best-effort `remove_dir_all`s the directory (`:454-472`), rather than depending on the `tempfile` crate or similar. `tempdir()`/`tempdir_named(prefix)` proactively remove any stale directory of the same name before creating it (`:467-471`) — defensive against a prior crashed run leaving debris, since directory names are keyed only by `std::process::id()` (`:468`), not a random suffix, so two same-PID runs (unlikely but possible across process-ID reuse) could collide. The other three files have no filesystem side effects to clean up at all — their only "teardown" is `client.disconnect()`, called via `.ok()` (ignoring the result) in most of `e2e_human_edit_agent_content.rs`'s teardown lines and via `.expect("disconnect")` in `e2e_long_form.rs`/`e2e_event_reminder.rs`. This is itself a minor inconsistency: `e2e_human_edit_agent_content.rs` almost uniformly writes `agent_client.disconnect().await.ok();` (ignoring disconnect failures), while the other two files `.expect()` the disconnect — meaning a disconnect-level transport error would fail the test in `e2e_long_form.rs`/`e2e_event_reminder.rs` but be silently swallowed in `e2e_human_edit_agent_content.rs`.

#### Logging

No file in this group uses `tracing` macros (`tracing::info!`, etc.) or `println!`/`eprintln!` for runtime narration — all four rely entirely on `--nocapture` (mentioned in `e2e_git.rs`'s doc comment, `:15`) plus assertion failure messages for diagnosability. This matches the harness's own use of `tracing::debug!` only at the connection layer (`lib.rs:100`), not inside individual test bodies — logging in this group is minimal by design, and every file's debuggability rests on descriptive `.expect()`/`assert!` messages rather than execution-trace logging.

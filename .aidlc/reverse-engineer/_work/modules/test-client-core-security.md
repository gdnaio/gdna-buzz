## Module: buzz-test-client — core protocol, status & team E2E (`crates/buzz-test-client`)
### Aspect: Security

Given the group's scope (core relay protocol, NIP-42 host-binding, and two smaller replaceable-event suites), security-relevant material is concentrated almost entirely in `e2e_relay.rs` and `nip42_host_binding_live.rs`. This aspect is organized around what is proven, what is only partially proven, and what is not tested at all.

#### Authentication boundary — thoroughly proven, with one loose assertion

`test_pubkey_mismatch_rejected` (`e2e_relay.rs:592-609`) and `test_auth_event_kind_rejected` (`:568-590`) together prove the two most basic identity-forgery vectors are closed: you cannot submit an event signed by a key other than the one that completed your connection's NIP-42 handshake, and you cannot smuggle a raw AUTH event through the ordinary EVENT path. Both are confirmed against `handlers/event.rs:658-660` and `handlers/ingest.rs:1465-1468` respectively.

`test_unauthenticated_rejected` (`:756-786`) is the weakest test in this cluster from a security-assurance standpoint: it accepts three different possible relay behaviors (`OK false`, `ConnectionClosed`, or `Timeout`) as all being "correct" (`:768-783`). The relay's actual behavior, confirmed at `handlers/event.rs:634-649`, is deterministic — it always replies `OK false "auth-required: not authenticated"` for a non-authenticated connection attempting to write. Because the test tolerates a strictly wider outcome space than the relay actually exhibits, a future regression where the relay silently drops unauthenticated writes (no `OK`, no close — a true hang) would pass this test under its `Timeout` branch, when that would actually be a meaningfully worse security posture (a client can no longer distinguish "denied" from "the network is slow"). This is the same shape of testing gap the sibling `test-client-media-agent-security.md` calls out generally in this crate: loose multi-branch assertions can hide a regression that a tighter assertion would catch.

#### Relay-only kind enforcement — proven on two independent transports simultaneously

`test_client_submitted_nip43_membership_snapshots_are_rejected` (`:216-244`) is the strongest single security proof in this group: it submits a forged kind:13534 (relay-signed-only membership snapshot) over **both** WebSocket EVENT and HTTP `POST /events`, from the same actor, and asserts identical rejection (`restricted: relay-only kind`) on both. The test first proves the same actor can submit an *ordinary* event successfully (`create_test_channel`), which rules out the alternative explanation "this actor just isn't authorized for anything." This directly proves `is_relay_only_kind` (`buzz-core/src/kind.rs:758-768`) is enforced identically regardless of transport — a real anti-spoofing property, since kind:13534 (the relay membership roster) being forgeable by any client would let an attacker inject fake membership state that other clients/agents might trust.

`test_membership_notification_kind_rejected` (`:1499-1524`) proves the identical property for kind:44100 (member-added notification) over WebSocket only — there is no equivalent HTTP-door test for this kind in this group, a minor asymmetry relative to the 13534 test's dual-transport rigor.

#### NIP-42 host-binding — the group's dedicated multi-tenant security proof

`nip42_host_binding_live.rs` exists purely to close a specific cross-tenant authentication-bypass vector: if the relay checked an AUTH event's `relay` tag against a single deployment-wide URL rather than the tenant the connection actually resolved to, an attacker could sign one AUTH event for host A and successfully authenticate a connection to host B (or vice versa), effectively laundering identity/authorization context across tenant boundaries. The two "cross-host rejected" tests (`:131-159`) are the actual security assertions; the two "matching-host accepted" tests exist specifically so those rejections can't be vacuously true (see Business Rules). This is a genuine multi-tenant isolation property, and the fact that it requires live two-host infrastructure and is `#[ignore]`d with an explicit reason string means it is very unlikely to run in ordinary CI — its assurance value depends entirely on someone manually running it (with `--test-threads=1`) as part of a deliberate security-regression check before a release that touches tenant resolution or NIP-42 verification. No automated CI job wiring for this file was found in this pass (see Configuration/Debt for the operational gap this implies).

#### Authorization layering (NIP-29 admin, private-channel roles) — proven per-layer, not proven as a composed whole

The `channel_add_policy` (nobody/owner_only/anyone) and private-channel membership/role tests (see Business Rules §6) each individually prove one authorization boundary holds. But no test in this group composes more than one layer at a time — e.g., no test checks whether a `"nobody"`-policy agent can still be added by a private-channel *member who is not the owner* attempting a third-party add (the self-add bypass and the nobody-policy block are each tested against a *public*-channel-style actor, not cross-matrixed against the private-channel membership gate). This isn't a proven bug, but it is a proven **gap**: the interaction surface between "who may invite" (private-channel membership) and "who may be invited" (agent's own `channel_add_policy`) when *both* gates are active simultaneously is untested by this group.

#### Membership-notification read-side isolation — six tests, comprehensive filter-shape coverage

The six `test_membership_notification_*` tests (Business Rules §7) are collectively a thorough proof that a client cannot use a REQ filter to surveil *other* users' membership add/remove events — every plausible filter-shape bypass attempt (`no #p`, `wildcard`, `someone else's #p`, `own + victim's #p together`, `mixed filters where a second filter widens scope`) is explicitly tried and rejected. This is meaningful information-disclosure prevention: membership add/remove events reveal which channels a pubkey is in, which is itself sensitive metadata in a private-channel model. The mixed-filter test in particular (`test_membership_notification_mixed_filter_rejected`, `:1569-1610`) proves the relay evaluates a subscription's effective OR-across-filters scope rather than gating each filter independently — closing a bypass class that a naive "check the first filter only" implementation would be vulnerable to.

#### What this group does NOT test

- **No COUNT-door coverage at all.** Despite the task framing's expectation that this group covers "EVENT/REQ/COUNT," zero tests in `e2e_relay.rs`, `e2e_user_status.rs`, `e2e_team.rs`, or `nip42_host_binding_live.rs` send a `["COUNT", ...]` frame or match `RelayMessage::Count`. Given that the membership-notification `#p`-filter gate (§7 above) is specifically about preventing REQ-based surveillance, and COUNT is a parallel read surface over the same filter grammar, this is a real coverage gap: nothing in this group proves the identical `#p`-filter restriction holds for `COUNT` on kind:44100/44101 (or any other gated kind), even though the crate's sibling `e2e_event_reminder.rs` proves exactly this pattern (WS COUNT gating) for a different kind. If the relay's COUNT handler and REQ handler ever drift in how they apply the membership-notification gate, no test in this group would catch it.
- **No rate-limit / admission-control testing.** `wamp-bench` is a load-generation *tool*, not a test — it reports latency and accept/reject counts but asserts nothing, and no test file in this group sends enough traffic to trigger the invite-claim rate limiter (`CLAIM_RATE_LIMIT = 10` per minute per pubkey, `api/invites.rs:38-40`) or any WS-level admission budget. `ARCHITECTURE.md`'s Known Limitations §9.2 already documents that `RateLimiter` has no real implementation beyond a test stub — this group's tests are consistent with that documented gap (they don't pretend to test something that doesn't exist), but it does mean the invite-claim limiter specifically (which *is* implemented, per `api/invites.rs:32-40`) has zero E2E proof of its actual enforcement behavior anywhere in this group.
- **No ban/moderation-cascade testing.** `handlers/auth.rs:105-180` implements a fairly involved ban-cascade check (direct ban, then NIP-OA-owner ban cascading to the agent) that runs before the allowlist and relay-membership gates on every NIP-42 auth. No test in this group establishes a ban and then attempts to connect — this entire gate is untested from this group's vantage point (it may be covered by a moderation-focused sibling group outside this analysis's scope).
- **No allowlist (`BUZZ_PUBKEY_ALLOWLIST`) testing.** The pubkey-allowlist gate (`auth.rs:189-207`) is likewise never exercised by any test in this group.

#### Test credentials — verified dev-only, no real secrets

`test_owner_keys()` (`e2e_relay.rs:46-50`) reads `BUZZ_TEST_OWNER_PRIVATE_KEY` and falls back to `Keys::generate()` if unset — the variable is never assigned a literal value inside the test file itself, and the repo's own `configuration.md` already classifies both `BUZZ_TEST_OWNER_PRIVATE_KEY` and `wamp_bench.rs`'s `BENCH_PRIVATE_KEY` as "sensitive: yes, test/benchmark identities, unset by default." Neither variable appears with an assigned value anywhere in `.env.example`, `deploy/compose/.env.example`, or any file under this group's scope — confirmed by grep across both env-example files and all eight files in this group. Every other identity in this group (`Keys::generate()` in `e2e_user_status.rs`, `e2e_team.rs`, `nip42_host_binding_live.rs`, `mention.rs`) is a fresh ephemeral keypair generated per test/invocation, never a hardcoded value. The one literal-looking cryptographic value in this group, the two-host relay URLs (`ws://a.localhost:3100`, `ws://b.localhost:3100` in `nip42_host_binding_live.rs:20-21`), are plainly local-development placeholder hostnames, not credentials.

`create_test_channel` and most of `e2e_relay.rs`'s `POST /events` calls authenticate via the `X-Pubkey` HTTP header — the relay's own documented dev-mode fallback (`api/bridge.rs:58-61,117-121`), active only when `require_auth_token` is false (the code default, confirmed at `config.rs:475-477`: `unwrap_or(false)`). This means the majority of this group's HTTP-door coverage implicitly assumes a dev-mode-auth relay posture; none of these tests would pass as written against a relay started with `BUZZ_REQUIRE_AUTH_TOKEN=true` (the documented production default in `deploy/compose/.env.example:14`), since the `X-Pubkey` header would simply be ignored and the request would need a real NIP-98 signature instead. Only the four invite-mint/claim tests in this group build and send a real NIP-98 header (`nip98_post_header`, `:60-72`) — everything else in this group's HTTP surface is dev-mode-only coverage, a distinction worth being explicit about since it means this group's HTTP-door assurance does not transfer to a hardened deployment without separately re-running (or rewriting) those tests against `BUZZ_REQUIRE_AUTH_TOKEN=true`.

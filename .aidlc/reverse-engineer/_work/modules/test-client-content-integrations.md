## Module: buzz-test-client — content & git E2E (`crates/buzz-test-client/tests`)
### Aspect: Integrations

#### What each file needs at runtime

| File | Live relay (WS) | Live relay (HTTP bridge) | Postgres/Redis (indirect, via relay) | S3/MinIO | Real `git` binary | `git-credential-nostr` binary |
|---|---|---|---|---|---|---|
| `e2e_long_form.rs` | yes (only transport used) | no | yes (relay needs it to run at all) | no | no | no |
| `e2e_event_reminder.rs` | yes (subscriptions, COUNT, recv) | yes (all writes/queries/counts go through `/events`, `/query`, `/count`) | yes | no | no | no |
| `e2e_human_edit_agent_content.rs` | yes (all message/admin events, NIP-OA auth) | yes (channel creation only, via `create_agent_owned_channel`/`create_private_agent_owned_channel`) | yes | no | no | no |
| `e2e_git.rs` | no (never imports `buzz_test_client`; talks HTTP + git only) | yes (`POST /events` for the kind:30617 announce, and implicitly `/git/{owner}/{repo}` for clone/push/fetch smart-HTTP) | yes | **yes, directly** (via `rust-s3`, independent of the relay's own S3 client) | **yes** (subprocess `Command::new("git")`) | **yes** (subprocess, invoked by `git` itself as `credential.helper`) |

This confirms and extends the prior analysis's claim: `e2e_git.rs` is the one file in this group with a materially heavier integration footprint — live relay **and** MinIO **and** a real `git` binary **and** a separately-built `git-credential-nostr` binary, versus the other three files needing only a live relay (which itself depends on Postgres+Redis, but that dependency is the relay's problem, not this test file's).

#### `e2e_long_form.rs`

Needs nothing beyond a running relay reachable at `RELAY_URL` (default `ws://localhost:3000`, `:29`). Every operation — send, subscribe, collect — goes through the shared `BuzzTestClient` WebSocket connection. No HTTP, no S3, no subprocess.

#### `e2e_event_reminder.rs`

Needs a running relay reachable at both its WebSocket URL (`RELAY_URL`, default `ws://localhost:3001` — note the different default port from the other three files, see Configuration) and its HTTP bridge, derived from the same env var by string-replacing the scheme (`relay_http_url`, `:32-38`). All write/query/count traffic goes through `reqwest::Client` hitting `/events`, `/query`, `/count` directly (bypassing the harness's WebSocket `send_event`/`subscribe` entirely for those operations) — only the WS-specific isolation tests (`test_author_can_subscribe_to_own_reminders_ws`, `test_other_user_subscription_closed_for_author_only_kind_ws`, `test_mixed_kind_filter_omits_other_authors_reminders_ws`, `test_fanout_isolation_other_user_does_not_receive_reminder`, `test_ws_search_isolation_other_user_cannot_find_reminder`, `test_ws_count_returns_zero_for_other_users_reminders`) use `BuzzTestClient`. The scheduler-delivery test additionally depends on the relay's background scheduler task actually running with a short poll interval — the doc comment (`:16`, `:1132-1133`) states the CI/local relay must be started with `SPROUT_REMINDER_SCHEDULER_INTERVAL_SECS=1`; this is set in the `backend-integration` CI job (`.github/workflows/ci.yml:500`) and in `scripts/start-relay-for-tests.sh:161` — no test in this file starts or configures the relay itself, it is purely a client of an externally-managed relay process.

One test (`test_mixed_kind_filter_omits_other_authors_reminders_ws`, `:679-764`) also creates a real channel via a direct kind:9007 HTTP POST (`:687-706`) purely as scaffolding to get a kind:9 message onto the wire for the mixed-kind-filter assertion — this is incidental channel-feature usage, not a dependency on channel-specific relay code paths.

#### `e2e_human_edit_agent_content.rs`

Needs a running relay at `RELAY_URL` (default `ws://localhost:3000`, matching `e2e_long_form.rs`'s default, **not** `e2e_event_reminder.rs`'s `:3001` default). Uses HTTP directly only for the two channel-creation helpers (`create_agent_owned_channel`, `create_private_agent_owned_channel`) — everything else (messages, edits, deletes, admin commands, NIP-OA authentication) goes through the WebSocket harness. Depends on the relay's `is_agent_owner` DB-backed lookup (`buzz-db`'s `user.rs:354`) being correctly populated by the NIP-OA authentication handshake — i.e. this file's correctness is coupled to the relay's auth pipeline persisting the owner↔agent relationship, not just accepting the AUTH frame.

#### `e2e_git.rs` — the heaviest integration surface in this group

Confirmed independently (not merely assumed from the prior `git-identity` analysis): the file's own module doc (`:1-16`) states plainly "Requires: relay at localhost:3000 with git + S3/MinIO configured, `git` on PATH, and the `git-credential-nostr` helper built," and the concrete dependencies are:

1. **Relay HTTP bridge** — `relay_http_url()` defaults to `http://localhost:3000` via `RELAY_HTTP_URL` (`:28-30`); used for the kind:30617 announce (`post_event`, `:47-59`) and implicitly by `git` itself hitting the relay's git-smart-HTTP endpoints under `{relay_http_url}/git/{owner}/{repo}`.
2. **Real `git` binary on `PATH`** — every git operation (`clone`, `add`, `commit`, `branch`, `push`, `pull`, `reset`, `tag`, `rev-parse`, `log`) is a genuine subprocess spawn via `Command::new("git")` (`git_status`, `:65-90`), not a library call or mock. The test isolates each invocation from the ambient environment via `-c credential.useHttpPath=true`, `-c commit.gpgsign=false`, `-c tag.gpgsign=false`, explicit `-c user.name=E2E -c user.email=e2e@example.com`, and `GIT_CONFIG_GLOBAL=/dev/null` + `GIT_CONFIG_NOSYSTEM=1` (`:69-87`) so a developer's or CI runner's own `~/.gitconfig` (e.g. commit signing) cannot leak into the test.
3. **`git-credential-nostr` binary** — resolved via `GIT_CREDENTIAL_NOSTR_BIN` env var, or derived as `<workspace-root>/target/release/git-credential-nostr` from `CARGO_MANIFEST_DIR` (`credential_helper`, `:34-42`). Wired into every git invocation as `credential.helper=<path>` (`:71-73`), and each invocation passes the pushing/pulling identity's `nsec` via the `NOSTR_PRIVATE_KEY` env var (`:88`), which `git-credential-nostr` reads directly (`crates/git-credential-nostr/src/lib.rs:51-56`, `load_key`) to sign a NIP-98 kind:27235 HTTP-auth event per git-over-HTTP request (`lib.rs:213-224`). This is the only place in the repository that exercises the real `git-credential-nostr` binary end-to-end against a live relay — confirmed by the crate's own dependency direction (nothing in `git-credential-nostr`'s own `tests/` directory spins up a relay; per its listing it has only unit-style tests) and by this file's doc comment explicitly naming the binary as a hard requirement.
4. **S3/MinIO, accessed twice over, independently** — once implicitly (the relay's own git-store reads/writes packs and the manifest pointer as part of servicing clone/push/fetch), and once **explicitly** by the test itself via `GitS3Probe` (`:107-193`), which opens its own `rust-s3` `Bucket` client using `BUZZ_GIT_S3_*` env vars (falling back to `BUZZ_S3_*`, then hardcoded MinIO dev defaults `endpoint=http://localhost:9000`, `access_key=buzz_dev`, `secret_key=buzz_dev_secret`, `bucket=buzz-media`, `:117-136`) to read the manifest pointer object directly and assert on its bytes. This means the test's assertions about "the pointer advanced" are **not** relay-mediated — they bypass the relay's own API entirely and read the backing store directly, which is what lets the test distinguish "git says it pushed" from "the durable pointer actually moved." The MinIO defaults match the values seeded by `docker-compose.yml`'s `minio` service (`MINIO_ROOT_USER=buzz_dev`, `MINIO_ROOT_PASSWORD=buzz_dev_secret`, `docker-compose.yml:108-109`) and its `minio-init` sidecar, which creates a bucket literally named `buzz-media` (`docker-compose.yml:143`) — so the test's hardcoded bucket-name fallback of `"buzz-media"` (`:130`) is the *media* bucket, reused for git objects rather than a dedicated git bucket, matching the documented git-store behavior of reusing `media.s3_*` config (noted independently in the prior `.aidlc` configuration analysis).

**Confirmed independently, per the task's request not to merely assume the prior finding**: both tests in this file carry `#[ignore = "requires live relay + MinIO + git"]` (`:196`, `:334`), and a repository-wide search turns up zero references to `e2e_git` in any `.github/workflows/*.yml`, `Justfile`, or `scripts/*.sh` — `grep -rn 'e2e_git' .github/ Justfile scripts/` returns no matches (verified directly, not inferred). This means `e2e_git.rs`'s tests genuinely never run automatically anywhere in this repository's CI; they are exclusively a manual/local verification tool, run per the module doc's own instructions (`cargo build --release -p git-credential-nostr` then `GIT_CREDENTIAL_NOSTR_BIN=... cargo test -p buzz-test-client --test e2e_git -- --ignored --nocapture`, `:11-16`). This matches `docs/git-on-object-storage.md`'s own framing of `e2e_git::git_concurrent_push_one_wins_and_repo_recovers` as "the checked-in regression fence" for the 8-way CAS race — the spec document treats the test as authoritative evidence, but that evidence is only ever generated by a human (or an out-of-band process) choosing to run it locally; it is not continuously re-validated by any automated pipeline in this repository. See Debt for the consequence of this.

**Correction to the framing implied by prior analysis for the other three files**: unlike `e2e_git.rs`, `e2e_event_reminder.rs` is **not** purely a manual/local tool — see Configuration and Debt for the CI wiring that runs it under `cargo nextest run -E 'binary(e2e_event_reminder)' --run-ignored ignored-only` in the `backend-integration` job (`.github/workflows/ci.yml:682-693`), sourced from an archive built by the `desktop-e2e-relay` job's `cargo nextest archive ... --test e2e_event_reminder` (`.github/workflows/ci.yml:337-347`). `e2e_long_form.rs` and `e2e_human_edit_agent_content.rs` have no such wiring anywhere (`grep -rn 'e2e_long_form\|e2e_human_edit_agent_content' .github/ Justfile scripts/` returns no matches, verified directly) — those two remain purely manual, like `e2e_git.rs`.

#### Crate dependencies beyond the shared harness

Per `crates/buzz-test-client/Cargo.toml`: the crate's `[dev-dependencies]` include `reqwest` (used by three of these four files for HTTP), `s3` (`rust-s3`, feature-gated to `tokio-rustls-tls`, `fail-on-err`, `tags` — used only by `e2e_git.rs`), and `buzz-sdk` (used only by `e2e_human_edit_agent_content.rs`, for `nip_oa`). `e2e_git.rs` additionally depends on the *build output* of a sibling crate (`git-credential-nostr`) rather than a `Cargo.toml` dependency edge — that binary must be compiled separately and located via an env var or a hardcoded relative path, which is a filesystem-level coupling, not a Cargo dependency graph edge.
